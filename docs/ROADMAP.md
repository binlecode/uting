## 记录在案的 NO

每条一个形状：**决定 · 理由 · 重开条件**。这几条是被提过又被拒的方向，再提之前先读。

- **打包 NO —— 公开，但不为分发打包。** 仓库以参考实现的身份公开（文档是更可传播的产物），
  不打包、无 installer、无 `v*` tag：支持面（`RESEARCH-tui-player.md` §4）大于差异化
  （`ARCHITECTURE.md`「六条发现」第 1 条）。**重开 = 真的要单文件分发** —— 那要一个静态
  二进制，所以它开的其实是 Go 重写 NO。

- **喜马拉雅 NO** —— `m` 端点要 `webtk`（每请求现算的令牌，住在 cookie jar 之外），
  "浏览器 profile → 导 jar → curl -b"在机制上够不到；而只有 resolve 没有 search 的不是引擎
  （`ARCHITECTURE.md`「平级动词，没有内核」）。**死线索**（挡住重走）：换端点、参数八种组合、
  先取首页 cookie、补 `xm-sign`、真登录重导 jar、SSR —— 全试过。
  **重开 = 喜马拉雅 `m` 侧不再答 `webtk缺失`**（上次实测 2026-08-28）。

  这一条原本叫"第三对引擎 NO"，作用域其实只有喜马拉雅：同一条里点名的候选**网易云已经落地**
  （`ne-search` + `ne-resolve`，2026-09-02），所以标题改成它真正拦住的那个站。落地过程中
  这条记的两件事被实测推翻，就地更正而不是留着：搜索半边**不再是明文**（旧的
  `/api/search/get/web` 返回加密块，走的是 weapi + 两道 AES，openssl 因此成了 `ne-search`
  一个文件的依赖），而"resolve 半边没量过"已经量过了 —— yt-dlp 的 `netease:song` 够用，
  半边一行自研代码都不必写。为什么这样切、代价是什么，在 `AS-BUILT-engine.md`。

- **ut-search NO** —— 它存在的理由只有 fan-out + 合并信封，砍掉即第二拼法
  （`ARCHITECTURE.md`「平级动词，没有内核」直接毙）；代价（多一个命令、冻结面上一种新信封形状）
  压过收益。**重开 = 第三对引擎落地** —— 先修三处把信封级 `engine` 当行 engine 的地方
  （`ut-playlist` 的 `results` 分支、`uting` 的 `build_all_rows` 与 `FOCUSED_PAYLOAD`）。

- **list= NO —— 一条 URL 里的 `list=` 不变成一个队列。** 它与起播偏移长得像同一类东西
  （都是链接里搭的一个 query 参数），但不是一个量级：偏移是**一个数**，由引擎读出、由播放器
  交给 mpv 一个 flag；`list=` 是把**一个句柄变成一份条目清单**，也就是一次分页的播放列表
  抽取、一份要塞进队列文件的记录数组，以及"清单变了怎么办"这个 `--queue` 今天不回答的问题。
  **重开 = 有人真的要它**，且第一步不是解析那个参数，而是回答清单的所有权：它是
  `<engine>-resolve` 的一个新动词（像 `--parts`），还是 `ut-playlist` 的一次导入 ——
  队列本身不是候选，队列是被消费中的播放列表（`AS-BUILT-player.md`「队列」）。

- **`--vo-tct-algo=plain` NO —— viz 不提供"满格"这一档。** 它看起来是白拿的：实测同一首曲子、
  同一个 120×30 pane，10 秒里 plain 是 0.64s CPU / 3.6MB 转义序列，half-blocks 是 0.69s /
  7.3MB —— 字节省一半、CPU 一样（2026-09-01）。但把柱顶放大看就知道代价不是"格子粗一倍"：
  **plain 那边糊了**。画布是按半格算的 `rows × 2`，而 plain 只吃 `rows × 1`，mpv 要降采样，
  柱顶被混成一格半亮的青；half-blocks 是 1:1，没有缩放，边缘是硬的。而省下的 370KB/s 本来
  就不是瓶颈。**重开 = 有人真的在一个吞不下 300KB/s 的终端上跑它**，并且第一步不是加一档
  algo，而是把画布一起降回 `rows × 1` —— 否则换来的是更少的纵向级数**加上**一个模糊的边。

- **图片不走 mpv 的 VO NO —— 终端里画图这件事，mpv 不是那个后端。** 这条**只否掉一条路线，
  不否掉功能本身**（图片功能是 `PLAN-` 的事，这里不答）。理由是实测的三条（2026-09-01，
  `RESEARCH-terminal-graphics.md`「不加依赖能走多远」）：mpv 给的是一个 **VO 不是一个 widget**
  —— 一帧输出里带 `\e[?1003h`（抢鼠标上报）与 `\e[2J`（清整屏，`--vo-kitty-alt-screen=no`
  也照清），而 `uting` 自己拥有终端（`AS-BUILT-tui.md`）；载荷是 `f=24` **未压缩**，
  一张 320×180 = **462KB** 且**与显示格子大小无关**（协议传原图）；**不带 `i=` 图像 id**，
  每帧整幅重传。**同一张图自己发 `f=100`（PNG，用 mpv 的 `--vo=image` 转码得来）是 52,012
  字节，而且只在换行时付一次、不是每帧** —— `base64`/`fold` 都在 `/usr/bin`，不是新依赖；
  mpv 在那条管线里只当解码器，一个转义序列都不发。所以贵的是这条**路线**，不是这件事。
  **顺带钉死两条别再重提**：chafa / img2sixel / ueberzugpp / kitty 的 `icat` 一律是**新增
  运行时依赖**，撞 `CLAUDE.md` 的硬规则；而缩略图 URL **不是契约缺口** —— 引擎的 `-J`
  现在就带着（`yt-search` 的 thumbnail arrays、`bili-search` 的 `pic`）。
  **重开 = mpv 长出一个不抢屏幕的放置模式**，或 `--vo-kitty-use-shm` / 图像 id 被实测证明
  把载荷压到手写发射器的量级（怎么量见「本轮没能确定的问号」）。
  **不在这条 NO 之内**：`YT_ASCII_VO=kitty` 的 viz 今天就能跑（门在 `ut-play` 的
  `mpv_supports_vo`）—— 那一格 mpv 的 VO 语义正合适，因为那时屏幕本来就归它。

- **Go 重写 NO —— 不做 Go 版。** 差异化在契约不在渲染，而契约与语言无关
  （`ARCHITECTURE.md`「六条发现」第 1 条）；single-binary 全有全无 —— 引擎永不移植（随外部
  网站变，shell 的原地可改性是净收益），于是 Go TUI 或 Go 播放器接 shell 引擎仍是四依赖，
  分发收益不兑现（「六条发现」第 2 条）；剩给移植的只有"删渲染负债"，买它要付一次生命周期
  语义与渲染器无法二分的回归风险。**Linux 不是理由**：mpv IPC 的硬卡点已由 netcat 变体探测
  关闭（`ARCHITECTURE.md`「已知约束」）。同样不足以构成理由：流式搜索结果、每次按键 fork
  `stty`、带编译期保证的测试套件、bash 3.2/5 双版本矩阵、busybox-only 环境。
  **两个重开条件**：真的要 MCP 那张脸（解除「定位与设计目标」的那条非目标 —— 领域证据与
  可抄的工程细节在 `RESEARCH-tui-player.md` §10），或**打包 NO 反转**。哪一条成立，
  第一步都是冻结当时的契约（`ARCHITECTURE.md`「冻结面」）。

- **按键注册表 NO —— 键位不进一张表。** 提这条的来源是 go-musicfox（`internal/keybindings`：
  按键先映射成语义化的 `OperateType`，再由事件处理器分发，配置文件改的是那层映射）。两半都
  不成立。**机制这半**：`uting` 的键门控是**表达式不是数据** —— `b`/`h`/`c`/`i` 在自己的视图里
  改标签（「打开」变「返回」），`e` 按已装引擎数量门控，`c`/`i` 按 `--parts` / `--info` 的能力
  门控（`display_list_menu` 的 `nav_items` 块）。做成表，每行就要挂一个门控表达式，于是要么
  `eval`，要么每行再挂一个 `case` —— 那不是消掉 `case`，是把它搬了个家，还顺手把今天钉在每个
  分支上的那些注释挤掉，而在这个文件里注释就是被保存的那部分。**动机这半**：go-musicfox 的
  注册表存在的理由是**键位可配置**，`uting` 没有这个需求，也没人提过。今天键的拼写出现在四处
  （dispatch 的 `case`、`nav_items` 的短标签、`usage()`、README），但那是**四种视图**不是四份
  同一个事实：`usage()` 是这个面的规范陈述（硬规则 2），短标签是本地化过的一两个词。
  **重开 = 真的要用户可配置键位** —— 届时第一步不是抽表，而是先答「一个用户改了的键，
  `usage()` 与提示块怎么跟着改」，因为那才是注册表真正买到的东西。

- **terminfo 探测 truecolor NO** —— 24 位色的探针只有 `COLORTERM`，不查 terminfo 的
  `RGB`/`Tc` 能力位。提这条的动机是"community 主题在某些终端悄悄退回 ANSI-16"，两半都经不起
  实测（2026-09-01，本机）：macOS 自带 `infocmp` 是 **ncurses 6.0.20150808**，而 `RGB` 是
  6.1（2018）才进的能力位 —— `xterm-256color`/`tmux-256color` 里都查不到它，库里也根本没有
  `xterm-direct`，所以这个探针在**首要平台上恒答"不支持"**，比现状更差；而 **tmux 3.7c 实测
  原样透传 `COLORTERM`**（外层 `truecolor` → 内层仍 `truecolor`），要补的那个洞本身不存在。
  **重开 = macOS 自带 ncurses ≥ 6.1**，或出现一个真支持 24 位色却不设 `COLORTERM` 的终端 ——
  届时也是按名字加白名单，而不是去查 terminfo。

## 重开触发器 —— 已定之事各自等着的条件

决定本身（含理由）住在 `ARCHITECTURE.md`「设计决定」；这里只记会把它重新打开的条件，
和触发后的第一步。

| 决定（章在 `ARCHITECTURE.md`） | 触发器 | 触发后的第一步 |
|---|---|---|
| 「站点知识的边界」B 站搜索走 curl | yt-dlp 的 `BiliBiliSearchIE` 学会透传元数据 | 删掉本仓的 HTTP 路径 |

| 「站点知识的边界」`auth` 只报"发不发" | 有用户被过期会话上的 `auth=chrome` 误导 | 加 `--auth --probe`，不改 `auth` 键的语义 |

## 还没做的事（每条等着自己的前置）

- **一条搜索结果 ≠ 一个可播对象：合集与专辑容器要在信封里说清。** 实测搜"周杰伦"前三条全是
  数小时的长合集，这是该站音乐消费的主流形态而非 bug。这是**引擎的**活：由 `<engine>-search`
  在信封里说，不让 `uting` 猜 —— 只在 TUI 加标记就是漏掉 agent 面的半个功能。**面已经在了**
  （行带必填的 `kind`/`access`），缺的是**信号**。

  **`access` 那一半已经交付了**：`ne-search` 从站点自己的 `fee` 算出 `full`/`preview`/
  `paywalled`，在已经取回的那一页里，零额外请求（`AS-BUILT-engine.md`「`kind` 与 `access`」）。
  这条等的"带真信号的引擎"就是它。**还欠的是 `kind`**：三个引擎至今都恒印 `track`，
  而合集/专辑容器正是它要说的那件事 —— 实测搜"周杰伦"前三条全是数小时的长合集。
  网易云能不能答这一半没量过：它的搜索是 `type:1`（单曲），专辑与歌单是另外的 type，
  开工第一步是量"一次请求能不能同时带回容器行"。（多 P 那一形态有 `bili-resolve --parts`；
  本条只剩容器类结果本身。）

- **B 站音频区（`au` 号）的歌词，走已有的字幕管线。** yt-dlp 的 `BilibiliAudioIE` 把
  `song.lyric` 作为 subtitles 暴露 —— 与 `yt-resolve --transcript` 同一条管线，届时
  `bili-resolve` 才长出 `--transcript`。**证据强度如实记：读源码得出、从未实跑**，
  开工第一步是拿真 `au` 号验证。前置：`bili-search` 只搜视频区，音频区的边界待答。

- **三个不可丢的文本预算，一个钳到 12、两个钳到 8 —— 待判，不是待编码。** 给布局预算的
  共用数字命名时（`LAYOUT_MIN_FIELD` / `LAYOUT_MIN_BUDGET` 等，已落地）穷举出两处同值
  但机制不同、因而**没有**被合并进常量的站点：结果行标题钳的是 12，而确认框标题与歌单名
  钳的是 8 —— 三者都是不可丢的文本预算；横幅字段阶梯的最后一级用的是 8，但它的机制是
  「丢」而不是「钳」。这可能是一处**已经存在的不一致**，也可能是三个不同的事实碰巧同值，
  而分辨它们要先答「结果行标题为什么比确认框标题更值钱」。**动任何一处都会改屏幕**，
  所以它没有跟着那一轮零行为变化的改动一起落地。开工第一步是在
  `tests/drive.sh` 的窄几何上把三处各自的降级点量出来，而不是先挑一个数。

- **下载器** —— 唯一一个引擎必须参与的条目；它会不会把引擎从"解流"推回"完整客户端"、与
  `ARCHITECTURE.md`「站点知识的边界」的分界冲突，是开工前要先答的问题。

- **频道订阅** —— 套件里第一个不由用户按键触发的路径，需要周期性调度（launchd/cron）；
  与"不做常驻特权进程"（`CLAUDE.md`）如何并存是前置问题。

## 还没定的事

- **MCP 那张脸到底属不属于这个产品** —— 还是 agent 通过通用 shell 工具直接调这些动词就够了？
  它只挡着 Go 重写 NO 的那条 MCP 重开条件，别的什么都不挡（领域证据两头都有：
  `RESEARCH-tui-player.md` §10）。
- **viz 的配色要不要可配** —— 现在是硬编码的 cyan。已经排除的是**读 `YT_THEME`**：
  调色板只住在 `uting` 里，让播放器读它就要在第二个文件里再写一份 theme→颜色的表；而且
  `uting` 一律 `-d` 播放、detached 拒绝 viz，所以那一刻屏幕上根本没有 chrome 在场可匹配。
  剩下的形状是**一个颜色键**而不是一张表：`UT_VIZ_COLOR`（ffmpeg 颜色名或 `0xRRGGBB`）
  加一个长选项 `--viz-color`（长选项，因为 `--color` 已立先例"没有 `-c`"，而 `t` 在
  `uting` 里已经是 theme 键）。只剩**要不要收**这一个问题。

- **引擎边界** —— 第三方音源的引擎对进本仓，还是各自成仓、只靠 `AS-BUILT-cli-contract.md` 对齐？
  能照着写引擎的文档在了（「数据契约」的引擎 envelope + 「加一个引擎」的清单），
  所以只剩**要不要收**，而不是**能不能靠文档对齐**。
