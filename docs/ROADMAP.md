## 横切规范 —— 每个新功能都要过的判据

这几条不描述代码，它们是**提案的过关条件**：一条新功能、一个新键、一条新提示进来之前，
先拿它们量一遍。写在这里而不是 `ARCHITECTURE.md`，因为那一份装的是**已落地的决定**，
而这些是**约束未来**的东西 —— 与下面那些 NO 同一性质，只是形状是"必须"而不是"不做"。

- **一个功能必带 agent 面。** 人有按键，agent 就要有动词加一个 `-j` 信封。
  **理由**：这套东西的定位是 agent 优先（`ARCHITECTURE.md`「定位与设计目标」），
  一个只有键位的功能只做了一半。**它挡住的形状**：先给 TUI 加个键、"agent 面回头再说" ——
  回头就是永远，而契约面是冻结的，补进去要开一次冻结面。收听那三件（播放列表、队列、
  收听日志）各自的键位与动词在同一个提交里到达，就是这条被执行过的样子。

- **按下前可预期 —— 但要分清"根本做不了"与"答案可能是没有"。** 两类键，两套要求，
  混为一谈的那一版是这条规范的第一稿，写完当天就被实测推翻了。
  **一、结构上做不了的键，不许占一格**：`e` 在单引擎装机上、`a`/`b`/`d` 在没装 `ut-playlist`
  时、`o` 在存储的行上 —— 按之前就知道答案，门控是白拿的，`nav_items` 今天已经这么做。
  **二、`c`/`i` 不是那一类，它们是提问键**：问的是"这一行里面还有没有东西"，而"没有"是一个
  合法答案。**实测 2026-09-03，三个站的搜索页里都没有这个信号**：B 站一条真 200P 的行与
  一条 5 分钟 MV 的键集逐字相同（`episode_count_text` 同样为空、`is_union_video` 同样为 0，
  站方自己的分 P 数在另一个端点、每行一次请求）；YouTube 的 flat 搜索条目里没有任何
  chapter/marker/section 字段；网易云 `type:1` 只回单曲。要这个信号就是每行加一次往返。
  **所以提问键改由三条约束管，每条都可检验**：不许偷走下一个按键（提示进帧）；
  否定的答案也要把它买到的东西带回来（`i` 带回上传日期与赞数）；同一个答案不许买第二次
  （单槽缓存 —— `i` 一直有，`c` 是 2026-09-03 补上的）。
  **仍然不许**由 UI 去猜那个信号（`ARCHITECTURE.md`「站点知识的边界」：`access` 是引擎算的，
  不是 UI 猜的）——标题里写着"【200P】"不是一个字段。

- **只为一个答案停下来。** 界面阻塞等键，只能是因为它真的要一个**答案**（歌单名、`y/N`）。
  一条不需要回答的消息是**帧的内容**，由那唯一的渲染器画出来，下一次状态变化就没了。
  **理由**：一条模态消息把下一个键的语义变成"撤消息 or 命令"二选一，而这个套件里
  两次事故同源于此（一次是提示返回的 1 在撤提示的那个键上把 TUI 杀了，一次是
  `tests/contract.sh` 的走行检查因为要替它喂键而 flaky）。**它挡住的形状**：
  `printf` 进滚动区 + `read` 吃一个键 —— 那是被删掉的第二个渲染器的缩小版，
  判据一样：**要么进帧，要么别占屏**（`ARCHITECTURE.md`「人机面」）。

- **付了的代价不丢。** 用户明确要的一次网络往返，取回来的东西要落到屏上；不因"没有行可换"
  就把整份丢掉。**理由**：那次往返是用户按键买下的。**它挡住的形状**：一个行源开不了门就
  `return 1`，连同已经取回、屏上有地方放的字段一起扔掉。

## 记录在案的 NO

每条一个形状：**决定 · 理由 · 重开条件**。这几条是被提过又被拒的方向，再提之前先读。

- **打包 NO —— 公开，但不为分发打包。** 仓库以参考实现的身份公开（文档是更可传播的产物），
  不打包、无 installer、无 `v*` tag：支持面（`RESEARCH-tui-player.md` §4）大于差异化
  （`ARCHITECTURE.md`「六条发现」第 1 条）。**重开 = 真的要单文件分发** —— 那要一个静态
  二进制，所以它开的其实是 Go 重写 NO。

- **喜马拉雅 NO** —— `m` 端点要 `webtk`（每请求现算的令牌，住在 cookie jar 之外），
  "浏览器 profile → 导 jar → curl -b"在机制上够不到；而只有 resolve 没有 search 的不是引擎
  （`ARCHITECTURE.md`「平级动词，没有内核」）。**死线索**（挡住重走）：换端点、参数八种组合、
  先取首页 cookie、补 `xm-sign`、真登录重导 jar、SSR —— 全试过。
  **重开 = 喜马拉雅 `m` 侧不再答 `webtk缺失`**（上次实测 2026-08-28）。
  作用域只有这一个站：换一个站就是换一对引擎，与这条无关。

- **ut-search NO —— 触发过一次，重新决定过一次，仍然是 NO（2026-09-03）。** 决定本身是：不做
  这个动词，它存在的理由只有 fan-out + 合并信封，砍掉即第二拼法（`ARCHITECTURE.md`
  「平级动词，没有内核」直接毙），代价（多一个命令、冻结面上一种新信封形状）压过收益。
  **触发器"第三对引擎落地"确实在 2026-09-02 触发了**，于是这条被真的重新算了一次，
  结论不变，而**理由多了一条，是那次重算自己给出的**：同一天定下的行模型（见「容器行」）
  把容器推向**各自的动词与信封**，于是每个引擎的搜索面在可预见的将来都不止一种形状 ——
  一个跨引擎的合并动词要合并的不再是"一种信封 × N 个引擎"，而是"N 种形状 × N 个引擎"。
  触发器让它更贵，不是更便宜。而今天的替代品是调用方的一行循环：
  `for e in yt bili ne; do "$e-search" -j -n 5 -- "$q"; done`。
  **重开 = 真的有人要那份合并信封**（而不是"第 N 对引擎落地了"—— 那个触发器已经用掉了）。
  **重开后的第一步不变**：先修三处把信封级 `engine` 当行 `engine` 的地方（`ut-playlist` 的
  `results` 分支、`uting` 的 `build_all_rows` 与 `FOCUSED_PAYLOAD`）。**刻意不提前修**：
  没有 fan-out 就没有任何生产者会发出带行级 `engine` 的行，那三行 `(.engine // $e)` 会是
  **没有输入能让它红**的分支，而这个仓库对这种检查与这种代码是同一条规矩
  （`CLAUDE.md`「Testing Guidelines」）。

- **list= NO —— 一条 URL 里的 `list=` 不变成一个队列。** 它与起播偏移长得像同一类东西
  （都是链接里搭的一个 query 参数），但不是一个量级：偏移是**一个数**，由引擎读出、由播放器
  交给 mpv 一个 flag；`list=` 是把**一个句柄变成一份条目清单**，也就是一次分页的播放列表
  抽取、一份要塞进队列文件的记录数组，以及"清单变了怎么办"这个 `--queue` 今天不回答的问题。
  **重开 = 有人真的要它**，且第一步不是解析那个参数，而是回答清单的所有权：它是
  `<engine>-resolve` 的一个新动词（像 `--parts`），还是 `ut-playlist` 的一次导入 ——
  队列本身不是候选，队列是被消费中的播放列表（`AS-BUILT-player.md`「队列」）。

- **`--vo-tct-algo=plain` NO —— viz 不提供"满格"这一档。** 它看起来是白拿的（字节省一半、
  CPU 一样），但代价不是"格子粗一倍"而是**糊**：画布是按半格算的 `rows × 2`，plain 只吃
  `rows × 1`，mpv 要降采样，柱顶被混成一格半亮的青；half-blocks 是 1:1，边缘是硬的。
  而省下的那点字节本来就不是瓶颈。数字见
  `RESEARCH-terminal-graphics.md`「`--vo-tct-algo`：省一半字节，买一个糊的边」。
  **重开 = 有人真的在一个吞不下那个码率的终端上跑它**，并且第一步不是加一档 algo，
  而是把画布一起降回 `rows × 1` —— 否则换来的是更少的纵向级数**加上**一个模糊的边。

- **图片不走 mpv 的 VO NO —— 终端里画图这件事，mpv 不是那个后端。** 这条**只否掉一条路线，
  不否掉功能本身**（图片功能是 `PLAN-` 的事，这里不答）。三条理由，全部实测于 2026-09-01，
  数据在 `RESEARCH-terminal-graphics.md`「不加依赖能走多远」与「载荷的量级也不成立」：
  mpv 给的是一个 **VO 不是一个 widget**（一帧里带抢鼠标与清整屏的转义序列，而 `uting`
  自己拥有终端）；载荷是**未压缩**的，且**与显示格子大小无关**；**不带图像 id**，每帧整幅重传。
  而**同一张图自己发 PNG 那一档便宜一个量级，且只在换行时付一次**（同上，「但 mpv 不是唯一的路」）
  —— 所以贵的是这条**路线**，不是这件事。
  **顺带钉死两条别再重提**：chafa / img2sixel / ueberzugpp / kitty 的 `icat` 一律是**新增
  运行时依赖**，撞 `CLAUDE.md` 的硬规则；而缩略图 URL **不是契约缺口** —— 引擎的 `-J`
  现在就带着（同上，「像素从哪来」）。
  **重开 = mpv 长出一个不抢屏幕的放置模式**，或共享内存 / 图像 id 被实测证明把载荷压到
  手写发射器的量级（怎么量见该文「怎么重跑这份调研」）。
  **不在这条 NO 之内**：`YT_ASCII_VO=kitty` 的 viz 今天就能跑（门在 `ut-play` 的
  `mpv_supports_vo`）—— 那一格 mpv 的 VO 语义正合适，因为那时屏幕本来就归它。

- **Go 重写 NO —— 不做 Go 版。** 差异化在契约不在渲染，而契约与语言无关
  （`ARCHITECTURE.md`「六条发现」第 1 条）；single-binary 全有全无 —— 引擎永不移植（随外部
  网站变，shell 的原地可改性是净收益），于是 Go TUI 或 Go 播放器接 shell 引擎仍是四依赖，
  分发收益不兑现（同上，第 2 条）；剩给移植的只有"删渲染负债"，买它要付一次生命周期
  语义与渲染器无法二分的回归风险。**Linux 不是理由**：mpv IPC 的硬卡点已由 netcat 变体探测
  关闭（`ARCHITECTURE.md`「已知约束」）。同样不足以构成理由：流式搜索结果、每次按键 fork
  `stty`、带编译期保证的测试套件、bash 3.2/5 双版本矩阵、busybox-only 环境。
  **两个重开条件**：真的要 MCP 那张脸（解除「定位与设计目标」的那条非目标 —— 领域证据在
  `RESEARCH-tui-player.md` §10），或**打包 NO 反转**。哪一条成立，第一步都是冻结当时的契约
  （`ARCHITECTURE.md`「冻结面」）。

- **按键注册表 NO —— 键位不进一张表。** 提这条的来源是 go-musicfox（按键先映射成语义化的
  操作类型，再由事件处理器分发，配置文件改的是那层映射）。两半都不成立。**机制这半**：
  `uting` 的键门控是**表达式不是数据** —— `b`/`h`/`c`/`i` 在自己的视图里改标签（「打开」变
  「返回」），`e` 按已装引擎数量门控，`c`/`i` 按 `--parts` / `--info` 的能力门控。做成表，
  每行就要挂一个门控表达式，于是要么 `eval`，要么每行再挂一个 `case` —— 那不是消掉 `case`，
  是把它搬了个家，还顺手把今天钉在每个分支上的那些注释挤掉，而在这个文件里注释就是被保存的
  那部分。**动机这半**：那个注册表存在的理由是**键位可配置**，`uting` 没有这个需求，
  也没人提过。**重开 = 真的要用户可配置键位** —— 届时第一步不是抽表，而是先答
  「一个用户改了的键，`usage()` 与提示块怎么跟着改」，因为那才是注册表真正买到的东西。

- **terminfo 探测 truecolor NO** —— 24 位色的探针只有 `COLORTERM`，不查 terminfo 的
  `RGB`/`Tc` 能力位。两半都经不起实测（2026-09-01，本机；这里是这两个数字唯一的家）：
  macOS 自带 `infocmp` 是 **ncurses 6.0.20150808**，而 `RGB` 是 **6.1（2018）**才进的能力位
  —— 所以这个探针在**首要平台上恒答"不支持"**，比现状更差；而 **tmux 3.7c 实测原样透传
  `COLORTERM`**，要补的那个洞本身不存在。**重开 = macOS 自带 ncurses ≥ 6.1**，或出现一个
  真支持 24 位色却不设 `COLORTERM` 的终端 —— 届时也是按名字加白名单，而不是去查 terminfo。

## 还没做的事（每条等着自己的前置）

- **容器行 —— 一条搜索结果 ≠ 一个可播对象，而答案不在 `kind` 上。**
  **行模型已定（2026-09-03）：一行结果就是一次可播调用，容器不是行。** 这条曾经写着
  "面已经在了（行带必填的 `kind`/`access`），缺的是信号"，那个前提**被否掉了**：把频道、专辑、
  歌单、艺人全压进 `collection` 这一个枚举值，调用方就只能回头看 url 才知道自己拿到的是
  一张十二首的专辑还是一个无界的创作者目录 —— 那是**把站点知识挪回调用方**，正是引擎接缝
  存在的目的所要消掉的东西；而 `track_count`、分页游标这些容器真正需要的字段，在一行
  为播放而生的记录里**无处可放**（`duration`/`view_count`/`channel` 在容器上同时无意义）。
  枚举也不许为它长大（AS-BUILT-cli-contract.md「数据契约」）。
  **所以容器归它自己的动词与信封**，像 `--parts` 那样，字段各就各位。
  **落地的那一半**：`yt-search` 现在按 `ie_key` 丢掉容器行（YouTube 是唯一混装的搜索面 ——
  `ytsearch` 没有 scope 选择器，而 `bili-search` 的 `search_type=video` 与 `ne-search` 的
  `type:1` 早已把范围钉死，两者从未见过这个形态）。实测由来与失败形状：
  AS-BUILT-engine.md「`kind` 与 `access`」。
  **还开着的那一半，就是那个动词本身**：谁拥有清单。第一步不是写抽取，而是回答所有权 ——
  它是 `<engine>-search` 的第二个动词（`--albums`，查站方另外的 type），还是
  `<engine>-resolve` 的一个新动词（像 `--parts`），还是 `ut-playlist` 的一次导入。
  与 **`list=` NO** 是同一个问题的两种入口，一起答，别分头答。
  **`collection` 这个枚举值由此暂时无人认领** —— 要不要把枚举收窄成 {`track`, `multipart`}
  是**冻结面上的一次刻意动作**，不作为本条的副作用发生（收窄对调用方不破坏：没有引擎发过这个值）。
  **它救不了 `c`/`i` 的门控，别再这么记**：这里一度写着"一条 `kind` 落地，那两个键就能按行
  门控"，2026-09-03 的实测把它推翻了（三个站的数字在「横切规范」按下前可预期那条里）——
  信号不在已经取回的那一页里，所以 `c`/`i` 仍然是提问键。
  （多 P 那一形态有 `bili-resolve --parts`；本条只剩容器类结果本身。）

- **B 站音频区（`au` 号）的歌词，走已有的字幕管线。** yt-dlp 的 `BilibiliAudioIE` 把
  `song.lyric` 作为 subtitles 暴露 —— 与 `yt-resolve --transcript` 同一条管线，届时
  `bili-resolve` 才长出 `--transcript`。**证据强度如实记：读源码得出、从未实跑**，
  开工第一步是拿真 `au` 号验证。前置：`bili-search` 只搜视频区，音频区的边界待答。

- **三个不可丢的文本预算，一个钳到 12、两个钳到 8 —— 待判，不是待编码。** 结果行标题钳 12，
  确认框标题与歌单名钳 8；横幅字段阶梯的最后一级也用 8，但它的机制是「丢」而不是「钳」。
  这可能是一处**已经存在的不一致**，也可能是三个不同的事实碰巧同值，而分辨它们要先答
  「结果行标题为什么比确认框标题更值钱」。**动任何一处都会改屏幕**，所以开工第一步是在
  `tests/drive.sh` 的窄几何上把三处各自的降级点量出来，而不是先挑一个数。
