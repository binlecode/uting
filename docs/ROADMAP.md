## 8. 决定

每条一个形状：**决定 · 理由 · 重开条件**。机制与实测细节一律在 as-built 文档，这里只指过去。

- **D0 —— 定位冻结为 `ARCHITECTURE.md` §1**：agent 优先的媒体引擎（播放器 + 可插拔引擎对）+
  一张人脸；不做通用 TUI 播放器。音源数量不是定位的一部分；功能边界含 D14 那三条收听功能；
  差异化那三件不受任何功能变更影响。

- **D1 —— 不为分发打包 shell 套件。** 支持面（`RESEARCH-tui-player.md` §4）大于差异化
  （`ARCHITECTURE.md` §1.1 第 1 条）。**重开 = 走 §9 的单文件分发触发。**

- **D2 —— 但照样公开仓库，定位为参考实现，不承诺打包。** 文档是更可传播的产物。
  公开不改 D1：不打包、无 installer、无 `v*` tag（D13）。

- **D3 —— 任何重写之前先冻结契约。** 契约（envelope、player record、退出码表、生命周期语义，
  **含引擎契约**）是唯一完整活过重写的东西，也是 Go 版的验收规格；它整个写在
  `AS-BUILT-contract.md`。刻意排除的只有一处：`--get-url` / `--info` / `--transcript`
  是引擎的动词，不是播放器的（`ARCHITECTURE.md` §13）。

- **D4 —— Go 的第一步只做 TUI**（`uting` → Go），调用今天原封不动的引擎与 `ut-play`。
  被否：一次性全量移植 —— 生命周期语义和渲染器重写进同一次变更，回归无法二分定位。

- **D5 —— "播放器是否也去 Go"是独立的、条件触发的决定**（§9）。触发前 `ut-play` 保持 shell。
  引擎不在这个问题里：它们随外部网站变，shell 的原地可改性在那半边是净收益。

- **D6 —— 项目名 `uting`**（筛查数据 `RESEARCH-tui-player.md` §2）；一个命令一个名字，
  不留第二种拼法。挪威语里 `uting` 是真词（"陋习"）—— 当彩蛋接受。

- **D7 —— Go 版只发一个二进制加子命令，绝不发多个通用名的可执行文件。**

  ```sh
  uting search … · uting play … · uting <engine> search … · uting（无参数 → TUI）· uting mcp
  ```

  永不发布 `bin/yt`（D10）。上表是草稿，per-engine 层的最终形状留到 Go 真正开工时定。

- **D9 —— 套件按「播放器 + 可扩展搜索引擎」重切，不按站点开命令。**
  理由（接第二个音源时的实测）：一个"什么都做"的核心里必然有只对某一站成立的逻辑，
  按 `-s/--source` 分站会让每个新音源继承它们并长出 `if source ==` 树；真正与音源无关的是
  **播放器**，与音源有关的只有**抽取**。判据三条：**引擎 = 两个动词**（search / resolve），
  加音源只加一对脚本；**四命令而非子命令**（窄动词，agent 取向）；**resolve 发生在播放时**
  （直链会过期，10 条结果只用 1 条）。形状在 `ARCHITECTURE.md` §4/§5，契约在
  `AS-BUILT-contract.md` §3。

- **D10 —— 三类命令，三条命名规则，按"谁在敲它"分。**

  ```
    人机面   uting          发布名本身
    播放器   ut-play        套件前缀 ut-
    引擎     yt-* bili-*    站名 —— 一个引擎最该先说清自己是哪个站
    状态     ut-playlist / ut-history   前缀 + 存的那件东西的全词，不缩写
  ```

  **不发任何短名**：六项筛查的结果是长前缀名可用、短名全被占（`RESEARCH-tui-player.md` §2）；
  第二拼法就是第二个要同步的东西，人机面因此也不叫 `ut-tui`。
  **状态命令的落选名**（挡住重开）：`ut-list` 与 `-l/--list` 撞车读不通；`ut-lib`/`ut-store`
  把两件事挤进一个命令；`ut-queue` —— 队列不是命令，是播放器的运行时状态
  （`AS-BUILT-player.md` §9.5）。

- **D11 —— B 站引擎按「操作」分原语：搜索走 curl，解流走 yt-dlp。**
  理由：解流那块（签名、选流、CDN、风控）自建就是重造一个完整客户端，归 yt-dlp；
  而搜索那格 yt-dlp 走不通 —— flat 零元数据，非 flat 因合集逐 P 递归超时，直连一次请求就拿全
  字段（实测数字与 `buvid3` 的角色在 `AS-BUILT-engine.md` §7）。分界在**操作**不在站点，
  与 D9 同一条原则。**重开条件**：yt-dlp 的 `BiliBiliSearchIE` 对齐 `SoundcloudSearchIE`
  的元数据透传 —— 一个上游 patch 就翻转，那时本仓的 HTTP 路径整个删掉。

- **D12 —— 一个引擎一套：`<engine>-resolve` 只解自己站的 host，别的一律退 1。**
  理由：`engine` 字段存在的全部理由是把结果路由回正确的 resolve，通配 host 让它说谎。
  被否：通用引擎（一张测不了的站表）、引擎间 exec 委托（引擎之间长出依赖）。
  非本站 URL 是 usage 错（1）不是抽取失败（2+）：什么都没尝试。
  要付的账：URL-only 音源（Bandcamp 一类）接不进来。**重开条件**：它们成为真实需求 ——
  正确做法是给它写一对，不是放宽 host 校验。

- **D13 —— 版本号走 semver 2.0.0，版本化的对象是「契约」，不是代码。**
  公共 API 的边界表（在里面 / 不在里面）与 bump 判法住在 `AS-BUILT-contract.md` 开头。
  0.y.z 期间：破坏性 → y，加法与修复 → z（semver §4 说主版本 0 一切可变，把 y 当 major
  是社区通行做法）。**1.0.0 = D1/D2 反转那一天**（真打包、真有下游），不是"感觉稳了"；
  在那之前 0.x 是诚实的，不是谦虚的。tag 只在真发布时打（pre-push 校验与 `VERSION` 一致）。
  不设 CHANGELOG：那个事实已在 git log 里，真有下游时再从 tag 之间生成。

- **D14 —— 收听完整度属于本项目：队列、播放列表、收听历史在范围内**（`ARCHITECTURE.md` §1）。
  三条服务于这套音源上的收听，不是通用本地播放器的替代品；收藏 = 一个具名播放列表。
  **硬约束（对以后每条功能同样成立）：每一条都必须有 agent 面** —— 人能在 `uting` 里用，
  agent 能用一个动词加 `-j` 做同一件事，契约进 `AS-BUILT-contract.md`，回归进 `tests/`。
  历史默认开、`UT_HISTORY=0` 关。**重开条件**：跑在共享账号上 —— 那时收听记录不再是
  一个人的（`AS-BUILT-player.md` §9.6）。

- **D15 —— 这批功能在 shell 版做，不等 Go 重写。**
  理由按分量：刚需有时间成本而重写没有排期；难点是状态与数据模型、不是语言（shell 已有
  能用的状态层，`AS-BUILT-player.md` §9.2/§9.3）；先在 shell 里跑顺再进契约，Go 版继承的
  是被真实使用过的规格。代价如实记：`uting` 变大，bash 3.2 无关联数组，持久化只能落
  jq + 文件。

- **D16 —— 登录状态可见，但只可见到"发不发"这一层，不做鉴权探测。**
  `auth=chrome` 的意思是"播放会送 chrome 的 cookie"，不是"你登录着" —— 站点认不认、
  认了够到什么，都不在这个动词的射程内（实测边界在 `AS-BUILT-engine.md` §8.2）。
  被否：带凭据的探测往返 —— 对一个会限流的 host 每次启动多打一发，去答一个便宜事实已答掉
  八成的问题。**重开条件**：有用户被过期会话上的 `auth=chrome` 误导 —— 升级路径是加
  `--auth --probe`，不改 `auth` 键的语义。

- **D17 —— `--auth` 归 resolve 半边，不归 search 半边。**
  cookie 决定本来就住在 resolve 里。被否（搜索信封加 `auth` 字段）的两条理由各自足以否掉：
  两个引擎在此不对称（`bili-search` 一个凭据都不发，只能诚实报 `none`，而那描述的是搜索
  传输、与播放相反）；要让它报 `chrome` 就得抄第 4 份 profile 判断副本，为的是报告一个
  它自己不据以行动的决定。

- **D18 —— 配置是一条四层链（flag > 环境 > 用户配置 > 出厂 `config`）；两个文件都按 DATA
  读、绝不 source；出厂那份永不被写，用户那份由 `uting` 写回六个偏好键。**
  理由：八个不共享库的可执行文件，"每个默认值声明一次"只能落到数据文件；source 会执行任意
  代码，DATA 读法让 `UT_X=$(cmd)` 存下的只是那几个字符；一个每开一次会话就要重按的偏好等于
  没有偏好，而"设偏好"的 agent 面就是那个 `KEY=value` 文件本身 —— 不为它造第九个命令
  （与 D21 同一笔账）。缺出厂文件 = 退 2（坏 checkout，不是依赖门）。
  键表、写回的白名单与三条硬约束、进公共 API 的部分，全在 `AS-BUILT-contract.md` §5。
  **重开条件**：出现第二种宿主形态（如 Go 版把默认值编进二进制）时，"出厂默认值是一个文件"
  可重开；链的顺序与命名空间不跟着重开。写回的重开条件：出现第二个写入方 —— 那时再谈锁。

- **D19 —— 引擎按 site 切，不按 stack 切**（否决 `resolve-curl` + `resolve-ytdlp`）。
  判据是量出来的：两个 resolver 逐字相同的只有样板与六行 `dump_once`，逐站不同的是
  ~600 行（handle 语法、host 白名单、格式表、错误词汇）—— 按 stack 切共用 6 行、
  换来 600 行长成 `if site ==` 树。三样单独就足以否掉的塌方：`engine` 是被持久化的路由键
  而 stack 会变 site 不会；host 白名单写不出来（D12）；发现机制（glob 配对、字符串拼接找
  resolver）没了。真正的重复（八份样板）与 stack 正交，是"要不要共享库"那个独立问题。
  **重开条件**：出现一个音源，其 resolve 半边与既有引擎**逐字**相同 —— 那时判据自然翻转。

- **D20 —— 第三对引擎：不做喜马拉雅；真要第三个音源时从网易云起步。**
  喜马拉雅的搜索半边过不去：`m` 端点要 `webtk` —— 每请求现算的令牌、住在 cookie jar 之外，
  "浏览器 profile → 导 jar → curl -b"在原理上够不到；唯一通法是把反爬 bundle 逆进 bash，
  违反"引擎只做薄薄一层"。只有 resolve 没有 search 的东西不是引擎（D9），整对不做。
  **死线索**（挡住重走）：换端点、补参数八种组合、先取首页 cookie、补 `xm-sign`、
  真登录重导 jar、搜索页取 SSR —— 全试过。
  **候选网易云**：搜索端点明文、零凭据、形状与 B 站一致，`fee` 就在响应里（§11 第一条的
  判据现成）；**但只验了搜索半边** —— resolve 半边没量过，且调研给的气候是坏的
  （`RESEARCH-tui-player.md` §9），真开工第一步是量 resolve。
  **重开条件**：喜马拉雅 `m` 侧不再答 `webtk缺失`（上次实测 2026-08-28）。

- **D21 —— `ut-search`（统一搜索入口 + fan-out）：不做。**
  它存在的理由只有 fan-out + 合并信封，砍掉那个能力它就是每个 `X-search` 的第二拼法（D10
  直接毙）。代价（第九个命令、冻结面上一种新信封形状、TUI 三处修正）压过收益，而收益要等
  第三对引擎。**重开条件**：第三对引擎落地 —— 那时先修 `ut-playlist` 的 `results` 分支与
  `uting` 的 `build_all_rows` / `FOCUSED_PAYLOAD`（三处都把信封级 `engine` 当成行的 engine）。

## 9. 把播放器推向 Go 的触发条件（可选项，非计划）

**Go 移植是 optional，不在任何排期上**：shell 版就是产品本体，`ut-play` 无限期保持 shell
是正当终态，不是等待状态。这一节存在只为一件事 —— 万一哪条触发真的成立，界定"值得移植的
是什么、代价怎么算"。（引擎在任何情况下都不移植，见 D5。）任一为真，**播放器**移植才值得
它的风险：

1. **真的要 MCP**（解除 `ARCHITECTURE.md` §1 的那条非目标）。同格竞争者给出了可抄的工程
   细节 —— `spotatui` 的默认关闭 + 只绑 loopback + token、双时代协议兼容、stdout 只跑协议、
   应用内与 MCP 复用同一张 tool table。2026-08 的领域证据两头都有
   （`RESEARCH-tui-player.md` §10）：agent 面已是标配，但除 `spotuify` 外全部只做"查" ——
   "agent 直接调 CLI"没有被谁证伪，MCP 依旧只是包装层。附带情报：`kevinwatt/yt-dlp-mcp`
   与 `--transcript` 正面重叠，B 站侧 MCP 服务器与 `bili-resolve --info` 同理 ——
   真做时要说清为什么用本仓的。
2. **真的要单文件分发**（推翻 D1）。

**Linux 不是触发**：mpv IPC 的硬卡点由 netcat 变体探测关闭（`ARCHITECTURE.md` §26），
主流发行版装一个带 `-U` 的变体即通。次要、单独不足以触发：流式搜索结果；每次按键 fork
`stty`；带编译期保证的测试套件；bash 3.2/5 双版本矩阵；busybox-only 环境。

## 10. 落地计划

**编号是标识，不是顺序。** 两条都是可选项（§9），今天都不动 —— 不动是正当状态，不是欠账。

  Go 播放器照样 `exec <engine>-resolve`。验收：固定查询集上两实现 `-j` 逐字段 diff +
  生命周期序列退出码全等，**两个引擎各跑一遍**。之后、且仅在之后：`uting mcp`、
  curl 安装脚本、Homebrew tap。

## 11. Future work（已蒸馏，等触发条件）

- **B 站的一条搜索结果 ≠ 一个可播对象 —— 合集至少要标出来。** 实测搜"周杰伦"前三条全是
  数小时的长合集，这是该站音乐消费的主流形态而非 bug；分 P（`?p=N`）与"结果是专辑/歌单容器"
  是同一问题的另两种形态，三种一起解。这是**引擎的**活（correctness 加在下面）：由
  `<engine>-search` 在信封里说清，不让 `uting` 猜 —— 只在 TUI 加标记就是漏掉 agent 面的
  半个功能。**面已经在了**：行带必填的 `kind`/`access`（`AS-BUILT-contract.md` §3），
  但两个在产引擎都无信号可算、恒印 `track`/`full`（`AS-BUILT-engine.md` §7.2）。
  本条等一个带真信号的引擎 —— 网易云的 `fee` 是量过的那个。

- **B 站音频区（`au` 号）的歌词，走已有的字幕管线。** yt-dlp 的 `BilibiliAudioIE` 把
  `song.lyric` 作为 subtitles 暴露 —— 与 `yt-resolve --transcript` 同一条管线，届时
  `bili-resolve` 才长出 `--transcript`。**证据强度如实记：读源码得出、从未实跑**，
  开工第一步是拿真 `au` 号验证。前置：`bili-search` 只搜视频区，音频区的边界待答。

- **下载器** —— 唯一一个引擎必须参与的条目；它会不会把引擎从"解流"推回"完整客户端"、
