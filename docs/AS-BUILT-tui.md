# AS-BUILT-tui —— 人机面 `uting` 的实现

## 结构

`shell/uting` 的实现 why：引擎发现、**唯一那个视图**的渲染、防闪烁的原地重绘、reflow
与分页、键位与输入层、主题与中英 chrome，以及所有被实测钉死的规矩。
**代码是唯一权威**：点名的函数是 soft ref（文件 + 函数名），不复制实现。

## 模块

这个面持有渲染，且**不持有任何站点知识** —— 一条 YouTube 或 Bilibili 的事实出现在这个
文件里，就是分层违规（ARCHITECTURE.md「命令拓扑」的支配原则）。它也不持有播放与存储：
**纯编排**，对下只调那些动词；唯一被批准的例外是播放器在 `-d -j` 信封里公布出来的那个
mpv socket（AS-BUILT-player.md「运行时 IPC」）。

## 接口与 API

一个 TTY 上的键位面（键表由 `uting --help` 陈述、由 `tests/contract.sh` 的 tmux 段证明），
对下组合动词：`<engine>-search -j`、`ut-playlist` / `ut-history`、
`<engine>-resolve --info/--parts -j`、`ut-play -d -j --engine <行自己的引擎>`。
契约面在 `AS-BUILT-contract.md`。

### 调用面 —— 选项的乘积

`uting` 的 argv 面很窄（搜索参数转发给引擎，菜单参数留给自己），但它有一个别的命令没有的
前提：**它要真 TTY，stdin 和 stdout 都要**。下面每一条都对应 `tests/contract.sh` 的检查。

```sh
uting                                  # 无 query，交互式问
uting "lofi hip hop"                   # 直接搜
uting --engine bili -n 40 "周杰伦"      # 转发给 bili-search
uting -f video --volume 60 "…"          # 菜单参数：起播 mode 与起播音量
uting --theme nord --lang zh "…"        # chrome
```

**两道门，都退 1，而且顺序是固定的**：flag 门在前，TTY 门在后。

| 组合 | 报什么 |
|---|---|
| `-f ascii` / `-f viz` | `-f must be one of: audio, video, fast` —— 它的播放**一律 detached**，终端渲染模式永远到不了一个终端 |
| 管道 / 无 pty（`</dev/null`、CI） | `requires a terminal (interactive menu)` |
| `UT_*_CYCLE` 里有未知成员 | 点名那个键 |
| `--theme` / 标量旋钮值非法 | 点名那个键，不是笼统的用法错误 |

**这两道门必须靠文案分辨，不能靠退出码** —— 两道都是 1。一个只看退出码的检查，在「拒了这个
值」和「拒了这根管道」之间是分不开的，也就等于**不会失败**。套件里 uting 这一段的每条断言
都是匹配文案的，原因就是这个。

顺带一条不对称：**cycle 被收窄后仍然必须能启动**。`-f` 与 `-s` 的默认值是拿 cycle 校验的，
所以如果默认写成字面量 `audio`，`UT_MODE_CYCLE=video` 就成了一个「跑不起来的配置」——用户
收窄了 cycle，却被告知自己的 flag 错了。检查里「能走到 TTY 门」就是那一条的通过条件：那是
它后面紧邻的那道门。

## `uting` 编排（自有胶水，零站点逻辑）

图说的是*什么*，图后面的条目说的是不显然的*为什么*。

**引擎发现，以及这个文件为什么不持有源清单。** 启动时 `scan_engines` 在自己所在目录 glob
`*-search`，且只有当 `<name>-resolve` 就在旁边且可执行时才保留这个名字 —— 装了一半的引擎
不算引擎。只有当 checkout 里一个都没扫到时才去扫 PATH，于是常见情形只花一次 glob，
而一个光秃秃的 checkout 不装任何东西也能跑。**零个引擎是致命的启动错误**，并说出缺的是哪一对。
会话从 `UT_DEFAULT_ENGINE` 起步 —— **与 `ut-play` 读的是同一个变量**，不是第二个，
因为一个用户设过一次默认源之后，不该再按面设第二次 —— 那个名字不存在时回退到第一个已安装的引擎。
`e` 轮换（`cycle_engine`）并重新取数，新引擎取数失败时把上一个恢复回来；
少于两个引擎时它立即返回，这个交互也不画出来。

**状态行的 `auth=` 来自引擎，不来自这个文件。** 一个源从哪个浏览器读 cookie 是站点知识，
而 `uting` 一条也不持有 —— 所以它去问 `<engine>-resolve --auth -j`
（`engine_resolve_bin`，与 `engine_search_bin` 同一条拼接规矩，不是第二张表），
取回的 `auth`/`cookie_browser` 渲染成 `auth=chrome` 或 `auth=anon`。
`refresh_engine_auth` 在**启动时**与**每次 `e` 换源成功之后**各跑一次 ——
跑在恢复窗口之后，不是之前，因为换源失败时 `ENGINE` 停在原处，而那个 token
必须描述屏幕上真正在的那个引擎。不做缓存表：bash 3.2 没有关联数组，
一次不碰 I/O 的 fork 比维护一组平行数组的正确性便宜。

它**只**出现在搜索结果的状态行上。播放列表与历史的行是**混源**的
（那一支报的是 `engine=${PLAYLIST_ENGINES}`），一个单一的 auth token 在那里
对其中一半是假话。引擎的 resolve 半边没有 `--auth` 时它非零退出、字段直接消失 ——
与 `--transcript` 缺失同一套"以有没有声明能力"的降级（ARCHITECTURE.md「站点知识的边界」），
所以第三个引擎不会被这件事卡住。

它说的是"播放会读哪个 profile 的 cookie"，**不是**"你登录着" ——
那条界线在 AS-BUILT-engine.md「先探后播」 量过，别在 UI 文案里把它说宽。

**状态行的 `total=` 是 parts 列表特有的字段，而且它只出现在那一行上。** 它存在的理由是
搜索行的一处不一致：B 站的搜索响应**只给聚合时长**，所以一个 100 P 视频的搜索行写着
`10h:32m:03s`（实测 2026-08-29：那个数字与 `--parts` 的 `total_duration_fmt` **逐字相同**），
而在那一行上按 Enter 放出来的是**第 1 P**，12:07。两个数字都没错，错的是搜索屏上没有任何
东西说它们是两个数字 —— 而这一层修不了：要在搜索行上分辨，得对每条结果多打一次
`/x/web-interface/view`，正是 `bili-search` 最稀缺的那样东西（AS-BUILT-engine.md）。

于是说清它的地方是 `c` 打开的部分列表，它把两个数字放在相隔一行的位置对峙：表头的
`total=` 是集合，下面每一行是它自己那一 P。第 1 P 的时长**不**在表头里再印一遍 ——
那一行就在下面，印了是 chrome 复读。`total=` 同样不印在搜索结果行上：那里没有任何东西
说"这是集合时长"，印了就是把两种数字混进一个字段。parts 列表的来源标签是 `parts=`
（与 `playlist=` / `history=` 同一条规矩）。

**状态行的 `quality=` 在 `auto` 上不印，而这是这个字段唯一值得记的一条。** `f`
（`cycle_quality`）轮换 `PLAY_QUALITY`，走的是 `cycle_mode` 一模一样的形状：纯本地、
不重取、对**下一次** Enter 生效，正在放的那个播放器留着它已经解出来的流。默认档
`auto` 不占格，与 `min=`/`max=` 在 `0s` 上不印是同一条规矩 —— 一个停在默认值上的字段
纯粹是宽度，而从没按过 `f` 的那台机器全都停在 auto 上。它排在 `mode=` 后面是因为它得
**对着 mode 读**：引擎那张表是 (mode, tier) 二维的，`high` 在 video 旁边是 1080p、
在 audio 旁边是一个码率。

这个文件不认识 yt-dlp 串，也不该认识：`f` 选的是一个**规范档位**，翻成 format-sort
是引擎的事（`quality_sort_for_tier`，AS-BUILT-engine.md）。TUI 只是把档位原样交给
`ut-play --quality`，与它交 `-f` 的方式一字不差。没有对应的 `uting` 旗标 —— 一个档位是
设一次的调音，它的入口是配置键、这个键、以及 agent 面上的 `ut-play --quality`。

**单 P 不开视图。** 引擎答 `count: 1` 不是错（AS-BUILT-contract.md 的 `--parts` 一节），
但在 TUI 里开一个单行列表是拿一次按键和一次重绘换一句废话 —— 屏幕上那一行**本来就是**
那唯一的 P。所以 `c` 在那里出的是提示（`分P: 这个视频只有一 P`），回答的正是这个键真正
在问的"这条还有别的吗"。

- **行数由两条边管，不由一个键管。** `→` 越过最后一页追加一批（`more_results`，要一次取数），
  `←` 在第 1 页砍掉一批（`fewer_results`，纯本地截断）。两件事让这条对称成立：
  ① **涨要一次网络往返，缩什么都不要** —— 行已经在 `ALL_ROWS` 里，一个 `head -n` 就够了，
  正是这条不对称让"缩"敢绑在一个裸方向键上；② 从前只有涨没有缩，而涨是被**最被动**的手势
  撑大的（`→` 一直按到底，20 就变成 200），唯一的复原手段是退出会话。
  **`m`/`M` 因此退役**：行数已经归翻页管，再给同一个数字配一个形状不同的手势，
  是给一个事实配第二种拼法 —— `more_results()` 这个**函数**留着，只是唯一的调用方变成了 `→`。
  - **不是 `Shift+←`。** `["*D` 那个 glob 今天就把所有带修饰符的方向键吞成裸 `←`，
    要分开就得在 glob 之前匹配 `[1;2D`，然后**指望终端真的发它** —— iTerm2/Ghostty/kitty 发，
    macOS 自带的 Terminal.app 不发。在一套以"macOS 自带什么就用什么"为地板的东西里，
    一个在自带终端上静默失效的键比没有这个键更糟。而 `←` 在第 1 页今天是个死的 no-op，
    它不挤掉任何东西，还是 `→` 越过末页的**精确镜像**：同一套语法，不用修饰符。
  - **缩不印动作回显。** 状态行的 `results=` 自己会变，那就是反馈；涨之所以要印，
    是因为它接着要等一次网络。**地板是 max(步长, 一屏)**，到了地板就是原地不动 ——
    与这个键从前在第 1 页的 no-op 一模一样。存的是 `RESULT_N`（要了多少）而不是
    `NUM_ENTRIES`（拿到多少）：一次只有 37 条结果的查询不该把下一次查询的起点钉在 37。
- **八个键改的设置会写回用户配置**（`mark_pref` / `flush_prefs`；机制、键表与那三条
  硬约束在 `AS-BUILT-contract.md`「配置面」「写回」，决定在 ARCHITECTURE.md「两个根数据文件」）。TUI 这一侧只有三件事
  值得记在这里：① **置脏点全都在成功路径之后** —— `cycle_engine` / `cycle_sort` 有一个
  取数失败就回滚的窗口，屏幕上是旧值，文件里就必须是旧值；② **写是延后的**，真正落盘发生在
  `nav_tick` 与 `cleanup_on_exit` 这两个现成的地方，所以连按 `t`/`l` 只付**一次**重写，
  而不是每键一次 —— 那个键循环同时还在用 `utf8_complete` 拼一个 UTF-8 字符；
  ③ 因为②，下面那个空闲时钟多了一个条件。
- **一个模式由进入它的那个键退出。** `b` 之于歌单，`h` 之于日志，`c` 之于分P，`i` 之于章节：
  一个键两个方向，不用多学一个键，也不用在一个**要量宽度**的提示块里多占一格 —— 那个键在
  自己的模式开着时**自己换词**（`b back to results`），而不是旁边多出来一个键。删掉第三个视图
  那一条里早就写着同一句话，只是当时没起名字：一个"去了再回来"的键，每多按一次就少值一点。
  **`Tab` 曾经是这条规矩的一个例外**（它开的是一个视图，不是一个行源），而视图塌缩之后
  它连例外都不是了：五个行源，五个自我关闭的键，没有第六种进出方式。
  - **回去走的是暂存的那次搜索，不是重跑那个查询**（`stash_search` / `restore_search`：
    信封、行、标签、引擎集，连同选中行与页码一起收着）。一个存储键的往返因此**零网络**，
    而且回来时屏幕上是他离开时的那些行 —— 重跑一次同样的查询未必给出同样的结果，
    "回去"就会变成一次静默的换页。暂存槽**只有一个**，这也正是 `c` 与 `i` 只在搜索行上
    可用的那条理由（`search_only`，见下）。
  - **Esc 不是这个问题的通用答案，而这是一次测量，不是口味。** `\x1b` 既是 Esc 键，
    又是每一个方向键与功能键的首字节，所以一个**孤立的** Esc 只有等过之后才知道 ——
    而 bash 3.2 没法表达比整整一秒更短的等待（`read -t` 只收整数；实测：孤立 Esc 1s，
    方向键 0s，因为它的 `[` 已经在队列里了）。ncurses 管同一个窗口叫 ESCDELAY，默认正好
    1000 ms —— 也正是每个用户都改成 25 的那个数；vim 与 tmux 落在 10 ms。C 程序用一次
    对着 tty 的 `select()` 就能拿到那个精度，shell 没有这个原语，所以 100 ms 要靠一次外部的
    单字节读 —— 每按一次方向键 fork 一个进程，一笔这个领域并不支付的税。一个要一秒才应答的
    "返回"键读起来就是坏了，所以回去的路是一个普通字节。**这是 shell 目前最锋利的
    那条交互地板** —— 记在这里是因为它是这条路的**已知代价**（`ROADMAP.md` 的 Go 重写 NO 把这类
    代价整体收下了），不是一句抱怨。
  - **例外是那些输入本身就是文本的模式**：实时过滤，以及三个提示（`n`，还有 `a`/`b` 背后的
    名称提示）。在那里，进入的那个键在模式**内部**就是一个普通字符 —— `/` 真的会出现在标题里
    （"beats to relax/study to"）—— 所以它没法同时表示"离开"，Esc 是那里唯一一个不是文本的键。
    它们付那一秒，而且不存在不付的版本。
- **`a` 与 `b` 共用同一段选单，它是滚动区里的一段散文，不是第二个渲染器**（`pick_playlist`）。
  它比"把存储自己的 `--ls` 原样打出来"多两样东西，而那两样就是这两个键能用的全部：一个**序号**，
  于是回答是一次按键而不是一次回忆（一行灰散文加一个与搜索提示**长得一模一样**的 caret，读起来
  是"它没给我看有哪些列表"）；以及一个用 `disp_w` **量出来的**名字列，因为 `--ls` 是按**字节**
  对齐的，而一个 CJK 名字在按字节对齐的列里根本不齐。窄面板先丢日期（<46 列）、再截名字，用的是
  这个文件里所有预算共用的那套 `truncate_disp` + 8 格下限。
  - **两个键的差别只有标题和提示语，由调用方传进来**，别的一概是同一份行为。这也是为什么
    `a` 会走这里：那个"凭记忆打名字"的 caret 在 `a` 上比在 `b` 上更糟 —— 打错一个名字在
    `b` 上是 `not_found`，在 `a` 上不报错，而是**悄悄多出一个播放列表**。
  - **读的是 `--ls -j`，不是那段散文**：选单要把名字当**数据**用（编号，再把其中一个交给
    `--show` 或 `--add`），而存储本来就以那个形状发布它们。这一次取用 `list_playlists`，
    一份，两个键共用 —— 那十行（errfile、rc、两步扒错误前缀）正是 F11/F12 里飘走的那种复制。
  - **空存储是这两个键唯一分岔的地方**，因为同一个 0 对它们意思不同：对 `b` 是死路，就地答掉
    （"还没有播放列表"），而不是去提示一个不可能存在的名字；对 `a` 那恰恰是一个列表开始的
    地方，于是问题换成"新列表叫什么"。
  - **序号在 TUI 里就解析掉**，于是 `ut-playlist` 从头到尾只听得懂名字，`open_playlist` 交出去
    的还是它本来要的东西。序号**压过**同名的数字：屏幕上那个数字才是用户看见的东西，而一个真名
    叫 `7` 的列表照样够得着 —— 用它自己那一行的行号。提示器仍然是 `prompt_name`，也就是 `n`
    与 `a` 用的同一个读取器（UTF-8 组装、退格宽度、取消契约都只有一份）。
- **`d` 是唯一一个破坏性的键，所以它是唯一一个先问的键**（`delete_from_playlist`）。三件事把
  它和别的存储键分开：
  - **它只在歌单视图里存在。** 键条里那条"不能动作的键不许占一格"的规矩（`e` 在单引擎装机上
    遵守的那条）在这里表现为：`d` 只在 `LIST_SOURCE == playlist` 时才画出来，按在别处由
    `playlist_only` 答掉 —— 它是 `search_only` 的镜像。**不是 `stored_rows`**：收听日志也是
    存储，但 `ut-history` 的全部动词是 `--ls --record --clear`，没有按行删除这回事，所以那里
    的 `d` 根本没有可调用的东西。
  - **确认是一个字节，不是一行文本。** `confirm_key` 直接 `read -rsn1`：确认不是文本，让一个
    会组装 UTF-8、会处理退格的读取器去接它，是在回答没人问的问题；只有 `y` 是"是"，别的键
    （含 Esc）都是取消 —— 对一个破坏性动词，默认必须是"否"，提示语里的 `(y/N)` 就是这个意思。
    确认框把**标题**印出来，因为只问"确定吗"是在让人凭记忆回答一件本该读到的事。
  - **交出去的是索引，而索引是从行的身份算出来的，不是 `selected`。** 今天这两个数恰好相等，
    但那是靠**另一个函数**的不变量（`filter_live` 退出时必然 `apply_filter ""`，所以主循环里
    永远看不到过滤子集），而它一旦变了，代价不是少删一行，是**删错一行**。所以
    `focused_index` 用 url **加上它的出现序号**（上方有几行是同一个 url）去查存储：歌单允许同
    一个 url 存两次，那时"第一个匹配"未必是光标所在那行；而两边都是条目顺序，于是视图里的第
    k 次出现就是存储里的第 k 次出现。查不到就是屏幕和存储已经不一致，此时**拒绝**而不是拿一个
    可能指向别人的索引去删。
  - **删完就地重读，光标留在原处**（`reload_playlist`）。重读用的就是 `open_playlist` 本身
    （它取的 stash 对已经属于存储的行是 no-op），所以没有第二份 show+build+load；额外做的只有
    光标 —— 删三首歌否则就是三趟从头往下走。重读失败（包括列表被删空）就回搜索，因为那一条已经
    没了，屏幕上的行是过去的照片；空列表说的还是 `b` 开空列表时的那句话，因为那是同一个事实。

- **播放是异步、非阻塞的，走 `ut-play -d -j --engine`。** 引擎取自搜索信封，绝不留给播放器的
  默认值（AS-BUILT-contract.md「门模型」）。`play_selected` 用一次 `jq` 从那个信封里读出
  `id`/`pid`/**`sock`**，从不自己重建 socket 路径（AS-BUILT-player.md「运行时 IPC」）。
  播放在一个独立的 detached 进程组里启动，于是 `uting` 保有对终端的完全控制。
  用户浏览结果、翻页、发起新搜索（`n`）时音频不中断。在任何一行上按一次 `Enter`，
  干净地停掉上一个播放器并启动新选择，没有延迟。
- **一个视图，五个行源。** 屏上永远是**同一个渲染器**画出来的那一张列表：多行结果、顶部
  Now-Playing 横幅、选中行的 details 段。变的只是那些行**从哪来** —— 搜索、歌单（`b`）、
  收听日志（`h`）、一条视频的分P（`c`）、一条视频的章节（`i`）—— 每一个都由**进入它的那个键**
  退出。`display_menu` 因此不再分派：它开关 DCS 帧保持，然后调 `display_list_menu`。
  - **一条提示不是一次退出。** 行源答不开门的时候（日志是空的、只有一 P、没有章节、取数
    失败），它印一条提示、等一次按键（`store_notice` → `press_any_key`），然后把 **1** 交回
    菜单循环 —— 那是"没开成"，不是"坏了"。可菜单循环跑在 `set -e` 下，所以 `h`/`c`/`i` 那三条
    case 臂必须写成 `open_… || true`，否则 TUI 恰好死在那次**用来撤下提示的按键**上：用户按键
    是为了回去。`Enter` 那条臂为同一个理由早就带着这个守卫（`play_selected` 失败时同形）。
  - **第二个渲染器是被删掉的，不是没做出来。** 曾经有一张全屏的 Now Playing 焦点卡，`Tab` 切进去，
    带两个主语（在播的那条 / 你按 `i` 问的那一条）。它在 100×30 上只填满 27%（30 行里 8 行），
    换来的是**一个状态两个渲染器** —— 而这正是这份文档一直用来否掉 "mini player" 的那条理由。
    删它是把那条理由用在自己身上：**要么把整屏挣回来，要么别占它**。
    `Tab` 因此**空了出来，并且刻意不派新活** —— 一个空着的键比一个硬塞的功能好，
    而"不能动作的键不许占一格"那条既有规矩自己就把它从提示块里请了出去。
  - **纯显示的损失，直说。** 列表布局一格没改（这次改动**不含任何样式工作**），所以卡上那些
    在列表里没有槽位的东西是**丢掉**的，不是搬走的：大标题、**前方队列块**、条目的**简介**、
    以及元信息行里那个 `selected`（引擎挑中的 format）。丢的全是**画面**，**没有一个能按的键**
    跟着走：`+`/`>` 照旧写队列，`f` 照旧轮换档位，`[`/`]`/`9`/`0`/`Space` 照旧。
    - 队列的**位置**留下了，因为它是 `+` 在屏上唯一的回执：状态行在队列长于 1 时印
      `queue=pos/len`（`CURRENT_QUEUE_POS`/`_LEN`）。队列的**尾巴**（`upcoming`）没有留 ——
      读它的只有那个块。
    - 进度条一个字没动：它本来就是**列表那条 rail**（`render_prog_bar`，见下面"列表那条 rail"），
      卡片只是当初也用了它。
  - **`i` 是第五个行源：把章节变成行。** 一次 `<engine>-resolve --info`，按 `engine:url` **单槽**
    缓存（`INFO_CACHE_KEY`/`INFO_CACHE_JSON`，会话内有效、不落盘）；`chapters[]` 经
    `build_chapter_rows` 变成一个 `{items:[…]}` 信封，再交给**歌单那个同一个** `build_playlist_rows`
    走完。`i` 读的是**那一行自己的** engine，与 `Enter`、`c` 同一条规矩。
    - **这个源叫 `chapters`，2026-08-31 之前叫 `versions`。** 源名不是内部名：`stored_rows` 的
      源名**就是**头一行印出来的字段名（`chapters='<标题>'`，与 `playlist='<名字>'`、
      `parts='<标题>'` 同形），所以一个错的源名，错在整个视图唯一一行"告诉你在看什么"的地方。
      `parts`/`history` 读得通是因为它们本来就是对的词；`versions` 不是这个键做的事。
      函数、信封变量与提示块那一格一并改名 —— 一个东西一个名字，不留第二种拼法。
    - **一个章节行是一个区间，rail 就印区间**（`0:00 → 2:30`）。从前它印**起点**一个数，
      而且是在搜索行印"这条有多长"的**同一列、同一种拼法**里 —— 于是屏上那一个数在两张
      除此之外一模一样的列表之间换了意思，还没有任何东西说一声。一个区间读不成一个时长。
      - **区间在 `build_chapter_rows` 里就拼好**，而不是渲染时从相邻行推：实时过滤与翻页会
        重排屏上的行，所以"下一行的起点"不是这一章的终点。它是记录里**第八个**字段
        （`rail`，见下面的行记录），也是唯一一个已经是显示形态的字段 —— 这正是它的用途：
        一行可以自己点名它的 rail，不点名的源留空、照旧走 `short_dur`。
      - **箭头是一列。** 各自右冲会把**终点**对齐、别的什么都不对齐：`5:42 → 8:00` 与
        `8:00 → 11:32` 的箭头差一格，过了一小时差四格 —— 于是全屏唯一一列供眼睛往下扫的东西
        自己在动。所以每条 rail 都建成**同一个宽度**：两个时间各自在一个字段里右对齐，
        字段宽度**按整张表**取最大（不是按页 —— 一列会随翻页重新对齐，那还是同一列毛边，
        只是晚一点才发现，与行号字段按 `NUM_ENTRIES` 定宽同一条理由）。代价是还没到一小时的
        那几页在箭头后面留着给 `1:0x:xx` 的位置；那正是对齐的价钱。
      - **终点取引擎自己的 `end_time`**，没有这个字段时区间半开（`2:30 →`）、`duration` 缺席，
        而不是猜一个：最后一章的长度要拿条目总时长去减，而这个视图不读条目总时长。
      - **`duration` 是这一章的长度**（秒），`duration_fmt` 是同一个数的 wire 拼法。从前这两个
        字段装的是**起点** —— 一条被 `a` 存进歌单的章节，回来会声称自己长 2 分 30 秒，
        因为那是它开始的地方。details 段、`a`、`+` 现在拿到的都是真时长。
    - **它建的是信封而不是行**，因为 `a` 与 `+` 是从 `json` 里切一条出来的（`focused_payload`）：
      一个 json 与自己的行对不上的行源，是一个能放但存不了的列表。
    - **和 `c` 一样只在搜索行上可用**（`search_only`）：暂存槽只有一个，从歌单里再开一层
      要么丢掉回搜索的路、要么需要一个栈，而栈是另一个单元的事 —— 返回栈只有一层，
      上面那条暂存规则就是它的全部。
    - **没有章节就出一条提示、原地不动**，与 `c` 在只有一 P 时的答法同形：一个空列表要花一次
      按键和一次重绘去说一句"没有"。
    - 状态行捡起那次取数付过、而行装不下的两格：`uploaded=` 与 `likes=`。`--info` 的读取也
      **从八个字段减到三个** —— 频道、时长、播放数本来就在按 `i` 的那一行上，而简介没有了去处。
  - **一个章节行是一次调用，不是一条引用 —— 而这一条 2026-08-29 曾被否掉过。** 当时的理由是
    "章节当行会逼着条目记录长出一个起始偏移字段，并让它蔓延进歌单、队列与历史"。
    **0.4.0 之后那条理由失效了**：`start_seconds` 已经是 resolve 信封的字段，两个引擎都从句柄的
    `?t=` 里读它（`AS-BUILT-engine.md`「起播偏移」）。所以行的 url 就是**带 `t=<秒>` 的那个句柄**
    （`chapter_url`，先把已有的 `t=` 剥掉 —— 带两个 `t=` 的句柄从哪一秒开始取决于解析器往哪看），
    记录还是七字段，**一个新字段都不用加**：`Enter` 从那一章起播、`+` 从那一章入队、
    `a` 存下来的也是从那一章起播的一行。偏移**随行走**，所以实时过滤重排了行也不会错位
    （一个平行数组会）。
  - **`Enter` 在章节行上的两个分支，是同一件事。** `play_chapter`：播放器手上已经是**这一条**
    （engine 与去掉 `t=` 的句柄都相等）就走 `ut-play --seek-to <秒>` —— 章节是**已经打开的那个
    文件里的一个偏移**，所以是一次 seek，永远不是一次 re-resolve（这正是这条轴与 `--parts`、
    `--quality` 的分界，AS-BUILT-contract.md「命令规格」）；否则照常 `play_selected`，偏移在 url 里。
  - **仍然没有第三个渲染器，理由没变。** 一个 "mini player" —— 用三行渲染同样那几个事实 ——
    会是一个状态两个渲染器，也就是会漂移的重复。今天这个数是**一个**，而不是两个。

  - **防闪烁的原地渲染，应用里再没有一处 `clear`。**
    1 秒一拍的实时刷新靠 `\033[H`（光标归位）平滑更新时间与进度条，不做整屏抹白、也不闪。
    正因为什么都不抹，**一帧发出的每一行都必须带 `\033[K`** —— 空白的间隔行也不例外。
    一帧的高度会变（提示块按宽度折行、details 块按标题折行、进度条要等 mpv 头一秒的
    `time-pos`），而一个没擦的间隔行会继续显示上一帧画在那一行上的东西。

    一次以 `clear` 开场的重绘 —— 先抹白、再重画，一帧两个可见状态 —— 会让任何按键都把整个
    列表闪一下，而暂停/恢复把这一点暴露得最清楚，因为真正变化的只有横幅里的一个字形。
    DCS 帧同步只在支持它的终端上把"先白后画"藏起来，而在 tmux 下同步默认是关的，
    于是什么也藏不住。`display_list_menu` 的做法是：
    归位光标、边画边擦，以一个 `\033[J` 收尾，而暂停/恢复恰好重画**一行**
    （一行变化、零个 `ED` 序列 —— 用 `tmux pipe-pane` 的流在两个标记之间数 `ED` 量出来的，
    因为 tmux 在 pane 打开时会自己发一个 clear；这是一条**记录下来的测量**，
    不是一条被守着的断言 —— 数 `ED` 是对画面本身做断言，而套件不做那件事）。
    换行源（`b`/`h`/`c`/`i`）同样不 `clear`：帧以 `\033[J` 结束，进来的那一帧盖住出去的那一帧，
    应用里再没有一帧空白。

    这个渲染器有而当初那张卡没有的两个细节：
    - **在结果行上，`\033[K` 放在最前面，不是最后。** 时长轨是用 CHA（`\033[<n>G`）定位的，
      它**跳过**标题与轨之间那些格子而不写它们，所以尾随的擦除会让上一帧更长的标题从那个缝里
      透出来。**先擦、再画**是唯一能盖住"画本身从不触碰的那个洞"的顺序。
    - **过滤输入行的光标用一个 `\033[J` 收尾。** 它一次擦掉那一行的其余部分**以及**下面的每一行，
      并把光标留在下一个键入字符必须落到的位置 —— 前面再加 `\033[K` 是多余的，而移动光标是错的。

    **这没有改变什么：一次按键仍然重算并重写整帧，而这是有意的。** 走掉的是终端*显示*的状态数
    （白，然后画好 → 画好），不是工作量。每个键处理器都以 `continue` 结束，循环顶端调
    `display_menu`，而 `display_menu` 是屏幕唯一的写者 —— 没有脏区跟踪，也没有局部重绘路径。
    在 100x30 的 pty 上实测：一次暂停发出 **2413 字节、耗时 15–24 ms**，
    与真有四行变化时一次下箭头发出的帧逐字节相同。

    重算的代价就是 reflow 的代价。列表几何是**每帧测量**的，不是固定的：`PAGE_SIZE` 是
    `LINES_N` 减去量出来的 chrome，`print_hints` 按宽度打包（1–4 行，行数随 chrome 语言变化），
    而 details 块有多高取决于选中标题折了多少行 —— 所以一帧要读一次 `stty size`、跑一遍提示打包、
    跑**两遍** `print_details`（先量后画），并把每一行过一遍 `truncate_disp`。
    任何状态变化都*可能*挪动那份几何，所以渲染器选择重算，而不是试图知道"什么时候它不会变"。

    暂停是唯一一个**可证明**不会挪动几何的变化 —— 一行之内的一个字形加一个词，
    而那一行的长度省略早就定死了。只重画那一行考虑过并被否决：它需要横幅的**绝对屏幕行号**
    （今天 `chrome_h` 是**边画边累加**的，它不是一张任何东西都能查的行号表）、需要一次 CUP 或
    save/restore 去够到那里，而且横幅的标题省略还是得重算，因为那取决于 `nav_cols`
    以及导航块有没有被丢掉。结果会是**第二条覆盖第一条子集的绘制路径**，副本会漂移，
    而每一次横幅改动都得做两遍。
    每次按键 2.4 KB、约 20 ms，在打字速率下是看不见的，而唯一会自己重复的重绘
    （播放时的时钟、`Starting` 的滴答）跑在 1 Hz。要重新考虑，是等到某一帧真的必须画得比这更快，
    而不是因为字节数看着大。
  - **进度条就是那条活的 rail。** `render_prog_bar pct total` 拿走它可以占用的**整个**格宽：
    调用方传的是 `cols`，也就是分隔 rail 自己的宽度，并像 rail 一样从第 0 列开始打印 ——
    于是条恰好铺在 rail 的足迹上，而不是坐在一个硬编码宽度上。两次改动把它弄成这样，
    都在 2026-08。它是作为一条**横线**画的，不是作为正文：在那之前它吃了 4 格的正文缩进，
    于是左边缘吊在 rail 里面、只有右边缘齐平。而 `[`/`]` 两个端点没有了：括号是一种边界，
    而一条"职责就是恰好与 rail 等宽且没有边界"的线不能有端点。`━` 表示已播、`─` 表示剩余，
    是分隔线自己的笔画家族，于是已播部分读起来像是 rail 在 `●` 播放头后面变粗了 ——
    而 `●` 正是状态行用的同一个字形 —— 而不是一个停在画面上的小部件。那两个括号还占着调用方
    2 格宽度去放标点；如今那 2 格买到的是 2 格分辨率（`width = total`，不是 `total - 2`）。
    渲染出来的串**永远**恰好是那么多格 —— 头部字形是轨道的一部分，`filled` 被钳在 `width-1`；
    而老的固定 42 格的条在 0% 时量出来 46 格、50% 时 44 格、100% 时 47 格，
    于是每次刷新那一行都在抖。`repeat_glyph` 负责生成那些连续段，因为
    `printf 'x%.0s' $(seq 1 0)` 仍然会打印一格（printf 总要把格式串走一遍）。
  - **直播没有位置，所以它不给位置读数。** mpv 报的 `time-pos` 是在**这场广播**的时间轴上，
    而 `duration` 是直播边缘，于是 `percent-pos` 从第一秒起就是 ~99.98%，进度条被钉满 ——
    在一个 24/7 电台上实测：`time-pos=77390 duration=77403 percent-pos=99.98`
    （同龄的一个点播读数是 0.03%）。所以 chrome 改为看那一行自己的 `live_status`
    （原样带在 `R_LIVE` 里；把它变成 `CURRENT_PLAY_DURATION` 上那个 `GL_LIVE` 徽标的是
    `play_selected`），用 `MM:SS · ● LIVE` 取代那对位置读数 —— 那是**这个**听众接上之后的
    墙钟时间，mpv 给不了 —— 并且不画条。`CURRENT_PLAY_IS_LIVE`/`CURRENT_PLAY_STARTED`
    带着这些；两者在停止时都重置。
  - **客户端靠"每轮循环问一次"来得知播放器的死亡。** 一个 detached 播放器拥有自己的生命周期：
    曲终或 mpv 崩掉时没有任何东西回调 `uting`，而 IPC 层对此刻意保持安静
    （`send_mpv_ipc` 吞掉每一个失败，`mpv_get_prop` 在死 socket 上答空），
    于是一个丢掉的播放器杀不死 UI。**安静不等于被注意到** —— 所以 `check_player_alive`
    跑在主循环的顶端，**并且**跑在 `filter_live` 自己那个键循环的顶端（`/` 开着时那个循环
    永远不回主循环），并在播放器一消失就经 `clear_play_state` 清掉整块 `CURRENT_PLAY_*`。
    测试方法是对信封里那个 pid 做 `kill -0`，而那是 **bash 包装进程**的 pid：包装进程阻塞在
    mpv 上，所以"包装进程活着"恰好等于"还在播"，这与播放器自己回收时依据的
    （AS-BUILT-player.md「运行时 IPC」 的进程组存活）是同一个真相，只是从客户端一侧、
    用一个 builtin、零 fork 够到 —— 便宜到 1 秒一拍也付得起。**空**的 pid 意思是"未知"
    而不是"死了"（`play_selected` 只要求 id 与 sock），所以它不动 chrome。
    pid 复用会让它误报，与 ARCHITECTURE.md「风险登记」 为播放器自己的 `group_alive`
    记下的完全一样。这次清除是静默的：那些空状态本身已经说明了，
    而在列表视图里它会落在下一次按键上，因为那次读是阻塞的。
  - **TUI 拥有终端的 echo，而每一个键入字符在成为"一个键"之前先被拼装完整。**
    在 bash 3.2 上 `read -rsn1` 交回的是一个**字节**，所以在过滤或新搜索提示处键入一个 CJK 字符，
    会作为两到三次独立按键到达 —— 过滤什么都匹配不到，提示回显出乱码。
    `utf8_complete` 在任何一个读取器把它称为"键"之前，从它的**首字节**（按表成员关系分类，
    见 ARCHITECTURE.md「可移植性契约」）把这个字符补完，后续字节的读带超时，
    于是一个撕裂的序列卡不死那一秒一拍的刷新。退格于是按**字符**工作而不是按字节：
    `${q%?}` 在 3.2 上本来就能剥掉一整个，但 `\b \b` 的擦除是**一格**而一个 CJK 字形占**两格**，
    所以被删掉的字符用 `disp_w` 量一下、擦掉那么多格。而驱动自己的 echo 整个会话都是关着的 ——
    连同规范模式一起：`stty -echo -icanon min 1 time 0`，并经与光标同一个 trap 恢复到进来时
    `stty -g` 存下的状态：`read -s` 只按**单次读**压制回显，于是两次读之间，
    驱动会把一次突发输入留在队列里的东西回显出来 —— 叠在这个 UI 自己已经画的回显上面。
    ICANON 跟着 echo 一起关，是因为"`-echo` 而 ICANON 还开着"正是 `getpass()` 的 termios 签名，
    而终端会对这一对做出反应（ARCHITECTURE.md「风险登记」与「可移植性契约」）；
    `min 1 time 0` 让一次裸读阻塞在一个字节上，而不是在零字节上空转。
    过滤的兜底分支必须从 `?)`（一个字节，所以永远不是一个完整 CJK 字符）放宽成 `*)`，
    这正是这两处必须同批发的原因 —— 而它止步于方向键分支没有认领的那些转义序列，
    否则 PageUp 会把 `[5~` 打进查询里。
  - **终端尺寸来自 `stty size </dev/tty`，不是 `$(tput cols)`。** 在命令替换里，
    ncurses 可能错过窗口尺寸 ioctl，转而按 terminfo 的默认答 80x24 —— 实测：
    一个 60 列的 pane 报了 80，于是那时的卡片画出 80 宽的 rail，每一行（rail、标题、进度条）都折了。
    `term_size()` 通过这个 UI 本来就要求的那个 TTY 读真正的 ioctl，
    再依次以 `tput`、80x24 兜底。（`ut-play` 的 `viz` 模式用同样的方式给它的滤镜定尺寸 ——
    只是宽度照抄、**高度乘二**，因为 `--vo=tct` 画的是半格：`AS-BUILT-player.md`「终端可视化」。）
  - **chrome 一次运行只说一种语言。** 把标签写成中文字面量、而帮助、错误与字段标签留在英文，
    会让这个工具读起来像同时在说两种语言。`init_ui_strings` 把每一个标签**一次性**解析进全局量
    —— bash 3.2 没有关联数组，而每次绘制查一次表会在每次重绘时 fork 或重新分支 ——
    来源依次是 `YT_LANG=en|zh`、`zh*` 的 locale、再不然英文（这也覆盖 cron/CI，那里 `LANG` 是空的）。
    那只是**起始**语言：`set_ui_lang` 与初始选择被拆开，于是 **`l` 键**可以在任何视图里实时重填
    这张表，且不碰播放。折行的缩进用 `disp_w` 量，不用 `${#var}`："导航:" 是 3 个字符但 5 格。

    **这条规矩如今是穷尽的：任何作为 chrome 画出来的东西，都不是它打印处的一个字面量。**
    它有两轮不是这样：提示行走了表，而播放状态（`Playing`/`Paused`/`Starting`，画了两处：
    当时是列表横幅的标签与卡片的状态）、页眉，以及每一条**瞬时**行（启动提示、`n` 提示、
    `searching…`、`→`/`o` 的动作回显、无匹配文案、过滤横幅、`Press any key…`、`Quitting…`）
    留在一个中文框架里说英文。它们之所以容易被漏掉，恰恰因为它们是瞬时的：它们打进滚动区，
    下一次重绘就抹掉，所以它们从不出现在一张截下来的帧里。三条约束塑造了修法：
    - **表里不能引用 `GL_*`。** `set_ui_lang` 在选项解析期间跑，`init_glyphs` 在它之后跑，
      所以一个标签里带字形会在第一次调用时于 `set -u` 下中止。因此一个字形在**中间**的句子
      是两个条目、在打印处组合（`$S_NO_MATCH $GL_DASH $S_NO_MATCH_KEYS`）——
      把一个字面破折号焙进去会活过 `YT_ASCII=1`，而那恰恰是字形表存在要防的那一件事。
    - **一个**打印点**一个条目，不是一个词一个条目。** `S_SORT_ACT` 刻意重复 `S_SORT`
      的中文值：提示行把键拼成小写、动作标题拼成 Title case，
      这个区别英文有、中文没有。共用一个条目会为了补一个中文的缺口而改掉英文的输出。
      `S_MORE_ACT` 如今没有提示行上的孪生兄弟（`m` 退役后，那个动作由 `→` 承担，
      而两个方向键在提示行上是**一个**条目），所以它是一个只剩标题的条目。
    - **经得起翻译的语序。** `→` 的回显里那个计数短语从 `for 50 results` 改成 `· 50 results`，
      于是**一个**固定的 `printf` 格式服务两种语言（中文要的是"，共 50 条"）；
      一个按语言分的格式串会把版式又塞回表里。这是这一轮对英文输出唯一一次刻意改动。

    **按设计保持英文的**：帮助文本、错误句子（`Play failed:`、`no results`、`search failed`），
    以及页眉/状态行的 `k=v` 字段标签。
  - **chrome 一次运行只说一套主题 —— 而且那是终端的主题，不是我们的。** 默认调色板
    （`minimal`）只用 ANSI 16 的索引码；刻意不用 RGB、也不用 256 色（grep 门禁：
    minimal/mono 路径能发出的转义只有 0/1/2/32/34/36 与 1;3x 的复合），
    于是默认情况下 uting 就用用户终端已有的那套配色渲染 —— One Dark、Catppuccin、
    随便什么 —— 而不是在里面再摁上第二套。社区主题
    （`catppuccin | tokyonight | nord | gruvbox | onedark`）是第二层：它们用 24 位 RGB（38;2）
    发出自己的**标志性强调色**，但**仅当**终端声明了 `COLORTERM=truecolor`；
    否则回退到最近的 ANSI-16 索引，于是在能力有限的终端上 chrome 永远不会变成垃圾。
    每一个主题、社区的也不例外，都要过同一道极简过滤：层级靠灰阶（dim → normal → bold），
    而色相只有**一个**强调色（`C_CYAN`：页眉、选中标记、播放状态，以及那些 rail ——
    静态 rail 与活的进度 rail 是同一个对象的两个状态，所以"暗 rail 压在强调色条上面"
    读起来像两条只是碰巧同宽的无关线条）；社区调色板剩下的部分（它的黄/红/紫/…）刻意丢掉。
    播放状态是最后一处双色相的钉子户 —— 播放用 `C_GREEN`、暂停用 `C_YELLOW` ——
    而在强调色不是绿色的地方，第二个色相读起来就是"这不是这个主题"
    （gruvbox 的橙色 chrome 旁边一个橄榄色状态）。状态点如今取强调色，由**字形**承载状态：
    播放是 `▶`（横幅；`●` 是当年卡片那半边），暂停是 `❚❚`，
    流还在起来时是一个转动的象限 —— 后两者用暗强调色，因为它们都不是稳态。
    于是 `C_GREEN` 与 `C_YELLOW` 都被彻底删掉 —— 一个没人打印的变量是陷阱不是备件，
    而它们按主题的十六进制值从 git 里找得回来。`C_YELLOW` 曾以 `""` 的形式多留了一阵，
    理由是"一次陈旧的读取不花什么钱"；但根本没有读它的地方，那段理由所辩护的东西并不存在，
    于是每一轮审计都要重新论证它一次 —— 留下来的成本是那个论证，不是那四行赋值。
    `C_MARK` 是选中/过滤的复合样式（bold + 强调色）。`YT_THEME` 挑家族
    （`mono` = 零色相，全靠 bold/dim）；`--theme` 压过环境变量，而 **`t` 键**可以在任何视图里
    实时轮换家族 —— 用的就是启动时那次 `set_theme` 重解析，由 `COLORS_ON` 把门，
    于是一个无色会话（`--color never` / NO_COLOR / 非 TTY）保持无色。
    各主题的官方十六进制值（catppuccin mocha/latte 的 mauve 与 green，tokyonight
    night/day 的 blue 与 green，nord 的 frost8/frost1 与 aurora14，gruvbox 的 orange 与 green，
    onedark/one-light 的 blue 与 green）。
  - **亮色与暗色终端都拿到一个读得清的强调色。** `YT_BG=auto` 的链条：显式的
    `YT_BG=light|dark` 赢；否则看 `$COLORFGBG`（rxvt 家族，bg==15）；否则发一次 OSC 11
    背景色查询（`\033]11;?\033\`）；再否则算暗色。对 `minimal`/`mono`，亮色把青换成蓝 ——
    黄色在白底上读不清，所以它不是任何主题的强调色；对社区主题，
    亮色选该主题**自己的**亮色变体（mocha→latte、night→day、polar-night→snow-storm、
    gruvbox light、onedark→one-light）。这个探测是照着 bash 3.2 的形状写的：那里 `read -t`
    只接受**整**秒，所以一次没人答的查询在启动时花掉 1 秒、且只花一次，
    并且在 tmux / `TERM=dumb` 下跳过 —— 它们答不了。回复
    （kitty 的 16 位 `rgb:RRRR/GGGG/BBBB`、xterm 的 8 位 `rgb:RR/GG/BB`，以 BEL 或 ST 结尾）
    是**逐字节**拼起来的（3.2 上没有 `read -d`）；RGB 之和 > 384（中灰）是亮/暗的分界。
  - **协议这一层是有礼貌的。** `--color auto` 尊重 `NO_COLOR`（显式的
    `--color always|never` 仍然赢）。降采样由 `COLORTERM` 把门：一个社区主题只有在终端声明时
    才是 24 位，否则就是 ANSI-16 —— 调色板从不猜。全屏重绘裹在 Kitty 的同步输出对
    （DCS `=1q` / `=2q`）里，于是一次重绘不会闪出半渲染的帧；`YT_SYNC=0|1` 可以覆盖，
    而它在 tmux 下默认关（tmux 会缓冲输出，而且本来就需要 terminal-overrides 透传）。
  - **一条宽度规矩，只在一个地方：`char_w`。** 一个非 ASCII 字符按**两**格算 ——
    对 CJK（East-Asian Wide）是精确的，对其余一切是保守的。**那个默认方向本身就是安全属性**：
    多算会让一行提早一两格打包、永远不会跑出边缘，而少算会溢出。所以 2 是兜底，
    只有那些**量过**不是 2 的字符才进表。
    这条规矩要是在五个地方各写一遍（`disp_w`、`disp_fits`、`truncate_disp`，
    以及 `wrap_print` 的两个循环），改一处就会静默地与另外四处不一致；
    **测量与断行不一致，比统一地多算更糟**，所以它们都调 `char_w`。
  - **量宽从不走完一段没有上界的文本（`disp_fits`）。** `disp_w` 那条 ASCII 快路径是
    **全有全无**的：一段 3621 字符的描述里只要有 54 个 emoji（用来分段的那种），
    整段就掉出快路径、逐字符走一遍。而 `truncate_disp` 开头问的只是一个是非题 ——
    "这段是不是已经放得下 max 格" —— 所以它问的是 `disp_fits` 而不是 `disp_w`：
    `char_w` 的取值域是 `{0,1,2}`、全非负，累计宽度只增不减，越过 `max` 的那一刻答案
    已经不可能反转。**严格等价**，代价从**文本长度**改成**预算**。
    实测（3.2.57，那段真描述，预算 576 格）：整段 0.550s → 有界 0.195s；
    条目卡片"顶部画完、底部还没画"的那段静止从 0.88 秒降到 0.20 秒。
    这条只对**开头那次判定**成立：裁剪循环本来就早退（`((w + CHAR_W > budget)) && break`），
    `wrap_print` 是按**词**量的（每个词各自吃到快路径），所以整条链上再没有第二处没上界的遍历。
  - **chrome 自己的字形按它们真实的一格入表**，这正是让版式**精确**而不只是**安全**的原因。
    这一点之所以站得住，是因为这套套件的字形库存刻意是**非图形**的 —— 文本呈现，
    `ut-play` / `yt-search` / `yt-resolve` / `bili-*` / `uting` 里没有任何 emoji ——
    所以这些字符都不可能背着表带上一个 U+FE0F 变成 2 格的 emoji 字形。
    全部 17 个都量到一格（`tmux display-message -p '#{cursor_x}'`）：

    **这份封闭库存（ARCHITECTURE.md「人机面」）** —— chrome 能画出来的每一个字形，由 `GL_*` 声明加上进度条与分隔线
    生成，其分类是从 UCD 读出来的（`unicodedata.east_asian_width`）而不是猜的。
    扫过每一条非注释行，除了中文标签文本与页眉图标槽的 `🎧` 之外找不到别的非 ASCII 字符，
    所以这份清单是**完整的**，不是**挑选的**。

    **一个刻意的例外：品牌字标（`YT_BRAND=1`）。** 页眉在开启时渲染
    `𝗨 𝗧 𝗜 𝗡 𝗚`（数学无衬线粗体，U+1D5D4 块）。它有意住在封闭库存**之外**：
    UCD 分类是 Neutral（"原则上"一格），但真实终端字体是靠 fallback 字体渲染这个块的、
    宽度随它高兴 —— 所以它**不量**、**不入表**，`char_w` 保守的 2 格默认对它生效
    （多算会让查询省略提早一两格；它永远不会溢出）。它之所以是 opt-in，
    恰恰因为一个没有这个块的字体会显示豆腐块，而只有用户的眼睛判断得了。
    `YT_ASCII=1` 压过 `YT_BRAND` —— 一个画不出 ♫ 的字体也画不出这些。

    **第二个刻意的例外：页眉图标槽（`YT_ICON`）。** 字标左边那一个不是一个字符，而是一个
    **两格的槽**。填进去的要么是 `♫`（U+266B，一格，`CW_NARROW` 里有它，所以 `GL_NOTE`
    自带一个空格把两格补满），要么是 `🎧`（U+1F3A7，East-Asian Wide，`char_w` 默认的 2
    正好就是它的真宽）。两者都量到 2，于是字标不管这次启动抽到哪一个都从同一列开始，
    查询省略也落在同一个字上（44 列实测：两种图标截在完全相同的位置）。
    **不设 `YT_ICON` 时，每次启动掷一次硬币**；`YT_ICON=note|phones` 把它钉死 ——
    一帧要进文档就得两次跑出同一个样子，而硬币不是。`🎧` 是整套件里唯一一个 emoji，
    它有意**不进任何表**：默认的 2 本就是它的真宽，而且它是单码位、不带 U+FE0F，
    入表只会多出一处会和现实分叉的声明。代价是它不吃 `C_CYAN` —— 颜色由字体给，不随主题走；
    这也是它只能是随机一半、而不是唯一图标的原因。`YT_ASCII=1` 下整个槽消失
    （`GL_NOTE=""`），这个开关连同它一起没有意义。

    **Neutral EAW —— 在每个终端里无条件一格（8 个）**

    | 字形 | 码位 | 声明为 | 名称 |
    |---|---|---|---|
    | `↵` | U+21B5 | `GL_ENTER` | Downwards Arrow With Corner Leftwards |
    | `♫` | U+266B | `GL_NOTE`（图标槽的一半，自带空格凑满两格） | Beamed Eighth Notes |
    | `❚` | U+275A | `GL_PAUSE`（画作 `❚❚`） | Heavy Vertical Bar |
    | `❯` | U+276F | `GL_CARET` | Heavy Right-Pointing Angle Quotation Mark Ornament |
    | `▖` | U+2596 | `GL_SPIN` | Quadrant Lower Left |
    | `▗` | U+2597 | `GL_SPIN` | Quadrant Lower Right |
    | `▘` | U+2598 | `GL_SPIN` | Quadrant Upper Left |
    | `▝` | U+259D | `GL_SPIN` | Quadrant Upper Right |

    那四个象限既是取数 spinner，**也是** `Starting` 播放态 —— 一个动画复用两处，
    于是"等一次搜索"与"等一条流"看起来是同一件事 —— 而它们的 EAW 分类正是它们被选中的理由：
    U+2596..U+259F 是 Block Elements 里唯一一座 Neutral 的孤岛，所以这个动画在每个终端、
    每种设置下都是一格。显而易见的替代品都不是：`◐◓◑◒` 与 `▁▃▅▇` 那些条是 Ambiguous，
    于是 `YT_AMBIG_WIDE=1`（或一个把 Ambiguous 当宽的终端）会让帧在一格与两格之间跳。
    它们仍然进 `CW_NARROW`，哪怕没有任何东西去量 spinner 那一行 ——
    这样"每个字形都有已知宽度"这条不变量是**由构造成立**的，而不是取决于字形碰巧打在哪儿。

    **Ambiguous EAW —— 默认一格，只有在 `YT_AMBIG_WIDE=1` 下才是两格（15 个）**

    | 字形 | 码位 | 声明为 | 名称 |
    |---|---|---|---|
    | `·` | U+00B7 | `GL_SEP` | Middle Dot |
    | `—` | U+2014 | `GL_DASH` | Em Dash |
    | `•` | U+2022 | `GL_BULLET` | Bullet |
    | `…` | U+2026 | `GL_ELL` | Horizontal Ellipsis |
    | `←` | U+2190 | `GL_AH` | Leftwards Arrow |
    | `↑` | U+2191 | `GL_AV` | Upwards Arrow |
    | `→` | U+2192 | `GL_AH`、`GL_ARROW` | Rightwards Arrow |
    | `↓` | U+2193 | `GL_AV` | Downwards Arrow |
    | `─` | U+2500 | 进度条轨道、分隔 rail | Box Drawings Light Horizontal |
    | `━` | U+2501 | 进度条填充 | Box Drawings Heavy Horizontal |
    | `▣` | U+25A3 | `GL_CPU`（资源读数的 cpu 标签） | White Square Containing Black Small Square |
    | `▤` | U+25A4 | `GL_RAM`（资源读数的内存标签） | White Square With Horizontal Fill |
    | `▶` | U+25B6 | `GL_PLAY` | Black Right-Pointing Triangle |
    | `○` | U+25CB | `GL_DOT_OFF` | White Circle |
    | `●` | U+25CF | `GL_DOT`、`GL_LIVE`、进度条头 | Black Circle |

    这 15 个 Ambiguous 就是**全部**依赖配置的表面：唯一一批格数会被某个终端设置挪动的字符，
    也是 `YT_AMBIG_WIDE` 唯一碰得到的一批。那 8 个 Neutral 按其分类的定义就是一格，
    任何设置都够不到它们。`♫` U+266B 属于后者而不是与箭头同列 —— 它是 Neutral，
    所以哪怕在 `YT_AMBIG_WIDE` 下也仍是一格。

    因此 TUI 画出来的一切都落在四个桶之一：ASCII（1 格）、这 23 个（入表）、
    CJK 标签文本（2 格，精确），或者未入表因而被保守多算 —— 最后这个桶里
    `🎧` 是个特例：它同样不入表，但默认的 2 对它不是多算而是**精确**。`YT_ASCII=1`
    （非 UTF-8 locale 下自动开）把这 23 个全部换成 ASCII 等价物，
    于是这份库存恰好只有两个状态、没有依赖字体的中间地带 ——
    这也是为什么每一个画出来的字形都必须有一个 `GL_*` 名字。分页圆点是最后一批硬编码字面量
    （行内的 `●` / `○`，而 `○` 连名字都没有）；它们如今走 `GL_DOT` / `GL_DOT_OFF`。

    一格是这里在用的每一个终端的**默认**：Ghostty（`grapheme-width-method = unicode`），
    以及 Terminal.app / iTerm2 / tmux —— 在它们那里"把 ambiguous 宽度当双宽"是一个出厂关闭的
    opt-in。`YT_AMBIG_WIDE=1` 只为 Ambiguous 那一行恢复保守的 2 —— Neutral 字形无论如何都是一格。
    它是一个显式旋钮而不是靠 locale 猜，因为 locale 什么也没说：Ghostty 在 `zh_CN.UTF-8` 下
    仍然把这些渲染成一格。`render_prog_bar` 早就把这个假设焙进去了 —— 它承诺一个恰好 `total`
    格、由 `━ ─ ●` 构成的串，而这只有在每个都是一格时才成立。在 60 列、中文 chrome 下实测到的
    效果：导航行在它的第一行上多放得下一项（`导航: … v 模式  n 搜索` = 量出 58 格，实际 58），
    而不是把它折下去。
  - **这份精确性精确地建立在什么之上。** 那些入表的字形只在**文本呈现**下才是一格：
    同一个终端里量过，`▶` 是 1 格，而 `▶️`（U+25B6 U+FE0F）是 2 格，表却会说它是 1。
    所以 `build_all_rows` 里 `clean` 的承重部分**不是**它那些 emoji 块区间 ——
    而是它剥掉 U+FE00–FE0F 与 U+200D，正是这一点保证了到达测量环节的任何东西都不是 emoji 呈现。
    任何活过 `clean` 的东西都是文本呈现，因此要么入表且正确、要么（未入表）被多算，
    于是"不溢出"这条性质对任意 YouTube 标题都成立，而过滤器不必穷举每一个 emoji 码位。
    如果哪天那个剥离被放宽，表就得先有一条 base+VS16 规则：一个基字符后面跟 U+FE0F 就是 2 格，
    表说什么都不算。**失败方向是不对称的，而这是唯一不安全的那一个** ——
    给 `GL_*` 加一个字形却忘了宽度表，只会回落到 2（多算，安全）；
    把一个没量过的字符塞进宽度表，才是会溢出的那种。
  - **零宽类是被修正过的**，因为在那里"两格"在每个终端里都是错的。在基字符仍按两格算的前提下，
    下面每一条都让整个序列的结果从"仅仅保守"变成**精确** ——
    对照终端自己的光标推进验证过（`tmux display-message -p '#{cursor_x}'`）：

    | 序列 | 旧 | 现在 | 终端实际 |
    |---|---|---|---|
    | `Ocean Coffee ☕️ Vibe`（U+FE0F） | 22 | **20** | 20 |
    | `flag 🇨🇳 cn`（区域指示符） | 12 | **10** | 10 |
    | `👍🏽 ok`（肤色修饰符） | 6 | **5** | 5 |
    | `café latte`（分解式，U+0301） | 12 | **10** | 10 |
    | `family 👨‍👩‍👧 here`（ZWJ） | 22 | 18 | 14 |
    | `● LIVE`（chrome，Ambiguous） | 7 | **6** | 6 |
    | `▶ ❚❚ ❯ ♫ ·`（chrome） | 16 | **10** | 10 |

    零格：U+200D ZWJ、U+FE0E/U+FE0F、肤色 U+1F3FB–U+1F3FF、组合记号
    U+0300–U+036F / U+20D0–U+20F0 / U+FE20–U+FE2F。一格：区域指示符 U+1F1E6–U+1F1FF。
    这些块之外的组合记号（阿拉伯文、天城文、泰文）不在表里，保持多算 —— 保守，绝不短算。
    一个 ZWJ emoji 序列仍然多算；把它折叠起来需要一次真正的字素簇行走，
    在 bash 3.2 里不值那个重量。这些表在启动时**按字节构建**（`cw_range`）而不是写成字面量：
    一行塞满不可见组合记号的源码是读不了的。纯 ASCII 串完全跳过逐字符行走，
    于是这个共享 helper **比**它取代的那个内联判断**更快**（对一行打包好的提示做 300 次测量：
    之前 94 ms，之后 5 ms）。
    累加要写 `n=$((n + CHAR_W))`，绝不写 `((n += CHAR_W))`：一个求值为 0 的算术命令返回退出码 1，
    于是一个开头的零宽字符会在 `set -e` 下中止脚本。
  - **切割落在字素边界上（`cluster_back`）。** 把一个基字符与它的组合记号、连接符或旗帜搭档
    切开，不只是量错，而是画出**错误的**字形：半面旗渲染成一个孤零零的字母方块，
    一个失去依附的 VS16 或 ZWJ 会挂到省略号上。`truncate_disp` 把切点往左走到一个真正的边界为止。
    一个 RI 只有在它前面那个字符也是 RI 时才挡住切点 —— 否则每一个落在旗帜前面的切点
    都会白白吃掉它前面那个字符。`wrap_print` 不需要这段行走：一个零宽字符加 0 格，
    所以它永远绊不倒预算判断、也永远不会开启一行续行 —— 记号免费地留在它的基字符旁边。
  - **所有 chrome 行都按量出来的宽度排版，不是写成固定串。** `disp_w` 量的是**纯文本**
    （一个非 ASCII 格算两格 —— 标签是 CJK，所以它们比字符数暗示的更早用完地方），
    并**通过全局量**返回，因为它在一次重绘里要跑好几遍，而 `$(...)` 会 fork。在它之上：
    `print_hints` 把 `key<TAB>label` 条目（或裸字段）打包进尽可能少的行，带首行/续行前缀，
    条目之间用 `HINT_SEP`（默认两个空格，调用方可覆盖 —— 与 `HINT_KEY_COLOR` 是同一种
    "一次调用一次覆盖"的形状，而且打印器与打包器的适配判断读的是同一个值，
    于是一个打包器不知道的分隔符不可能让某一项提早一格折行）；`truncate_disp` 省略掉那种
    "与固定 chrome 共享一行预算"的变长值。它被用在导航行、空状态文案，
    以及状态行（它的 `min=`/`max=` 如今只在设置过时才出现 —— 在 `0s` 默认值下它们纯占宽）。
    Now-Playing 横幅把固定部分剩下的都给标题，在会把标题挤到 12 格以下之前先丢掉它内联的
    提示块。结果：每一条 chrome 行在 46 列都装得下，而旧的固定串从约 72 列往下就会在条目中间折。
  - **列表视图里**每一行**都是一条物理行，结果行也不例外。** 它们是最后一批未经测量就打印的行，
    也是最要命的那批：在 62 列，一条 `标题 · 时长 · 播放量 · 频道` 的行要占两到三行，
    于是十个条目填满 21 行，把页眉、状态行、Now-Playing 横幅和整个导航块统统顶出屏幕顶端 ——
    版式刚刚打包好的每一条提示，全花在那些随后就滚走的行上。每一行的**标题**被省略到
    "序号字段、两格间隔与时长轨之后剩下的宽度"（`cols - iw - 1 - 2 - rail`）。
    标题行（一条长查询会折）与过滤输入行的文案用同样方式省略，于是整个视图逐行可测量。
  - **一行就是一个标题加一个时长；其余一切都是它下面的一个段。** 一行一条物理行是必要但不充分的：
    把一行拼成 `标题 · 时长 · 播放量 · 频道` **一个**串再从右边省略，
    会让省略**先**吃掉元数据 —— 在 62 列时一行就是一个被砍断的标题、旁边什么也没有，
    整个截断预算都花在那三个最后被切掉的字段上。所以一行带的是标题与一条右贴的时长轨，
    而完整标题、频道、播放量与视频 id 住在分页圆点下面的一个 **details 段**里，只给选中的那一行。
    轨上打的是光秃秃的 `LIVE`，而 details 行打的是 `● LIVE · live now`：
    一个数字列里不想要状态字形，而在一行散文里同一个字形读起来就是一个徽标。两者都用 `short_dur`，
    于是信封里补零的 `06h:10m:58s` 永远上不了屏 —— 一行也不会与它自己的 details 块矛盾，
    因为两者都从**同样的字段**渲染，而不是从对方渲染。
  - **序号是一个定宽列；标记在它前面有自己的槽位。** 把前缀写成每行的字面量 ——
    选中时 `> 1. `、没选中时 `  1. ` —— 会让宽度是 `4 + <位数>`，
    而一页一旦进到两位数，每一个一位数的标题都会比周围的行左移一格。参差不齐，
    而且恰恰是在眼睛**竖着**扫的那一列上。所以序号在一个 `iw - 2` 格的定宽子字段里右对齐
    （最大序号的位数 + 1 给那个点），它前面的标记槽是恒定的 2（`"> "`，未选中行留 `"  "`），
    再用一个空格把字段与标题分开：每一行 `iw + 1` 格前缀，`iw = ${#NUM_ENTRIES} + 3`。
    宽度取自 `NUM_ENTRIES` 而不是取自当前页，所以翻页时它不动；而因为它是一个数，
    `row_w` 与 CHA 的轨跳都读它，而不是各自重新推导前缀。在一位数的页上这个子字段不需要补白，
    于是输出与旧的字面量逐字节相同 —— 这个字段只有在总数跨进两位数时才显形，
    而那恰恰是它存在的那种情形。

    **每一行都保留自己的序号，选中的那行也不例外。** 第一版做法是在选中行上用 `>` 取代序号，
    理由是"你只会为**不在**的那一行敲序号"。那个理由讲的是键盘，而这一列不是：
    把光标所在那行的序号抹掉，等于拿走了唯一一个说明"那是哪一行"的标签，
    而当一个读者想说清自己在哪儿时，找的正是它。已回退；标记改为拿到自己的槽位，
    而那正是定宽子字段腾出来的地方。
  - **提示行用点号连接、且没有括号。** 这个形状是在当年那张焦点卡上定下的，而它活得比卡长：
    带 `[方括号]` 的键名、两空格连接、句子式标签（`back to list`、`pause / resume`）量出来
    110 格；去掉括号（粗键/暗标签的字重差别本来就把两者分开了）、标签各砍成一个词、
    条目之间改用套件自己的 `GL_SEP`（` · `，暗色），量出来 63 格 —— 一直到 63 列都是一行
    （`YT_AMBIG_WIDE=1` 下是 69，那时 `←`/`→`/`·` 各花两格）。再窄就折成两行，与其他每一个
    chrome 块走的是同一条优雅退化的路。中文标签是**重新裁**的，不是机械地截：
    `返回列表选单` → `列表`、`快退 / 快进 5s` → `跳转`，于是中文那行量出来也是 63。
  - **chrome 不带标签，结构由排版承载。** `Title:` / `Channel:` / `Time:` / `Mode:` /
    `Status:`（以及提示块的 `Controls:` 与导航块的 `Navigation:`）都没有了：粗体标题、
    暗色频道、一行由 `GL_SEP` 连接的暗色元信息，状态保留它的颜色。补白也随标签一起消失：
    `%-8s` 在 bash 3.2 上补的是八个**字节**，所以一个 CJK 标签渲染出来的宽度与适配估算
    假设的不同 —— 没有标签，就没有补白可搞错。横幅的标题也不带 `▶`：播放状态住在它前面
    那个带颜色的状态里，一个事实两个指示器是同一种重复的微缩版。
  - **一格提示只画在这个键**能动作**的地方，而"能不能"有两层：装了没有，和**现在这个视图**里
    有没有意义。** 第一层原来就在（`e` 只在装了第二个引擎时画、`a`/`b` 要 `ut-playlist`、
    `h` 要 `ut-history`、`c`/`i` 要引擎有那个动词、`+`/`>` 要真的有播放器在放）。第二层是后补的：
    `o`（重排搜索并重取）、`e`（换源并重取同一个 query）与 `c` 三个键的函数第一行都是
    `search_only`，所以在歌单 / 历史 / 分P 视图里，它们的**全部效果**是一句"只对搜索结果生效"
    的提示 —— 一个量宽度的块，不能拿一格去说"这里不行"。`d` 早就按这条规矩画（只在歌单视图），
    补上的是把同一条规矩铺到那三个键上。
    **一个例外，明写在这里**：从分P 视图**出去**的那一格 `c` 照画不误，不管能力探测此刻怎么说 ——
    人正站在那个视图里，而一个把人带到某处的键，必须在那里写得下自己。
    顺带退掉的是 `e` 那个**按下标 splice 进数组**的写法：下标是位置，它上面每加一个键就得改一次，
    而当时守着那个数字的只有一句注释。整块改成**按顺序构建**，每个条件键待在它自己该在的位置上。
    （审议里点名的第三个死格 `m` 早在 0.3.10 就被 `←/→` 边缘取数换掉了，派发表里根本没有它。）
  - **键位提示块也丢掉了它的标签，并补上了它从没写下来的那些键。** `Navigation:`
    是 chrome 带上最后一个标签，它走的理由与当年卡片的 `Controls:` 一样：**键本身就是内容**，
    而它的邻居 —— 上面的横幅、下面的 rail —— 也都不带标签，所以这个词只是在宣布读者本来就看得见的东西。
    它还在这个视图最宽的那一行上占了 12 格。`S_NAV` 从两张语言表里**删掉**而不是留着定义，
    因为没有任何地方读它。分隔符是 `GL_SEP` —— 而 `HINT_SEP` 要在**测量**调用与**打印**调用两处都设，
    绝不能只设一处：` · ` 是 3 格而默认是 2，跨 11 个间隔就是 11 格，足以把这个块从一行推成两行。
    而一次**少算** chrome 的测量，恰恰就是页眉被顶出屏幕的原因。
    还有三个键**在这个唯一以"写下键位"为职责的视图里缺席**：`9/0` 音量、`Space` 暂停、
    `[ ]` seek —— 它们都由菜单循环那个通用分支处理，所以在这里一直是能用的 ——
    横幅的窄终端兜底记着音量与暂停，`uting --help` 的键表与
    ARCHITECTURE.md「支持的工作流」 也都记着，正是这一点让它们的缺席是一个**缺口**而不是一个决定。
    它们聚在末尾、挨着 `s`，因为在一个其余都在讲移动与搜索的清单里，它们是播放键。
    seek 键印成 `[ ]` 而**不是** `[/]`：`/` 在这一行里是"或"的分隔符（`9/0`、`↑/↓`），
    但这两个键**本身就是**方括号，所以一个被它们裹住的斜杠读起来像"一个被括起来的 `/`"，
    并与三项之前那个真正的 `/ 过滤` 撞车。一个空格能说出"两个键"，
    而不必花掉一个在这行里已经另有含义的字符。`S_SEEK5` 更名为 `S_SEEK`：
    它的值本来就是那个光秃秃的词，而当时它同时服务卡片的 ±5s 箭头与列表的 ±10s 方括号，
    所以旧名字唯一做到的事就是宣称一个步长（卡片走后只剩方括号，名字仍然对）。
    仍然**刻意**不写进这个块里的：`j`/`k`
    （`↓`/`↑` 的别名 —— 会按它们的人本来就带着这个手势，而同一个块开头几格就印着那两个箭头，
    再给一格是给一个已经印出来的键配第二种拼法）与 `Esc`（在这个视图里是 no-op）。
    `p`/`P` 与 `Tab` 都不在这个清单里了：前者不是"不写进文档"，是**退役**了（见下一条），
    后者是它开的那个视图没有了。
  - **`p`/`P` 退役，`j`/`k` 补上。** `p` 从前是 `Tab` 的一个别名（那时 `Tab` 还
    切视图），
    两条理由各自就够：mpv、ncmpcpp、cmus 三家的 `p` 全是**暂停**，所以一个播放器用户按它，
    拿到的是换屏；而它在任何提示块里都没出现过，屏幕上没有任何东西能纠正他。TUI 键位不属于
    冻结面（ARCHITECTURE.md「冻结面」 冻的是 CLI），退一个键零成本，还把一个字母还给了一个只有
    26 位（大小写同绑）的键空间。补进来的 `j`/`k` 是现代 TUI 的桌面赌注
    （lazygit / k9s / yazi / gh-dash / spotify-player 全数支持），此处空闲、零反义，
    而且**只取这一对，不取 hjkl 全套**：`h` 已经是历史（`b`/`h`/`c` 这个行源键族的内聚更
    值钱），`g`/`G` 被大小写同绑封死，半套 vim 比没有更糟。
    - **它们骑在 `↑`/`↓` 自己的 case 臂上**，不新开两条：一条别名要是自己一条臂，就是把
      翻页那段算术抄了第二份，而这个文件里每一块重复都是为了消掉这种漂移才重写的。
    - **只在列表视图，而 `filter_live` 刻意不接它们**：`/` 开着时 j 和 k 是用户正在打的字，
      一个会吃掉字母的导航键是不能用的。卡内方向键另有职责（章节游标），
      所以 j/k 在卡上落到 `*)` 的 no-op。
  - **提示块有两档，`?` 是那道门。** `core`（出厂档）只印这个视图**自己的活**：
    移动、对行的动作、回程、`q`，外加 `?` 自己；`full` 是它今天有的每一个键。
    **两档而不是一个开关**：core 在 100 列上是**一行**，把这一行也省掉，换来的是全部
    可发现性；而矮终端上既有的 `nav_ok` 闸本来就会自动降级到横幅尾巴上的迷你提示 ——
    自动降级是 reflow 的活，不是一个要用户去选的档。三态循环 `core→full→hidden` 因此被否。
    - **实现是逐格把门，不是先建一个 core 数组再往上追加。** `keys_full` 是一个**状态函数**
      （`[[ "$KEYS_TIER" == "full" ]]`，不 fork），每个只属于 full 的格子在**它自己该在的
      位置**上带一句 `keys_full &&` —— 于是 full 档打印出来的顺序与它一直以来的顺序逐字节
      相同。这正是上一条里"按顺序构建、不按下标 splice"那条规矩往前走了一步。
    - **回程是 core，进门是 full —— 这是这次分档里唯一不是"本职 vs 其余"的地方。**
      一个换过词的存储键（`b back to results`、`h`、`c`）是人**此刻站着的那个房间**唯一的
      出口，core 要是把它藏了，人就被留在里面、屏幕上没有一条印出来的出路；而同一个键
      **打开**那个房间时，它只是一个可以去的地方，那正是 full 的用途。
    - **`?` 两档都印，且永远是块里最后一格。** 它是整块里唯一一个既不关行、也不关播放器的
      格子，一个不带它的 core 就是一个没印出自己出路的块。（视图塌缩之前这里还有一条：
      卡片的 core 不等于列表的 core，因为那张卡自己的活就是播放器。只剩一个块之后，
      分档只按一条规矩走 —— 这个视图自己的活是 core，其余是 full。）
    - **`？`（全角）与 `?` 同绑。** 这是一个双语 TUI，zh 输入法下 shift-/ 出的是全角问号，
      `utf8_complete` 本来就会把它拼成一个键，所以这是多一个 case 模式，不是第二条代码路径。
      case 模式里那个 `?` **必须带引号**：裸 `?` 是"任意单字符"的 glob，会把它下面每一个键吞掉。
    - **它是第八个写回键**（`UT_KEYS=core|full`，机制见 `AS-BUILT-contract.md`「配置面」「写回」）：
      一个每次开会话都要重按的偏好不是偏好。也因此它在出厂 `config` 里有一个值，
      而一个拼错的值**当场就死**，与 `UT_PLAY_QUALITY` 走同一道闸。
    - **它藏的是提示，不是键。** core 档下 `i`、`a`、`b`、`h`、`c`、`v`、`f`、`o`、`e`、
      `l`、`t`、`9`/`0`、`Space`、`s`、`[`/`]`、`+`、`>` 全部照按不误 —— 派发表一格都没动。
    - **`t` 曾经一档都不印，那是漂移不是分档（2026-08-31 补上）。** 它在 `usage()` 与 README
      的键表里一直都在，唯独这个块里没有 —— 而这个块是用户唯一一个"读一个词就知道这个键干嘛"
      的地方。它按块自己那条规矩带门：`COLORS_ON` 关着时 `cycle_theme` 直接返回，
      与单引擎装机上的 `e`、没装 `ut-playlist` 时的 `a`/`b` 同形。
    - **`i` 那一格印的是这个键做的事（`章节`/`chapters`），不是行源的内部名。**
      `versions` 是源名，也是头一行那个字段名（`versions='<标题>'`，`contract.sh` 与四份文档
      都引它），两者都没动；块里从前印的是后者，而"版本"不是这个键做的事。
  - **横幅的尾巴是一个位置，不是一个时长。** 单独打印曲目长度（`▶ Playing: … · 3:34`）
    只是把它下面三行那一行上已经有的数字再说一遍；所以它打印 `1:12 / 3:34`，
    与它下面那条活 rail 画的是同一对，于是读数与条不可能互相矛盾。
    它不额外花任何 IPC：`PT_CUR` 与 `PT_TOTAL` 就是那个共享时钟最后留下的值，最多一秒旧，
    而这正是这一行绘制的分辨率。`PT_CUR` 为空意味着还没有任何读数落地 ——
    按下 Enter 之后的第一帧、第一次滴答之前 —— 那时回退成单独显示时长，而不是打印一个光秃秃的 `/`；
    `PT_TOTAL` 以同样方式回退，而因为 `fetch_play_times` 用那一行自己的 `short_dur` 给它播种、
    只有在 mpv 答话之后才用 `fmt_sec` 换掉它，这个读数在播放开始一秒后不会改变**形状**。
    直播保留它自己的形态（`12:34 · LIVE`，没有斜杠）：mpv 的钟描述的是那场广播，
    不是这一次收听，所以没有可以拿来做分母的总长。**这件事也暴露了 `clear_play_state` 不完整。**
    它为 rail 重置了 `PT_PCT`，却把 `PT_CUR` 与 `PT_TOTAL` 留着，
    而 `play_selected` 是在启动下一首**之前**经 `stop_current_playback` 够到它的 ——
    于是横幅会一直显示**上一首**的已播时间，直到第一次滴答把它覆盖掉。
    如今三个一起清，而"空"也恰好就是兜底所读的那个"还没有读数"的信号。
  - **横幅带一个播放器足迹字段（`▣ N% ▤ NM`，UT_RESOURCE）。**
    标签是 `GL_CPU`/`GL_RAM`（▣ U+25A3 / ▤ U+25A4，Ambiguous，入 `CW_AMBIG` 表；
    `YT_ASCII=1` 下回退成 `cpu`/`ram` 文字）。
    读的是同一对缓存（`RES_CPU`/`RES_MEM`，`fetch_play_res` 在共享时钟上每
    UT_RESOURCE_TICKS 拍采一次），
    渲染也不为它花任何 fork。口径、读法与两个键的语义在 `AS-BUILT-contract.md`「配置面」
    （一个事实一个地方）。丢弃顺序里它排在键尾之后、位置读数之前 ——
    足迹说的是播放器的开销，不是曲目。
    与 PT_ 三元组一起在 `clear_play_state` 清空，计数器同时归零，
    于是下一个播放器的第一拍就采样，而不是接着上一个播放器的步幅走。
  - **时长轨是用绝对列跳定位的，不是算出来的补白。** 靠补白右对齐会发出 `room - DISP_W`
    个空格，那会把这一列放在**我们的测量**说的地方 —— 而宽度规矩是**按设计多算**的。
    一个由数学粗体字母组成的标题（`𝗖𝗛𝗜𝗟𝗟`：量出 2 格、画出 1 格）会把它的时长停在
    比上一行左约 10 列的地方：参差不齐，而且是在那个唯一因"要被扫视"而存在的列上。
    `\033[<n>G`（ECMA-48 CHA）把光标移到第 *n* 列，不管它之前打印过什么，
    于是即使某个标题量错了，轨在每一行也落在同一格上。列是 1 起的，
    所以一个 `rail_w` 格的右贴字段从 `cols - rail_w + 1` 开始。标题**仍然**被截断到给轨留出位置
    ——这是**由构造保证**的；列跳修的是测量漂移，它不给溢出发许可证 ——
    而在"某个标题渲染得比量出来更**宽**"这种理论情形下，CHA 会往回移动、干净地覆盖掉标题的尾巴，
    而不是把轨推到折行，这正是我们想要的失败方向。它是一次光标移动而不是文本：
    它从不进 `disp_w`，也不打扰 `\033[K` 的处理。
  - **details 段里唯一一件行上没有的事，是简介。** 这个块从前印的是：整条标题（只有在行被截断时
    才有新东西）、`频道 · 时长 · 播放数 · id` —— 时长是 rail 的重复，id 是给人复制的，章节行上更
    是一件新事都没有（`1:47 · CLeZyIID9Bo&t=0`，连 id 都被 `t=` 拼坏了）。原因不在这个块：
    搜索信封里当时就只有这些字段。**两个引擎的搜索响应里本来都带着 `description`，两边都把它
    扔了** —— yt 的 flat 搜索给的是站方自己截断的那段摘要，bili 的搜索接口给的是简介本身 ——
    所以它现在是信封的一个字段（`AS-BUILT-contract.md`「数据契约」），不多花一次请求。块里最多两行，
    **截两次**：先按两行能装的宽度 `truncate_disp`（省略号从这里来，因为折行没有办法说"还有"），
    再由 `WRAP_MAX` 兜底，因为按词折行可能把一行花在更少的字上。
    - **`WRAP_MAX` 住在 `wrap_emit` 那一个出口上**，理由与 `WRAP_LINES` 一样：一个提前停止
      喂数据的调用方就是第二个折行器，可以和这一个在"行落在哪"上产生分歧。标题**刻意不设**
      上限 —— "看到完整标题"正是这个块存在的理由。
    - **章节行的那一行改成说这一章是什么**：`章节 7/53 · 1:47 · CLeZyIID9Bo` —— 位置（行号是
      **过滤后**的序号，章节号是条目的，两者在过滤时不同，所以 `n` 跟着行走）、真时长、
      以及**剥掉 `t=` 的** id。位置只在 `chapters` 与 `parts` 两个源上印，按**视图**把门而不是
      按字段：一个将来长出 `n` 的仓库不该借走这个词。
  - **details 段是变高的 chrome，且在行被画出来之前就测量。** 它存在的理由是找回**完整**标题
    —— 那是一行永远无法完整展示的那一个字段 —— 所以它是**折行**而不是省略，并占用它需要的高度：
    rail + 标题折出来的若干行 + 一行元数据。这让它成为"高度取决于**选择**"的 chrome，
    而在行之后才测量的 chrome，花掉的是页眉而不是一行。所以 `print_details` 遵守
    `DETAIL_MEASURE`，方式与 `print_hints` 遵守 `HINT_MEASURE` 一模一样，
    只报 `DETAIL_LINES` 而不画（这需要给 `wrap_print` 加一个 `WRAP_MEASURE` 模式，
    并通过唯一的 `wrap_emit` 汇流，于是计数器不可能与打印器漂移）。让它不循环的是**顺序**：
    先钳住 `selected`（不需要页面几何）→ 为它测量这个块 → 推出 `PAGE_SIZE` →
    再从 `selected` 推出 `page`。因为页跟着选择走，这个块描述的那一行永远在屏幕上，
    所以页永远不可能把选择从测量脚下抽走 —— 没有需要跨多帧才能收敛的东西。
    因此当选择跨过"一行标题"与"三行标题"时 `PAGE_SIZE` 会变化一行；那是"不给标题设上限"
    的既定代价，而 reflow 本来每次重绘都重算它。在一个矮到两者不能兼得的终端上，
    块让位、行留下 —— 与导航提示做的是同一笔交易。
  - **每行七个原始字段，用 US 分隔 —— 永远不是渲染好的串，也永远不是 tab。**
    details 段每行都需要频道、播放量、直播态与一个 id，所以一行不再是一个显示串。
    第七个字段是这一行自己的 `engine`，是在播放列表成为第二个行源时加的
    （AS-BUILT-player.md「持久状态层」）：一个存下来的清单可以混源，所以"哪个引擎播这一行"
    是**行**的属性，不是会话的属性。**第八个是 `rail`** —— 这一行自己点名的那一格 rail，
    已经是显示形态；只有章节表写它（一个区间，不是一个长度），别的源留空、照旧由渲染器
    对 `duration_fmt` 走 `short_dur`。同一条理由：那一格是**行**的属性 —— 从相邻行去推，
    实时过滤一重排就错。字段数是承重的：`read` 会把剩下的一切都给最后一个变量，
    所以每一处读记录的地方（`load_rows`、`apply_filter`）都必须数得一样多。`IFS=$'\t' read` 会**折叠连续的 tab**
    （tab 是 IFS 的*空白*字符），于是一个空字段会静默地把它后面每一个字段都挪位 ——
    而一条直播行的 `duration_fmt` **就是**空的，一个原型正是这么把频道名读成了播放量。
    ASCII 的 US（0x1f）不是 IFS 空白，所以空字段活得下来；`clean`/`oneline` 把两个自由文本字段
    里的空白折叠掉，于是没有哪个字段能包含换行、把一条记录劈成两条。视频 id 是从 url 推出来的，
    不作为独立字段携带。`play_selected` 直接读那些数组，也就不必"按 ` · ` 切开、
    重新解析那个拼好的显示串" —— 一个标题里含有那个分隔符就会切错。
    同样的 tab 陷阱也在 `ut-play -d -j` 的信封解析里（`id`/`pid`/`sock`，
    全都默认 `""`、用 `@tsv` 连接：一个不报 pid 的播放器会把它的 socket 路径放进 `pid`，
    于是守卫拒掉一次其实已经启动的播放）；它现在也读 US。
  - **没有播放量不等于播放量为零。** 当播放量未公开时（每一条直播行、部分投稿），
    信封报的是 `view_count: null`。`// 0` 会把它变成 "0 views"，也就是陈述一个我们并不拥有的数字；
    如今这个字段发成空，details 行把那一段整个省掉。
  - **一页能放多少行是量出来的，不是猜的（reflow）。** `PAGE_CAP = LINES_N - 8` 把 chrome
    硬编码成 8 行，而 chrome 是**由构造**变高的：`print_hints` 按终端宽度打包，
    所以状态块与导航块随宽度与 chrome 语言占 1–4 行。那个常数只有在英文、≳72 列时才对。
    在 tmux 里用真脚本量过：40×20 时 chrome 是 11 行，于是十条一行的行加页脚在一个 20 行的终端里
    是 21 行，把页眉顶出去 —— 与"一行一条行"当初要终结的是同一种失败，只是从另一侧到来。
    50×14 与 62×12 以同样方式坏掉。`display_list_menu` 如今**边打印边数** chrome
    （`print_hints` 报 `HINT_LINES`），再从剩下的推出 `PAGE_SIZE`。
    再重算 `NUM_PAGES`、把页钳住 —— **每一次重绘都做**，于是一次 resize 或一次 `l`
    语言切换会重新分页而不是溢出 —— 一个只在启动时算一次、之后不复查的 `PAGE_SIZE` 会溢出。
    分页圆点那一行只有在**多于一页**时才计费，而且是先对着"没有圆点时的尺寸"检查的，
    于是这次预留不可能循环；另有一行留给光标的停靠行，因为填满最后一行并发出它的换行
    会把屏幕整体上滚一行、于是又赔上页眉。details 段以同样方式计费，来自它自己那次测量，
    顺序如上。
    提示块自己的适配判断也必须预留那一行分页行：块之后的行是空行、一条结果行、
    行后的空行、光标停靠行，**以及**只要列表会分页就会有的页码指示 —— 这个判断只在矮终端上咬人，
    而在矮终端上"多于一个条目"总是意味着"多于一页"。不带它量过（发布版本亦然）：
    一个 62×10 的终端保留了这个块、打印 7 行 chrome、一条行、一个空行和 `page 1/17`，
    把十一行塞进十行 —— 页眉出顶，而这正是 reflow 存在要防的那次失败。
  - **当预算付不起一行时，是页脚把行数还回来。** reflow 里其他每一个块都能丢掉自己 ——
    导航提示会，details 段会。行不能：一个没有行的列表不是列表，所以 `psize` 有一个硬地板 1。
    那个地板会赢过一个为零的预算，于是帧高出一行、把页眉顶出去 ——
    正是 reflow 存在要防的那次失败，只是从下面到来。在 62×12、`/` 打开时量过：
    chrome 8 + 间隔 1 + 过滤提示 1 + 光标行 1 + 圆点 1 + 一行 = 一个 12 行 pane 里的 13 行，
    标题行就没了。所以页脚不是一个数：
    间隔、过滤的说明行、光标行与分页行**分开计费**，而当预算盖不住列表欠下的那些行时，
    它们按价值顺序被回收 —— 间隔什么也不承载，过滤提示教的那个模式它下面的光标行已经在演示，
    分页行是真实状态所以最后走，而光标行永远不丢，因为它回显用户正在敲的东西。
    在 62×12 上这恰好买回需要的那两行：页眉、一条行、圆点与光标行全都活下来。
    只有当再没有什么可丢时地板才溢出，而在那里溢出是诚实的 ——
    那个终端没有任何一种排法能同时显示页眉、一条行与一个光标行。
    回收循环里那个"列表欠不欠一行圆点"的判断用的是 `NUM_ENTRIES > 1`，
    而不是随后给圆点计费时那个 `> psize` 的判断：这个循环只在 `psize` 落到 1 的区间里跑，
    而在那里两者一致。它不是关于页脚的第二种意见，它是同一种意见、只是早到还来得及花出去。
  - **跨一次重新分页时，锚是**选择**，不是页码。** 用户看的是**一行**。从 `selected` 推出 `page`
    能让那一行留在屏幕上；把选择钳进旧的页码则会把它瞬移 —— 实测：把 24 行 resize 到 12 行，
    每页从 10 条掉到 2 条，选择从第 15 行弹回第 4 行。
  - **矮到放不下提示块的终端，拿到的是它的行。** `HINT_MEASURE=1` 跑 `print_hints`
    完全相同的打包并报出高度而不绘制，于是列表视图可以在真正花掉这些空间之前先问
    "它会有多高？"。低于约 12 行时，导航块是一个 10 行屏幕里的 4 行、无论怎么重新分页都会把页眉顶掉，
    于是它走、结果留下 —— 与 Now-Playing 横幅对它内联提示做的是同一笔交易，
    而横幅的窄终端兜底会把播放键接过去。在 40×10 与 62×8 验证过。低于 40 列的终端按设计仍不在范围内
    （`layout_cols` 的地板）；在 35 列时提示块会如文档所述在条目中间折行。
  - **`truncate_disp` 绝不超过给它的 max。** 把剩余预算往上钳到 1，会打破这个函数唯一的承诺：
    在 `max=1` 时它发出了一个字符**加**省略号，两格。当预算装不下那个记号时，记号就得走。
    今天没有任何调用方会走到那儿（都钳在 >= 8）—— 它是那条契约上的守卫。
  - **一个钳、一次取数、一条 rail。** `layout_cols` 是唯一的宽度钳（地板 40，无上限：
    列表把全部宽度用于它的行）。那个**可选上限**曾经是参数，因为播放器卡片传 80、
    免得它们的 rail 在超宽窗口里拉满 —— 卡片走了，参数跟着走：一个视图一个宽度，
    而一个没人传的参数是一个调用方并没有做出的承诺。`fetch_play_times` 是 `PT_CUR` / `PT_TOTAL` / `PT_PCT` 背后唯一的
    `time-pos` / `duration` / `percent-pos` 取数，也是 `CURRENT_PLAY_PAUSED` 背后唯一的
    `pause` 读取，直播特例也包含在内：同样的三条 `nc | jq` 管道在两个播放器视图里各内联一遍
    会漂移，而直播路径取 mpv 的钟只是为了把它丢掉（它描述的是那场广播，不是这次收听）。
    直播路径只问 `pause`、别的什么都不问 —— 一条连接一个属性 ——
    因为暂停 chrome 恰恰是那条路径**免费搞错**的东西：任何别的东西在驱动这个 socket
    （`ut-play`、某个 agent 自己的 `nc`、第二个 TUI）都会让横幅断言一个播放器已经离开的状态。
    `toggle_pause` 也不再猜：它调 `ut-play --pause`/`--resume` 并从信封里取 `paused`，
    于是横幅在按键那一刻是从一个**读数**重绘的。那次盲翻只作为"一次什么都没答上来的调用"
    的兜底留存，而滴答的读取仍会纠正它。**先乐观，后真相。** 分隔 rail 由 `repeat_glyph`
    构建并按 `(宽度, 字形模式)` 缓存，而不是 `printf '─%.0s' $(seq 1 "$cols")` ——
    那是一次 fork，而且恰恰是 `repeat_glyph` 存在要取代的那个写法，还要跑两遍，
    好让 ASCII 模式下把 Unicode 那条丢掉。`repeat_glyph` 与 `render_prog_bar` 如今像宽度层其余部分
    一样**通过全局量返回**（`GLYPH_RUN`、`PROG_BAR`），于是一次重绘不为它们花子 shell。
- **进程清理保证。** 一个 `EXIT INT TERM HUP` trap 确保 `uting` 会话期间生出的任何后台播放器
  在退出（`q`）时被自动、干净地停掉。
- **过滤是一次对已取行的、纯 bash 的实时收窄** —— 不走网络、不重新取数、不用外部工具
  （这正是 ARCHITECTURE.md「人机面」 得以成立的原因）。`/` 进入过滤模式；**每一次击键**都在 `ALL_ROWS` 上重跑
  `apply_filter` 并重绘，于是列表**边打边窄**（本地列表收窄的最佳实践 —— fzf / 命令面板那一派，
  而不是回车才应用）。`↑↓←→` 在过滤后的集合内移动（共享的 `move_selection`），
  `Enter` 播放高亮的那条匹配，`Esc` 清掉过滤并退出。
  **两条边在过滤开着时不响** —— `move_selection` 里那个 `FILTER_MODE == 0` 的判断：
  过滤给出的是**匹配**的一页，跑到它的尽头不是"再来一批行"的请求。这一条是量出来的，
  不是想出来的：`more_results` 里那句"这里不可能有过滤开着（filter_live 自己占着键循环）"
  曾经是一句**断言**而不是事实 —— `filter_live` 的方向键分支调的就是同一个
  `move_selection`，于是 `/` 之后打 `zzz`（零匹配）再按 `→`，会真的多取 20 行、并把过滤
  丢掉（2026-08-29 实测的红）。现在判据由调用点强制，回归检查在 `contract.sh` 的 TUI 段。
  输入行坐在屏幕**底部**（fzf 风格，列表下方），
  渲染时不带尾随换行，于是**真正的终端光标**就是那个插入符 —— 没有假方块。
  选中行由一个 `> ` 插入符标记（ASCII，不怕字体），不是反显条。匹配语义是社区标准：
  大小写不敏感（`shopt -s nocasematch`，限定作用域）、空格分隔的 **AND** 词元、空查询恢复全部。
  词元在 glob 里被引号包住（`*"$tok"*`），于是用户输入的 `*`/`[`/`?` 按字面匹配 —— 没有注入。
  检索串是**每行每次击键现合成**的，而不是作为第八个字段存下来：行本来就有那些零件，
  这个串永远不会被打印，而一个存下来的键会多出一样需要与渲染器保持同步的东西。
  它含标题、频道、播放量与**两种**时长形态 —— 信封的 `11h:53m:45s`（与过滤器一直以来匹配的东西
  对齐），以及 `short_dur` 的 `11:53:45`（因为那才是轨上显示的形态，
  而一个匹配不了屏幕上那个东西的过滤器，看起来就是坏的）。它还含直播行的字面词 `LIVE`，
  正是这一点让"敲 live"在今天仍然有效 —— 如今已经没有哪一行携带一个渲染好的 `● LIVE` 串可供匹配。
  匹配到的行被原样重新发出，于是 `ALL_ROWS` 始终是唯一来源，一次过滤永远不可能把一行弄劣化。
  `n`（新搜索）保持"回车提交" —— 它要走网络 —— 所以两个提示**刻意**分道扬镳
  （页内过滤是实时的；一次远程搜索是要提交的）。
- **chrome：分页与光标。** 分页圆点（`●○○`，当前的那个填实）**只在多于一页时**渲染 ——
  孤零零一个点什么也没说 —— 并在 ASCII 模式下、或超过一个可读的点数上限时回退为数字 `page X/Y`。
  菜单绘制期间终端光标是隐藏的（于是不会有一个游离方块停在页脚下面），
  只在底部过滤输入、键入式提示与播放时显示；一个 `trap … EXIT` 在退出 / 出错 / Ctrl-C 时把它恢复。
- **取数 spinner。** 一次搜索是 TUI 唯一无物可画的时刻 —— 在启动时它更是一个空白终端上唯一的东西
  —— 而一条不动的 `searching "lofi"…` 读起来像卡死了，这就是为什么这一行如今以一个转动的象限结尾
  （`▘▝▗▖`，`YT_ASCII=1` 下是 `|/-\`）。三个值得留住的决定：(1) 它夹的是 `fetch_json`
  而不是它的调用方，于是启动取数、`n`、`→` 与 `o` 全都从**一个**实现里得到动画，
  第五个调用方也会自动拥有它；(2) 跑在后台子 shell 里的是**动画**，不是搜索 ——
  把搜索后台化需要一个 rc 文件和一个完成标记，因为 `kill -0` 对一个未被回收的子进程仍然成功、
  于是轮询永远不结束，而且 `fetch_json` 那三个不同的返回码还得靠文件偷渡回来；
  (3) 计时器是 `sleep 0.12`，因为 bash 3.2 没有别的 —— 那里 `read -t` 会把小数超时截断
  （实测：`-t 0.2` 在一个 5 秒的管道上一直坐到底），而 1 秒一帧不算动画。
  每一帧打印自己的字形再退格盖回去，于是这一行永远不变长；`spin_stop` 擦掉最后一帧并收尾这一行，
  正是这一点让 `report_fetch_failure` 的句子落在干净的一行上。echo 在 `spin_start` 处关掉，
  并且**刻意不恢复** —— 否则一个在取数中途按下的键会落进 spinner 那一行里，
  而每一个调用方都正走向菜单循环，那里本来就是关着 echo 跑的。
- **一个时钟。** 按视图授予 `read_nav_input` 的 `-t 1`（当年是卡片永远有、
  列表只在 `CURRENT_PLAY_LOADING` 时有）会让列表一个活元素都不能有，
  而同一个超时授予两次就是两个改节拍的地方，它们会漂移。条件只有一处，
  而且它不问是哪个视图在上面：它问的是**有没有东西在等这个时钟** ——
  屏幕上有东西能在不按键的情况下变化（那就是播放），或者内存里有一个偏好还没落盘。
  `[[ -n "$CURRENT_PLAY_ID" ]] || ((CURRENT_PLAY_LOADING)) || [[ -n "$PREF_DIRTY" ]]` ——
  play id 覆盖一个正在跑的播放器，LOADING 覆盖 socket 出现之前那个窗口，
  那时 spinner 必须在还没有任何东西可轮询之前先转起来，第三个覆盖延后的写回：
  没有它，一个什么都不放的会话里改的偏好会一直停在内存里到退出为止 ——
  阅读器会**阻塞**，`nav_tick` 根本不跑。一串 cycle 键因此只多付一次醒来，
  而那一串正是延后本身要吸收的东西。它**刻意**是双向的：
  列表在整个播放期间都滴答（它的 rail 是活的，见下），而什么都不播时**没有东西**滴答 ——
  当年那张卡会永远每秒重画一次静态的 `(nothing playing)`。实时过滤免费搭上这趟车，
  因为 `filter_live` 驱动的是同一个读取器。
  - **`read_query_input` 被刻意排除在外。** `n` 新搜索提示有自己的读取器、且不带超时：
    在那里滴答会在一条查询正被键入时把屏幕重画。
  - **时钟拥有轮询，渲染器不拥有**（`nav_tick`）。渲染器只需要百分比给它的 rail 与横幅，
    所以那次轮询在滴答上发生。`fetch_play_times` 是一对 `nc` + `jq` —— 两次 fork ——
    把它放进渲染器会让每一次方向键按下都赔上一次 IPC 往返。一次在两拍之间发生的重绘
    复用上一次的值，最多一秒旧，而那本来就是 rail 绘制的分辨率。**每拍恰好一次轮询。**
    （当年那张卡在自己的渲染器里轮询，因为它的整个正文就是那个读数 —— 于是同一拍会有两次；
    只剩一个渲染器之后，这个例外没有了。）
- **列表那条 rail 就是同一条 rail，而且它在播放期间是活的。** 导航块下面那条边界如今画成强调色
  而不是暗色 —— 它与那条活的进度 rail 成对，所以对齐能保住**一套** rail 语言
  （`print_details` 那条 rail 也加入其中）。
  一首曲目播放期间，那条边界**就是**那条活 rail：时钟把百分比留在 `PT_PCT` 里，
  于是这一行兼作位置读数，列表不需要自己的条。它从不改变宽度、也从不消失 ——
  没有百分比时（一条直播，或者 mpv 答话之前的第一秒）就在同样的 `nav_cols` 宽度上画静态分隔线，
  而 `clear_play_state` 会重置 `PT_PCT`，于是一个停掉的播放器不会在身后留下一个画好的位置。
- **两条 rail，两个时钟 —— 这是章节视图存在的第二个理由。** 章节列表里，上面那条 chrome rail
  仍然是**条目**的时间轴（曲目走到整支视频的哪里），而 `print_details` 那条 rail 变成**被选中那一个
  章节**的播放进度（`chapter_pct`）：一条 rail 把同一个百分比印两遍，等于花掉一整行去复述三行以上
  的那个数。两条线用的是同一个 `render_prog_bar`、同一个 `nav_cols`，所以它们是一套语言的两个读数，
  不是两个部件。
  区间之外**钳住**而不是留白：播放头已经越过的章节就是放完了（100%），还没到的就是没开始（0%），
  两句都是真的，而钳位是这条线在选择上下移动时不改变形状的原因。留空只留给答不上来的问题 ——
  没在播、直播、还没有读数、播放器里是**另一个**条目（`handle_key` + engine 这一对，
  与章节行上的 Enter 在决定 seek 还是 launch 时问的是同一个问题）、或者引擎没有发布 `end_time` ——
  那时它退回静态分隔线，与上面那条 rail 在 `PT_PCT` 为空时的做法一致。
  章节的终点是**按起点**在条目自己的章节表里查的，不是按行号：过滤与翻页会重排行
  （`chapter_sec` 从行的 url 里把偏移读回来正是为此），而 `ITEM_CHAP_*` 是引擎发布的整张表。
- **光标跟着播放头走，而不是跟着按键走（`chapter_follow`）—— 这条 rail 的另一半。** 少了它，
  第二条 rail 是一个填满一次就停住的条：一章放完了却仍然被选中、钳在 100%，而正在播的那一章
  在屏幕上没有任何东西，读起来像是视图卡住了，而不像文档说的"被选中那一章"。rail 两种情形下
  都没说错；缺的是**选择本身也是条目那个时钟推动的东西**。
  是**跟随**，不是抢夺：用户一动光标就归用户。`CHAP_FOLLOW_SEC` 记住上一次看时播放头在哪一章，
  只有当选择还停在**那一章**上才移动 —— 曲目在播时往下翻两章看看，不会有东西被夺走。它存的是
  起点**秒数**、从不是行号，理由与 `chapter_sec` 存在的理由相同：过滤与翻页会重排行，一个行号
  在下一次按键之后就指向另一章了。锚在 `ITEM_URL`/`ITEM_ENGINE` 而不是被选中的行上，因为问的是
  **这个视图**的问题（这里每一行都是同一个条目的一个偏移），答案不该随光标移动而改变 —— 于是
  `chapter_pct`、`play_chapter` 和它对"播放器里是不是这个条目"的理解是同一个。
  `open_chapters` 在门口先跑一次同一个函数：播放器里就是这个条目时，视图**开在正在播的那一章**上。
  播放头在第 9 章而光标在第 1 行，既是卡住感的第一帧，也会把光标停在任何一次跨界都够不到的地方。
  翻页由它自己设 `page_index`（`selected / PAGE_SIZE + 1`，与 `display_menu` 重新分页时同一个式子）：
  一个随后被主循环钳回旧页的选择，等于没有移动。`filter_live` 也调它，理由与它同样要调
  `check_player_alive`/`player_check_ready` 一样 —— `/` 开着时那个循环不回主循环，它略过的东西
  就冻结整场；而过滤掉了新那一章时，光标就留在原地。
- **三个播放态，不是两个。** `-d` 在播放器一 fork 出来就返回，但 mpv 还得经 yt-dlp 解出流、
  填满它的缓存，而在一个冷 URL 上那是**好几秒**（实测：第一次播一个 lofi 混音约 9 秒）。
  横幅在整个静音窗口里一直宣称 `▶ Playing`。如今在"已启动"与"出声"之间有一个 `Starting` 态，
  用的是取数 spinner 那几帧象限，于是这次等待看起来与它之前那次等待是同一件事。
  四件事让它成立：
  - **看 `core-idle`，不看 `time-pos`。** mpv 早在放出一个音符之前就会应答 IPC。
    `core-idle` 在播放器什么也没产出时为真 —— 加载、seek、等缓存 —— 并在输出开始的那一刻翻假，
    而那恰恰是标签该翻的那条边。`time-pos` 在文件仅仅被**加载**时就非空，
    于是它会把一条还在缓冲的流叫做"正在播放"，把问题又放回原处。
  - **正是这个状态第一次让"会滴答的列表"成为必需**（见上面的共享时钟）。
    一个只在按键时刷新的横幅，就是 `check_player_alive` 存在要防的那种陈旧 bug。
  - **一个裁决者。** `play_state_marks` 挑字形/标签/颜色；横幅传入自己的 "playing" 字形
    （`▶`）并画出返回的东西。它是为两个视图写的（卡片传 `●`），而状态与字形本来就是两件事，
    所以少了一个调用方之后它照旧带着那个参数。
  - **这个窗口里刻意不画 rail。** 列表保持它的静态分隔线 —— 活 rail 需要一个百分比而此刻还没有。
    考虑过一条"不确定"的动画 rail 并谢绝：它会成为紧挨着 spinner 与标签的**第二个**状态指示器，
    与横幅标题丢掉它的 `▶` 所针对的是同一种重复，还额外附赠一个代价 ——
    一条停在 40% 的扫描线与一首播到 40% 的曲目分不出来。而列表自己那一行无论如何都不改变宽度，
    这正是"静态"这个选择在那里免费的原因。
  - **除了成功之外还有两条出路。** 窗口期内的一次暂停会清掉这个状态 ——
    暂停时 `core-idle` 保持为真，所以那个探测永远清不掉它，而在一个用户刚刚暂停的播放器上写
    `Starting` 是一句错话。以及一个 20 秒的上限无论如何都会清掉它：
    在一条慢成那样的流上，选择是"一个永不收敛的动画"与"这个状态存在之前它显示的那个乐观标签"
    之间的二选一，而上限选后者，且只选一次。
- **URL 管道：** url 是那条 US 分隔记录的第 1 个字段，`load_rows` 把它连同五个 `R_*` 字段数组
  一起拆回 `urls[]`，于是一次选取就是一次直接的数组下标 —— 绝不重新解析一条渲染好的行。
  标题不可能打破字段边界，因为 `clean` 会折叠空白（于是没有 tab 或换行活得下来），
  而分隔符是一个没有标题会携带的控制字符。
- **拒绝而不是挂起：** stdin 与 stdout **两者**都必须是 TTY，否则就 die，
  于是一次 agent/管道调用干净地退出，而不是阻塞在键盘输入上。`-h` 不需要 TTY 也能用。
