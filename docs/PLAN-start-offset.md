## 1. 触发这份计划的事

用户原话：「目前的 ut-play 不能直接放一个 sourcelink」，例子
`https://www.youtube.com/watch?v=I9aVc4Z-n-M&t=601s`。

追下去是**两件不同的事**，只有第二件是本仓的：

1. **链接本身能放。** 实测（2026-08-30）：加引号 `ut-play -d -j -- 'https://…&t=601s'`
   返回 `{"status":"started","id":"7rztar",…}`，`yt-resolve` 也正常吐 `stream_urls`。
   不加引号是 zsh 先炸（`?` 触发 NOMATCH、`&` 把命令扔后台）。**不是本仓的问题，不修。**
2. **`t=601s` 被静默吞掉，从 0 播。** 这是本计划的全部内容。

之所以定性为「缺口 + 一个沟通缺陷」而不是 bug：契约从没承诺过起播位置，
`ut-play` 的 handle 定义回答的是**放哪个东西**。但**静默**接受一个自己不打算兑现的输入，
违反本仓「缺能力就用没有这个动词来声明」的规矩（`bili-resolve` 没有 `--transcript` 是那条规矩的样板）。

## 2. 实测到的事实（证据基座，2026-08-30）

每一条都是跑出来的，除了明确标注的那条。

1. **偏移在三处都够不着，一处不落。**
   - `yt-resolve` 的 ok 信封 `url` 取自 yt-dlp 的 `.webpage_url`（`shell/yt-resolve:533`），
     那是规范化过的播放页地址，`t` 不在里面。实测返回 `"url":"https://www.youtube.com/watch?v=I9aVc4Z-n-M"`。
   - `ut-play` 全文 `grep -- --start` **零命中**，`run_mpv`（`shell/ut-play:576`）从不传起播位置。
   - `--seek` / `--seek-to` 是 **ACTION**（`shell/ut-play:2394`，走 `set_action`，与播放互斥），
     不是启动参数。重载它会撞上动词分派 —— 这是必须新造一个词而不是复用旧词的原因。

2. **mpv `--start=N` 成立，且不扰动 duration。** 本地合成源（`av://lavfi:sine`，按
   `CLAUDE.md` 测试规矩用合成源而非 YouTube），IPC 读回：

   ```
   start=none  time-pos=0.317334   duration=1.857596
   start=42    time-pos=42.272673  duration=43.839274
   start=42    time-pos=42.295471  duration=43.839274   ← 复现一致
   ```

   **对照组是必须的**：`duration` 那一列看着可疑，但无 `--start` 时同样是 `time-pos+1.5` 左右，
   所以那是 lavfi 报未知时长的怪癖，**不是 `--start` 造成的失真**。结论：playhead 落在 N，别的不动。

   **这个合成源是一次探针，不能当 `tests/playback.sh` 的源**（pre-mortem F3，实测确认）：
   `ut-play` 每一条播放路径都过 `resolve_media`（`shell/ut-play:768`、`:845`），
   **没有绕过引擎的口子**，所以要让 `av://lavfi:sine` 走完播放器就得有一个假引擎 ——
   那是 mock，仓规不许（`tests/playback.sh:334` 的注释正是为这件事写的）。
   `tests/playback.sh` 今天播的是真 YouTube URL（`:58`、`:59`），全文没有 lavfi。见 §7。

3. **`--status` 的 `position` / `duration` 是活体读的**（`shell/ut-play:1018`、`:1859`，
   一次 IPC 往返读 `time-pos`/`duration`），不是记录里的投影。所以 `--start=601` 之后
   `position` 从 601 起报 —— 这是对的，无需任何额外投影工作。

4. **`ut-history` 的 `seconds` 是墙钟差**（`shell/ut-play:1269`，`now_epoch - TRACK_STARTED_EPOCH`），
   回答的是「你听了多久」，与起播位置无关，**不需要改**。但见 §6 第 3 条的一个已知后果。

5. **时间戳的站点写法 —— S0 量完了（2026-08-30，yt-dlp `2026.08.19`）。**
   量的是 `yt-dlp -J` 的 `start_time`：yt-dlp 的 extractor 就是「这种写法存不存在」的权威。

   **YouTube —— 十种写法，yt-dlp 全都认，一种都不用我们自己解：**

   ```
   FORM                                             start_time   webpage_url 带 t?
   watch?v=ID&t=601                                 601          否
   watch?v=ID&t=601s                                601          否
   watch?v=ID&t=10m1s                               601          否
   watch?v=ID&t=1h2m3s                              3723         否
   youtu.be/ID?t=601                                601          否
   embed/ID?start=601                               601          否
   watch?v=ID#t=601        ← 锚点也认               601          否
   watch?v=ID&t=0                                   0            否   ← 判别性输入，天然分得开
   watch?v=ID&t=601.5                               601.5        否   ← 浮点，不是整数
   watch?v=ID&t=banana                              null         否   ← 认不出 = null，不是错误
   watch?v=ID            （不带时间戳）             (键不存在)   否   ← 缺键，不是 null
   ```

   `start_time` 在 `yt-resolve` **自己那条 dump 上也在**（带 `-f` 与 `--format-sort` 复跑，
   `start_time=601`），所以不是 `-J` 裸跑才有的字段。

   **Bilibili —— yt-dlp 一个都不给，`start_time` 键在任何形态下都不存在：**

   ```
   FORM                                    start_time   webpage_url
   video/BV…                               (键不存在)   -
   video/BV…?t=601                         (键不存在)   video/BV…?t=601      ← 原样留着
   video/BV…?t=601.5                       (键不存在)   video/BV…?t=601.5    ← 原样留着
   video/BV…?p=2                           (键不存在)   video/BV…?p=2
   video/BV…?p=2&t=60                      (键不存在)   video/BV…?p=2&t=60
   b23.tv/BV…                              (键不存在)   video/BV…/           ← 短链被规范化
   ```

   **两条推翻计划的结论**（见 §4 S1 的重写）：
   1. yt 这一半**不需要解析代码**：读它已经拿在手里的那份 dump 的 `.start_time` 即可。
      §4 S1 原本写的「在 `normalize_target` 里摘出来」对 yt 是白写一遍 yt-dlp 已经做完的事。
   2. bili 这一半**必须自己解**，而且只能在 `normalize_target` 里 —— 那是它唯一看得见原始
      query 的地方。所以两个引擎从**不同的来源**填同一个键，这正是本仓的家法：
      缝是信封，不是缝后面那个工具。

6. **`.webpage_url` 今天不带 `t`，两种写法都不带。** 实测（2026-08-30，pre-mortem 期间）：

   ```
   https://youtu.be/I9aVc4Z-n-M?t=601          -> {"status":"ok","url":"https://www.youtube.com/watch?v=I9aVc4Z-n-M"}
   https://www.youtube.com/watch?v=I9aVc4Z-n-M&t=601s -> {"status":"ok","url":"https://www.youtube.com/watch?v=I9aVc4Z-n-M"}
   ```

   短链形态也被规范化掉了，所以 §4 S1「`url` 照旧规范化」的前提在 **yt 这一半**今天成立。
   但 yt-dlp 是外部、不 vendor 的依赖，这是一条**会漂移的前提**，而漂移的后果是静默的：
   `ut-playlist --add` 存的正是这个 `url`，一旦它带上 `t`，收藏的曲目下次就从 601 秒开播。
   §7 为此单开一行反向断言。

7. **而 bili 这一半的前提今天就不成立 —— 这是 S0 撞出来的、计划完全没预料到的事。**
   实测：

   ```
   bili-resolve -j -- 'https://www.bilibili.com/video/BV1mL411E7Fb?t=601'
     -> {"status":"ok","url":"https://www.bilibili.com/video/BV1mL411E7Fb?t=601"}
   ```

   `bili-resolve` 的 ok 信封 `url` 也取 `.webpage_url`（`shell/bili-resolve:551`），
   而 B 站这边 yt-dlp **原样保留整个 query string** —— 它必须保留，因为 `?p=N` 就在里面，
   那是「哪一分 P」的唯一凭据。于是 `t=` 顺带被留下了。

   后果不是理论上的：**今天** `ut-playlist --add` 存一条带 `?t=` 的 B 站记录，
   存下的就是带偏移的 url。而 `start_seconds` 一旦落地，重放时会从那个 url 里再解出
   601 —— 收藏的曲目就真的从 10:01 开播。这正是 §4 S1 第 1 条要防的那个后果，
   在 bili 上先于本计划就已经半成立了。**这是一条新的、要拍板的决定，见 §8 第 3 条。**

## 3. 为什么这是两层的活

一句话：**认得写法是站点知识，执行偏移是播放动作。**

- `?t=601s` 是 YouTube 的语法，`?t=601` 是 B 站的语法 —— 让 `ut-play` 去 parse query string，
  等于把站点知识重新长回播放器里，正是 §3.4 划走的那部分。所以**解析在引擎**。
- 「从 N 秒开始」是 mpv 的一个 flag —— 引擎不碰 mpv（碰了就是分层违规）。所以**执行在播放器**。
- 中间的缝是**信封**，和套件里其他每一条缝一样。

推论：第三对引擎不需要为这个功能做任何额外设计，它只要在自己的信封里填那个键。
本站没有时间戳语法就恒填 `null` —— 与 `kind`/`access` 恒填默认值是合法状态同理
（`AS-BUILT-engine.md` §7.2）。

## 4. 逐项设计

### S1 —— 引擎填 `start_seconds`（信封新增必需键）

**这一节被 S0 改写过。** 原设计是一句话「每个引擎都在 `normalize_target` 里把偏移摘出来」，
它假定两个引擎干同一件事 —— 实测证明不是：那对 yt 是白写一遍 yt-dlp 已经做完的事
（§2 第 5 条）。现在是**一个键，两个来源**：

| 引擎 | 值从哪个数据来 | 在哪个函数 | 在哪一步 | 要写多少解析代码 |
|---|---|---|---|---|
| `yt-resolve` | `dump_once` 输出里的 `.start_time` | 已有的信封 jq | 网络请求**之后** | **零**，十种写法全免费 |
| `bili-resolve` | 原始句柄 query 里的 `t=` | `normalize_target` | 任何网络请求**之前** | 全部，yt-dlp 一个字都不给 |

两个来源不同侧不是妥协，是本仓的家法：**缝是信封，不是缝后面那个工具**
（`CLAUDE.md` —— 一个引擎的两半本就不必用同一个 primitive）。

推论给第三引擎作者：**先跑一次 `yt-dlp -J <带时间戳的 URL> | jq .start_time`**。
有值就照 yt 那样白拿，没有就照 bili 那样自己解 —— 这一句进 `AS-BUILT-contract.md` §6 的清单。

四条约束（不变，S0 只是给每一条都补上了实测依据）：

1. **`url` 照旧规范化，偏移只走新键。** `url` 回答「这是哪个媒体」，`start_seconds` 回答
   「从哪开始」，两件事不混。直接后果：`ut-playlist --add` 存下的是**歌本身**，
   下次从头放 —— 收藏一首歌不该把 10:01 一起钉进去。
   **yt 这一半白拿（`webpage_url` 本就不带 `t`），bili 这一半要动手剥** ——
   §2 第 7 条是事实，§8 第 3 条是决定，§5 的 5.3 是那条契约动作。
   这条约束是本计划里唯一一条**两个引擎代价不同**的约束。
2. **必需键，值可为 `null`。** 与 `http_headers`（必需、可为 `{}`）、`kind`/`access`
   （必需、枚举封闭）同一套家法：第三引擎作者不会「忘了实现」，
   漏键与一次被截断的读也才分得开。`null` = 这个句柄没带偏移。
3. **值是非负整数秒，浮点向下取整。** 站点写法（`601s`、`10m1s`）化成秒 —— 对 yt 是
   yt-dlp 化的，对 bili 是我们化的。**取整是必须的，不是洁癖**：实测 yt-dlp 对
   `?t=601.5` 吐的是浮点 `601.5`，B 站的 `webpage_url` 也原样留着 `601.5`（§2 第 5 条）。
   向下取整而非四舍五入 —— 见 §8 第 2 条。
4. **解析不出来 = `null`，不是错误。** 一个看不懂的 `t=` 值不该让整次 resolve 失败；
   它没有回答一个必须被回答的问题。实测坐实了这条在 yt 上是白拿的：
   `?t=banana` → yt-dlp 给 `null`，不带时间戳 → 键直接不存在，两者在我们这层都塌成 `null`。
   **注意 jq 的坑**：`?t=0` 给的是 `0`，`.start_time // null` 在 jq 里对 `0` 返回 `0`（0 为真），
   所以这个写法安全；但换成 `// empty` 或 bash 的 `[[ -n ]]` 就会把 `0` 当没有 —— 
   §7 的判别性输入正是为此。

`--info` 信封同样带这个键（它和 resolve 共用 `TARGET_URL`），保持两个信封说同一件事。

**pre-mortem F2 那张表就是上面那张，它当场起了作用**：两个格子填出来是两个不同的答案，
而原设计假定它们相同。这正是那条规矩要抓的东西 —— 填不满（或填出不一样）的格子是分层
假设不成立的信号，那时改设计，不改断言。它同时是 §7 那条「每一个被发现的引擎上都是必需键」
的前置：一个恒填 `null` 的引擎能让不变量绿掉，而那正是这条不变量本来要防的东西。

一处 pre-mortem 期间查掉的伪风险，记下来免得再查一次：**B 站的分 P 不构成障碍。**
`bili-resolve` 的 `normalize_target`（`shell/bili-resolve:408`）对 URL 是 `TARGET_URL="$t"`
**整个穿过**，query string 原样交给 yt-dlp —— yt-dlp 解的就是 `?p=N` 那一分 P，
mpv 打开的流**就是那一分 P**，所以 `?t=601` 天然是那条流的 601 秒。
不需要 `fetch_view_once`，不需要分 P 结构，不需要重排解析顺序。

**一处已存在的不一致，随手记下不随手改**：ok 信封的 `url` 来自 `.webpage_url`（无 `t`），
error 信封的 `url` 来自 `--arg url "$TARGET_URL"`（有 `t`，`shell/yt-resolve:558`）。
先于本计划存在，与本计划无关，**不在本计划的范围内** —— 但 S1 动的正是这个函数附近，
所以写在这里以免下一个人以为是本次引入的。

### S2 —— 播放器消费

`resolve_media` 多一个 out-param `RESOLVED_START`（与 `RESOLVED_DURATION` 同一批全局，
每条 track 清空后重填）。`run_mpv` 在 `--volume=` 附近多一行：非空则 `mpv_cmd+=(--start=N)`。

**清空写在 `resolve_media` 的入口无条件块里，不写在成功路径上**（pre-mortem F5）：
`shell/ut-play:450-459` 已经在函数开头无条件清掉全部 `RESOLVED_*`，`RESOLVED_START=""`
加进那个块即可 —— 这不是新约定，是既有惯例，照抄就行。写在成功路径上的后果是具体的：
队列第一条带 `t=601`、第二条 resolve 失败或没有偏移时，全局留着上一条的 601，
`run_mpv` 照样加 `--start=601` —— 直接违反 S4 写死的「只作用于第一条」。
单人仓没有评审能抓这个，机械约定就是评审的替代品。

**放在 mode 选项之前**，与 `--volume` 同侧 —— 它不是要压过谁的收尾选项，
而 `detached_opts` 那一组「放在后面才赢」的理由（mpv 末位优先）在这里不适用。

### S3 —— `--start SEC` 覆盖

新长标志，取**非负整数秒**，与 `--seek-to N` 同一套词汇（套件里时间一律是秒：
`duration`、`position`、history 的 `seconds` 全是）。

- 负数、`hh:mm:ss`、非数字 → **usage 错误，退 1**，在门上拒。
  不透传 mpv 的完整 `--start` 语法（含 `--start=-60` 从末尾算）：那会把 mpv 的语法泄进冻结面，
  以后换掉 mpv 就换不掉这个形状，且与 `--seek-to` 只收秒不一致。
- **优先级 `--start` > 引擎的 `start_seconds`**，与套件的四层链同向（flag 最大）。
- 与 `--status`/`--stop`/`--seek` 等动词互斥 —— 它是播放路径的标志，不是动词。

### S4 —— 队列作用域

`--start` **只作用于第一条**。它是一次性的启动意图（「从这儿接着听」），不是队列级策略；
「每首歌都跳过前 10 分钟」没有真实用例。

实现：脱离子进程的播放循环（`shell/ut-play:1102` 起）里，`--start` 的值在**第一次**
`play_url_directly` 之后清空。跳过（`--next`）不保留它 —— 一次性就是一次性。

队列里**每条各自的 `t`** 自动成立：每条都单独 resolve，`RESOLVED_START` 逐条重填。
所以「混源队列里第 3 条带时间戳」不需要任何额外设计。

## 5. 契约动作（两项，都在冻结面上）

| # | 动作 | 面 |
|---|---|---|
| 5.1 | `<engine>-resolve` 的 resolve / `--info` 信封新增**必需键** `start_seconds`（`null` 或非负整数） | `AS-BUILT-contract.md` §3 |
| 5.2 | `ut-play` 新增 `--start SEC` | `AS-BUILT-contract.md` §1.1、§2 的门表 |
| 5.3 | `bili-resolve` 的 resolve / `--info` 信封的 `url` **剥掉 `t=`**（只剥它，`?p=` 保留） | `AS-BUILT-contract.md` §3 的 `url` |

5.3 是**改一个已有字段的值**，不是加一个键 —— 三项里唯一一项对现有消费方可见的变化。
它单独存在的理由在 §8 第 3 条：不做，`start_seconds` 就会让 §4 S1 第 1 条只对一半引擎为真。

`AS-BUILT-contract.md` §6「加一个引擎清单」要同步长出这一条，否则第三引擎作者按清单写出来的引擎
会漏一个必需键。

**版本位：`0.4.0`，y 位。** 曾倾向 z（对信封的**消费方**零破坏，只是多一个键），
pre-mortem 推翻了它：「今天仓外生产方零个」论证的是「不会有人红」，
那和「是不是新增了对外义务」是两件事。§6 那份加引擎清单长一条必需键，
就是对第三引擎作者的一条新义务，义务的破坏性不取决于今天有几个人在履行它。
按规矩 `VERSION` 单独一个 commit，且见 §8 的门。

## 6. 明确不做的（每条附理由，免得日后当成疏漏）

1. **不进播放信封、不进 player record、不进 `--status` 投影。** `--status` 的 `position`
   已经活体报出真实播放位置（§2 第 3 条），起播偏移是它的**成因**而不是一个新事实；
   多一个只写不读的键，就是本计划自己在 §4 里拒掉的那种字段。
2. **不进 TUI。** `uting` 的行来自 `<engine>-search`，搜索结果的 `url` 从来不带 `t` ——
   这个功能在 TUI 上没有入口，所以没有键位要加。`ARCHITECTURE.md` §3.5 的
   「每个功能都要有 agent 面」在这里是满足的：agent 面就是 `--start` + `start_seconds`，
   而**它本来就没有人面**，不是漏了人面。
3. **不给 history 行加偏移字段。** 已知后果：从 601s 听到结尾的一条，行上是
   `seconds=3000 of duration=3601` —— 看着像没听完。这是**如实记录了收听时长**，
   不是错。加一个 `start_offset` 是第二次改冻结面，为的是今天没有任何读者的一个读法。
   **重开条件**：出现一个真的要区分「听完了」与「听了一半」的消费方。
4. **不认 `list=` / playlist 参数。** 那是把一个 URL 变成一个队列，与起播偏移是两件事，
   量级也完全不同。
5. **不改 zsh 引号那件事。** 见 §1 第 1 点。
6. **不动 error 信封的 `url` 不一致。** 见 §4 S1 末尾。

## 7. 验证矩阵（三层，各归各的套件）

| 层 | 检查什么 | 落在哪 | 为什么在这一层 |
|---|---|---|---|
| 门 | `--start` 的取值门：负数 / `hh:mm:ss` / 非数字 / 缺参 → 退 1；与动词互斥 → 退 1 | `tests/contract.sh --offline` | 纯参数解析，零网络。**必须 offline**，否则这条门会被跳过 |
| 信封 | `start_seconds` 是**每一个被发现的引擎** × resolve/`--info` 上的必需键；带 `t` 的句柄解出正确秒数、不带的解出 `null` | `tests/contract.sh` 活体半 | 引擎的解析只能经一次真 resolve 观察到 —— 没有干跑的面。按「对每一个被发现的引擎」陈述为不变量，第三引擎落地当天自动被覆盖 |
| 行为 | mpv 真的从 N 秒开始：`--start 600` 起播后从**真 socket** 读回 `time-pos`，判 `595 ≤ p ≤ 605` | `tests/playback.sh`，源用它已有的 `U1` | 「真 mpv 在那一头」的断言只住在这里（`CLAUDE.md` 测试规矩）。参数在下面写死，不留给实现时现定 |
| 漂移 | `yt-resolve -j -- 'https://youtu.be/ID?t=601'` 的 `.url` **不匹配** `[?&#]t=`，且 `.start_seconds == 601` | `tests/contract.sh` 活体半 | 这条抓的是 **yt-dlp 漂移**，不是我们的代码。守的是 `start_seconds` **存在的理由**（§2 第 6 条），不是这个键本身 |
| 漂移 | bili 同名一条，但**两侧都要断**：`bili-resolve -j -- '…/BV…?p=2&t=601'` 的 `.url` 不匹配 `[?&]t=` **且仍匹配** `?p=2`，`.start_seconds == 601` | `tests/contract.sh` 活体半 | 剥是我们写的（§5 的 5.3），所以这条同时是**剥对了**和**没剥过头**的证据。只断前半句的话，一个把整个 query 都扔掉的实现会绿 —— 而那会让 `?p=` 指的分 P 丢掉 |

**加固优先于新增**（`CLAUDE.md`）：信封那一层不新开文件，挂在 `contract.sh` 已有的
「跨所有被发现引擎的信封不变量」那组检查上 —— 那组已经在断言 `kind`/`access` 必填，
`start_seconds` 是同一句话多一个字段。

**判别性输入**（不能靠改源码看红）：`?t=0`。一个把「解析不出/没带」和「带了但等于 0」
混成同一个值的实现，会在这里印 `null` 而不是 `0` —— 而正确实现两者分得开。
这条输入零成本、不碰工作树，且作为覆盖长期留在套件里。

**一条实现时量出来、计划没预料到的事：活体那一层的句柄不能随便取。**
最初写成「取搜索结果第一条」，结果 `lofi` 的头几条是电台 —— `is_live` 的 24/7 直播，
以及 `was_live` 的十二小时回放。对任一种做定格式 resolve 要跑**几分钟**：
`contract.sh` 从 118 秒涨到 9 分钟以上。第一版的过滤只排掉了 `is_live`，
于是仍然挑中一条 `was_live` 的十二小时行，照样挂。
最终形状：`live_status == null`（两种时态的广播都排掉）之后取 **duration 最短**的一条 ——
不需要争一个时长阈值，且按构造就是整页里最便宜的句柄（实测 yt 4 秒、bili 3 秒）。
句柄本身也被断言（`<engine>-search offers a non-live row to resolve`），
所以哪天这个查询不再返回合适的行，红的是一条有名字的检查，而不是它底下的四条。

**行为那一层的三个参数在这里写死，不留给实现时现定**（pre-mortem F3）：

- **源 = `tests/playback.sh` 已有的 `U1`（`:58`），不是合成源。** 理由在 §2 第 2 条：
  `ut-play` 没有绕过引擎的口子，合成源进不来 —— 硬要进就得造一个假引擎，那是 mock。
- **N = 600**，不是 42。
- **容差 = ±5 秒**（判 `595 ≤ p ≤ 605`）。

**为什么这个容差不会让一个错误实现变绿**：一个把 `--start` 吞掉的实现，`time-pos` 读回的是
个位数 —— 与 600 差两个数量级，±5 怎么放都分得开。反过来，N 若取 42，冷启动 + 未预热解码
时读回值会在 42.0–43.6 之间抖，容差就得放到 ±1.5 以上，而那个宽度已经能让「从 0 开播」
在小 N 上蒙混过关 —— 那就是一条**不能失败的检查**，仓规明令拒绝。
N 拉大是把这个两难直接消掉，不是把它调参调过去。

不加「起播后立刻 `--pause` 再读」：`playback.sh:215` 用那个手法是因为 `--seek` 之后
播放中的 `time-pos` 自己在走；这里 N 与误差差两个数量级，多一次 IPC 往返换一个不需要的精度。

## 8. 还没定的

**门：归零之前不写 `VERSION`**（pre-mortem F5）。它们不是备注，是未答的问题；
在有项目悬着的情况下发版，等于让版本号替一个还没做完的决定背书。

S0 关掉了两项，又开出一项，那一项也已拍板。**本节归零，`VERSION` 的门开了。**

### ~~1. `#t=` 锚点要不要认~~ —— S0 关掉了

**认，而且零成本。** 实测 `watch?v=ID#t=601` → yt-dlp 给 `start_time=601`（§2 第 5 条）。
它不是「凭空多出一种写法」，它是我们白拿的十种之一 —— **要拒绝它反而得写代码**。
B 站那边不适用：没有任何证据说 B 站用 `#t=`，而 bili 是手解的，
所以 `bili-resolve` 只认 query 里的 `?t=`，不认锚点 —— 缺证据的写法不进实现（S0 的规矩）。

### ~~2. B 站的小数秒怎么落~~ —— S0 关掉了

**这种写法真的存在，且不止 B 站有**：yt-dlp 对 `?t=601.5` 吐浮点 `601.5`，
B 站的 `webpage_url` 也原样留着 `601.5`。**向下取整**（`601.5` → `601`）。
理由两条：四舍五入会把播放头推过用户指的那一刻，而「从这儿接着听」宁可早半秒不可晚半秒；
且套件里 `seconds` / `position` / `duration` 一律是「已经过去了多少秒」，
向下取整是这个词本来的意思。

### ~~3. B 站的 ok 信封 `url` 要不要剥掉 `t=`~~ —— 拍板：**剥**

事实见 §2 第 7 条。选**剥**（只剥 `t`，`?p=` 等一概保留），理由：不剥会让 §4 S1 第 1 条
变成一句**只在一半引擎上为真**的话，而那种话是本仓最难查的一类 bug ——
它不会红，只会让收藏的 B 站曲目某天从 10:01 开始放。这是第三项契约动作（§5 的 5.3）。

**剥在 jq 里，不在 bash 里 —— 所以先前记的那笔代价不存在。** 值是从 yt-dlp 的 JSON
里出来的，两处都已经在 jq 中：ok 信封的 `url: (.webpage_url // null)`（`shell/bili-resolve:551`）
和 `--info` 的 `url: .webpage_url`（`:674`）。`CLAUDE.md` 那条 `${var//}` 是 O(n²) 的规矩
管的是 **bash 参数替换**，jq 的 `gsub` 不在其列（jq `1.8.2`，正则可用）。

**三段锚定 gsub，一段都不能少**（`t` 可能是首个参数、中间参数、或唯一参数）：

```
&t=…      →  ""        （非首个）
?t=…&     →  "?"       （首个，后面还有）
?t=…$     →  ""        （首个，且唯一）
```

**`--parts` 免疫，不用改**：它的 `$base` 是从 `.data.bvid` 拼出来的
（`shell/bili-resolve:846`），不经过 `TARGET_URL`，`t` 漏不进去。

一处实现注意：这两处信封的 jq **今天没带 `JQ_PRELUDE`**（它只在 `:660` 和 `:886` 用），
所以剥的 helper 要么让这两处也带上 prelude，要么就地内联 —— 选哪个是实现时的小决定，
不是设计决定。
