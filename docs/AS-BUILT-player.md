# AS-BUILT-player —— 播放器、队列与两个持久存储的实现

`shell/ut-play`、`ut-playlist` 与 `ut-history` 的**实现细节**：模式→格式→mpv 的落点、
错误分类、detached 生命周期的每一条状态规则、队列，以及收听行的写入点。两个存储写在这里而不是
另开一份，是因为它们是 §9 的子节：生命周期与"围着它的那些状态"是同一个故事。

**引擎那一半不在这里。** 站点知识 —— 搜索、解流、cookie 与 PO token 探测、句柄文法与 host
白名单 —— 在 `AS-BUILT-engine.md`；播放器是 source-agnostic 的，这条分界就是它的意思。

**这份文档与 `ARCHITECTURE.md` 的分工**：架构文档只留图、流程、伪码与决定；具体怎么落地、
哪一条规矩是被实测逼出来的、以及踩过哪些坑，都在这里。节号沿用架构文档原有的编号
（§8.1 / §8.3 / §9 及其子节），所以既有的 `§9.5` 一类引用只需要换文件名，不需要改号。
契约面（argv、信封、退出码）不在这里，在 `AS-BUILT-contract.md`。

**代码是唯一权威。** 本文点名函数时给的是 soft ref（文件 + 函数名），不复制实现；
伪码是形状，不是源码的副本。

## 8. 播放子系统

### 8.1 模式 → 格式 → mpv —— **模式是共享的，格式表是引擎的**

`-f MODE` 是播放器的 flag，原样传给引擎；一个模式作为格式字符串**意味着什么**是站点知识，
所以 `format_for_mode()` 住在每个 `<engine>-resolve` 里，绝不在 `ut-play` 里。播放器从头到尾
没见过格式字符串，除了把它当作一个不透明的值记进播放器文件、且再也不读
（AS-BUILT-contract.md §3）。

```
  MODE（播放器 flag）  <engine>-resolve: format_for_mode()   ut-play: mpv 选项集
  ──────────────────   ─────────────────────────────────     ───────────────────────────────
  audio                YT_AUDIO_FORMAT (ba/b)                 --no-video（仅音频）
  video                YT_VIDEO_FORMAT (bv*+ba/b)             默认 VO
  fast                 YT_VIDEO_FORMAT_FAST                   默认 VO（渐进式）
  ascii                YT_VIDEO_FORMAT                        --vo=<YT_ASCII_VO> --profile=sw-fast
  viz                  YT_AUDIO_FORMAT                        --vo=tct + showwaves lavfi 滤镜
                       （给了 -S SORT 时原样转发为 --format-sort）
```

播放接缝只有一个：`shell/ut-play` 的 `run_mpv()` —— 它读引擎调用填好的 `RESOLVED_*` 全局量，
拼出 mpv 的命令行：`--no-ytdl`、detached 才有的 `--volume=N` / `--input-ipc-server=<sock>`、
来自 `http_headers` 的若干 `--http-header-fields-append`、来自信封的 `--force-media-title`、
`stream_urls[0]`（合并格式时再带一个 `--audio-file=<stream_urls[1]>`），以及 detached 专有的
`--no-term-osd-bar --msg-level=all=error`（把日志钉在有界大小）。

**`--no-ytdl`，以及 `ytdl_hook` 曾经免费替我们做的三件事。** mpv 拿到的是直链，自己不做任何抽取
（ARCHITECTURE.md §6.1）。那个 hook 隐式做的三件事如今各自显式地来自解析信封的一个字段：

- **请求头** —— `--http-header-fields-append` 重复给，而不是一个逗号拼起来的
  `--http-header-fields`：后者是一个**列表**选项，一个值里带逗号的头会被劈成两个坏头。
- **媒体标题** —— `--force-media-title`，否则 OSD 上显示的是一条 googlevideo 路径。
- **视频+音频配对** —— `--audio-file`，mpv 原生的合流方式；hook 当年是合成一份 EDL。

**请求头的值落在 mpv 的 argv 上，因此在 `ps` 里看得见。** 引擎**不得**在 `http_headers` 里
返回任何凭据类的头（`Cookie`、`Authorization`）；YouTube 引擎只返回 `User-Agent` / `Accept` /
`Accept-Language` / `Sec-Fetch-Mode`。这是一条**对引擎的契约**，在这里说一次，
在 AS-BUILT-contract.md §3 说一次。

**cookie 已经完全不是 mpv 的事。** 当年 mpv 自己抽取时，cookie 是经 `--ytdl-raw-options` 传进去的；
如今 cookie 的决定完全归发起 yt-dlp 调用的那个引擎（§8.2），播放器没有 cookie 代码、
不读 `YT_COOKIE_BROWSER`、也没有任何一条能把它泄出去的路径。

**终端噪声压制与视口保护（video 与 audio 模式）。** `video`/`fast` 会把媒体**标题**经 libass
渲染成视频 OSD。当标题里带着没有字体覆盖的字形（emoji —— 在 YouTube 上遍地都是），libass 会
逐帧吐一条 `[osd/libass] fontselect: failed to find any fallback with glyph …`，macOS CoreText
再吐一条 `CoreText note: … .LastResort …`。再加上 mpv 默认启动会打 8–10 行元数据
（`File tags:`、`Date:`、`Uploader:`），把 `uting` 的菜单顶进 scrollback、并挤掉进度条。
修法分两部分，且要让窗口 OSD/OSC 与终端进度条都保持稳定：

1. **`--msg-level=display-tags=warn,osd/libass=error`** —— 从源头压掉 libass 的 `fontselect`
   警告与多行元数据倾泻（`File tags:`），同时给 `-j` 的分类器保留 error 级（§8.3）。
2. **`run_mpv` 里的一层 stderr 过滤** —— 剩下的 CoreText note 没有任何 mpv flag 够得着，
   用 `2> >(grep -vE 'CoreText note|\.LastResort|fontselect' >&2)` 丢掉。

**这件事之所以安全，靠的是流的分开**：mpv 把有用的 `--term-osd-bar`/`AV:` 状态打在 **stdout**，
把噪声打在 **stderr**，所以过滤 stderr 永远碰不到进度条。用进程替换（而不是管道）让 `$?`
仍然是 mpv 自己的退出码，于是 `q`（130）与真实失败照样往上传。

**这层过滤只在"有人正看着这个终端"时才开** —— 即：不在 `-j` 下，也不在 detached 子进程里。
两个理由。其一它在那里买不到东西：`play_url_json` 把 stdout+stderr 收进一个从不显示的临时文件，
detached 子进程则写自己的日志。其二它会**损坏正确性**：进程替换不被 wait，而 `play_url_json`
在 mpv 一退出就去读那个临时文件 —— 它可能错过一行晚刷出来的错误，于是把一个真 403 分类成
`unknown`。过滤器只丢非错误行，所以在 prose 路径上 `-j` 的错误分类不受影响。`audio` 模式靠
`--no-video` + 压掉 tag 来避免菜单被纵向挤走，让 mpv 原地刷新的状态行（`A: ...`）就贴在菜单
下面；`ascii` 用 `--really-quiet`。

三种替代方案试过并被否决：**`--osd-level=0`** 能从根上灭噪声，但连窗口内的 OSD/OSC 一起关掉
（窗口里没有进度条与控件）；**`--msg-level=all=error`** 能静音，但**过度**压制，连有用的状态行
也没了（播放看起来是空白）；**`OS_ACTIVITY_MODE=disable`** 根本挡不住 CoreText note（它发在
`os_log` 活动层之下）。实测（一个 emoji 标题的视频，窗口 VO）：12 条 `fontselect` + 7 条
`CoreText` → 0/0，状态行与窗口 OSD 都在，`-j` 契约也验过（单行合法 JSON、`reason` 正确、
退出码照传）。

### 8.3 播放输出模式与错误分类

```
   ut-play -- <handle>       → play_url_directly → prose（"Playing audio: …"）  [默认]
   ut-play -j -- <handle>    → play_url_json     → 最后一行 JSON，闲话全部压掉
   ut-play -d -- <handle>    → detach_play       → 后台；JSON/prose 报 "started"
   （只要流 URL 而不播，是 `<engine>-resolve -j`，不是播放器的动词 —— §10；
     旧的 `--get-url` 拼法已退役，并用那条调用来回答。）
```

`play_url_json` 把播放器的 stdout+stderr 收走（压掉闲话）并只发一行 JSON。
`classify_playback_error(text, rc)` 把收到的输出映射到那份固定枚举 —— 绝不用 mpv 的原话，
那不是契约：

```
   rc == 130 ......................................... stopped_by_user
   文本命中 yt_reason=<member> ....................... 原样取该成员
                                                       （引擎已经分好类了）
   "HTTP Error 403" | 403 | "Forbidden" .............. forbidden
   name-resolution|connection|timeout|429 ............ network
   （其余一切 —— 保守默认）........................... unknown
   rc == 0 ........................................... reason = null（status ok）
```

**两个分类器，一份枚举，而播放器那个是小的那个。** 自 B-2 起，识别*一次抽取为什么失败*的那些
措辞 —— 视频不可用、请求的格式没有、需要登录确认 —— 只有引擎见得到，由它分类并报出 `reason`。
播放器通过 `yt_reason=` 这个标记**转述**那个裁决，而不是从它只能猜的散文里重新推导；它自己分类的，
只有"URL 已经在手时 mpv 还能怎么失败"：传输，以及 rc 130。`forbidden` 在两边都仍然可达，
因为一个签名过的媒体 URL 可能在解析与打开之间过期或被拒。**任何一边都不得新增
AS-BUILT-contract.md §3 未列出的成员。**

`exit_code` 是 mpv 真实的退出状态；进程退出码保持诚实（130 归一为 0 —— 那是一次有意的停止）。
（schema → AS-BUILT-contract.md §3。）

## 9. detached 播放的生命周期

### 9.1 进程组模型（为什么是它，而不是 PID 树）

一次 detached 播放是 `bash ut-play`，加上引擎那些短命的 `<engine>-resolve`/`yt-dlp`/`curl`
子进程，再加上 `mpv` —— 在没有 curl 的机器上，还可能有**一个更晚才生出来的（重试）mpv**。
两个事实让"朴素地杀进程树"失效：

1. 晚生的 mpv 出现在任何一次性 PID 快照**之后**。
2. 父 `bash` 一退出，mpv 就**改挂到 init**（`ppid=1`）—— 从原来那个 PID 往下走再也找不到它
   → 一个还在播的孤儿。

解法：把子进程作为**它自己进程组的组长**启动，并对整个组下手。`pgid` 在改挂父进程时不变，
所以它永远够得到每一个后代。

**进程组要拿子进程"免费的 stdin"来换，而这笔账必须显式还上。** bash 本来会自己把后台作业的
stdin 重定向到 `/dev/null` —— 但只在作业控制**关**的时候，而那恰恰是上面为了拿到进程组而
`set -m` 打开的东西。于是买下 pgid 的那两行，悄悄把**启动者的** stdin 交给了子进程，
对一个交互式调用方来说那就是终端。mpv 于是保持 `input-terminal` 打开，读的是与启动者同一个 tty：
在 `uting` 下两个进程逐字节抢输入，而 mpv 自己的默认键位占着 `[`/`]`（播放**速度**）、`9`/`0`、
`Space`、`q`、`s`、`m` —— 与 TUI 绑的是同一批键。谁的 `read()` 赢了字节就归谁，于是按键
"时灵时不灵"，mpv 赢的时候 `[`/`]` 还会悄悄改变流的速度。用 `lsof` 在 pty 下验证过：
修之前，包装层与 mpv 都持有 `/dev/ttysNNN`，mpv 答 `input-terminal=true`；修之后两者都持有
`/dev/null`，答 `false`。`</dev/null` 加在**启动**上而不是只加进 mpv 的 flag，是因为启动是每个
detached 播放器都必经的那一个点，它覆盖整棵子树 —— 探测用的 `yt-dlp`/`curl` 与任何晚到的重试
mpv 都包含在内。mpv 那个 flag 也保留：它在"读得到 mpv"的地方陈述同一个事实，并且能活过
以后有人用别的方式启动子进程。

```
   detach_play()                     # shell/ut-play
      ensure_state_dir()             # 0700 的 STATE_DIR + players/（socket 是一条控制通道）
      id = new_player_id()           # mktemp token；启动前 socket 路径就已知
      set -m                         # monitor 模式：被后台化的作业成为组长
      YT_IPC_SOCK=… YT_DETACHED=1 YT_PLAYER_ID=<id> \
        nohup bash SELF -f MODE --engine NAME [--volume N] [-S SORT] -- HANDLE \
            </dev/null >mpv-<id>.log 2>&1 &     # pgid == pid（$!）；stdin 见上文
      set +m ; disown
      players/<id>.json ← {id,pid,url,mode,format:null,started_at,log,sock,title:null,volume}
      rm PLAYERS_DIR/<id>            # 丢掉光秃秃的 mktemp token；状态住在 <id>.json 里
                                     # title/format 由子进程回填（见下）

   ┌─ 进程组  pgid = 57678（播放器 <id>）───────────────────────┐
   │  57678  bash ut-play -f audio --engine yt HANDLE（组长）    │
   │    ├─ <engine>-resolve（yt-dlp + curl，短命）               │
   │    └─ 57712  mpv --no-ytdl --input-ipc-server=…sock         │ ← 改挂到 init
   └──────────────────────────────────────────────────────────────┘   但 pgid 不变

   stop_group(pgid):  先 kill -TERM pgid（**只**发给组长 —— §9.5 事实 2）；随后每 0.2s 一拍：
                      kill -TERM pgid + kill -INT -pgid；再升级到 kill -KILL -pgid
   group_alive(pgid): pgrep -g pgid 至少有一个成员
```

soft ref：`shell/ut-play` 的 `detach_play()` / `stop_group()` / `group_alive()` /
`ensure_state_dir()` / `new_player_id()`。

**`YT_DETACHED=1`（子进程为什么必须知道自己是 detached 的）。** 一个 detached 播放器没有终端，
所以永远没人读 mpv 的状态行 —— 但 mpv 照写不误，写进 `mpv-<id>.log`：在一条 24/7 的直播上
实测 ~2.4 MB/小时，也就是说，恰恰是 `-d` 存在的意义所在的那种长命播放器，会在 `$TMPDIR` 里
无界增长。所以子进程的 `run_mpv` 追加 `--no-term-osd-bar --msg-level=all=error`
（放在模式选项之后，于是它们赢），并跳过 stderr 噪声过滤。修后实测：日志 59 字节，12 秒内
零增长，而真实失败仍然记得下（`[ytdl_hook] ERROR: …`）。`-S` 与 `--engine` 像 `--volume`
一样转发给子进程 —— `-S` 曾经在 detached 路径上被悄悄丢掉 —— 句柄跟在 `--` 之后传。

**`title` 与 `format` 由**子进程**回填，而不是由一个后台兄弟进程（`patch_player_meta`）。**
父进程必须在毫秒级返回，因此它两个字段都不可能知道；子进程从它本来就要取的解析信封里学到这两样，
然后自己去补自己的记录。它像老的更新器那样自我保护：那段 jq 程序只有在记录的 `pid` 仍是本进程时
才输出内容，所以一次落在解析窗口内的 `--stop` 会赢，且永远不会被覆盖回去。它用一个有界轮询
（50 × 0.1s）等那条记录，而不是固定 sleep，因为 `detach_play` 是在启动子进程**之后**才写
`players/<id>.json`，而一次快解析可能先到；正常情况下这只花一次 `stat`。

> **那个已退役的后台更新器当年的代价 —— 记下来是因为这个坑是通用的。** 它是每次 detached
> 播放额外一整个 `yt-dlp --print "%(title)s"`，作为后台作业跑 —— 而后台作业会继承 shell 的
> stdout，于是一个**捕获**我们输出的调用方（`out=$(ut-play -d -j …)`，正是 `uting` 干的事）
> 会一直阻塞到那个管道的**每一个**写端都关闭为止，而不是到我们退出为止。在它的 fd 被重定向
> 之前，"瞬时"的 detach 实测是**捕获下 1.67s、不捕获 0.04s**。信封喂出来的回填根本没有后台
> 作业，所以这个坑在这里不会重现 —— 但任何未来写在动词里、且调用方可能捕获的 `… &`，
> 都必须自己关掉 fd。

### 9.2 状态机（多播放器）

```
   多个 detached 播放器共存，各有自己的 id/pgid/socket/state/log。第二个 -d **不会**被拒 ——
   它启动一个独立的播放器。生命周期动词负责挑目标。

        ┌───────────────── （没有活着的播放器）◄────────────────┐
        │              ut-play -d -- HANDLE   （多少次都行）      │
        │                             ▼                          │
        │                   ┌────────────────────┐               │
        │  --status → 列出  │ N 个活播放器        │ --set-volume N│
        │  players[] ───────│  players/<id>.json  │  [--id ID] ───┤（经 IPC 改实时音量）
        │                   └─────────┬──────────┘               │
        │   --stop --id ID  │ 停那一个            │  --stop --all │ 停掉每一个
        │   （只有 1 个活着 ▼（2+ 活着且没给 --id ▼               │
        │     时 --id 可省） resolve_target       → {ambiguous,   │
        └──── 删掉它的 state/sock/log              players:[...]} 退 4）

   • 一个播放器消费一条**队列**（§9.5）：启动时 --queue，之后 --enqueue 与 --next。
     单个句柄就是一条长度为一的队列，所以 `queue` 永不为 null，上面这张状态机也不变 ——
     一个播放器、一份生命周期，不管它播多少首。
   • --status **永远**退 0。--stop 除了目标歧义（2+ 活着且没给 --id，退 4）之外一律退 0 ——
     见下一条。其余情况幂等：一个在轮询的 agent 绝不能把"非歧义的非零退出"读成失败。
     每一次生命周期调用都会回收进程组已经消失的播放器。
   • --set-volume / 歧义的 --stop 退 4（没生效；-j 的 reason 说明为什么）。
   • **自己死掉**的播放器留下一块墓碑：--status 在 failed[] 里报它一次，而不是干脆变空（见下）。
   • 状态：${TMPDIR:-/tmp}/uting-$(id -u)/players/<id>.json（+ mpv-<id>.sock、mpv-<id>.log、
           queue-<id>.json），墓碑在 players/dead/<id>.json —— 其中失败的**队列曲目**是
           <id>-q<pos>.json，形状相同（§9.5）
```

**生命周期的另一半：没人叫它死、它自己死了（`failed[]`）。** `launch → status → stop` 描述的是
调用方驱动的每一条路径。它对"调用方**不**驱动的那条路径"什么也没说，而那条路径当时是静默的：
`-d -j` 在 yt-dlp 解析出任何东西之前就返回 `{"status":"started"}` 加退出 0，所以一个私享或已删除
的视频是在**子进程内部**失败的；`reap_dead_players` 随后删掉记录与日志，`--status` 变空 ——
与一首正常播完的曲目逐字节一致。原因只存在于一份刚被删掉的日志里。

两块东西把它补上，而这个拆法是被"每个进程知道什么"逼出来的：

- **子进程写自己的墓志铭**（`detached_epitaph`）。只有子进程知道 `rc`，而 `rc` 恰恰是日志显示
  不了的东西："播得好好的"与"以一种我们认不出的方式失败了"，对 `classify_playback_error`
  来说是同一段文本（都是 `unknown`）。子进程的 stdout **就是**那份日志，所以它追加一行 ——
  `{"yt_event":"exit","rc":2,"reason":"unavailable","ended_at":"…"}` —— `reason` 取自共享的
  那份分类（AS-BUILT-contract.md §3），由它拿到的 `YT_DETACHED_LOG` 的尾部分类得出。
  `rc` 为 0 或 130 时什么也不写。
- **回收器把它变成墓碑**（`record_player_death`），在记录与日志都还存在的那**一个**瞬间读走，
  写成 `players/dead/<id>.json`。

那些边界是契约，不是礼貌 —— 它们正是让这东西保持为一份**错误记录**、而不是一份收听历史的原因：
**只记失败**（正常播完不写墓志铭；一次 `--stop` 会在子进程来得及写之前就杀掉整个进程组 ——
同一条规矩的另一面）、**最多 8 条**、**不超过一小时**，而且它住在状态目录里，随目录一起死。
没有墓志铭就没有墓碑：一份被截断的日志、或一次 `kill -9`，报的是沉默，而不是一次被推断出来的死亡。

> **这条边界活过了范围变更，也因此更要紧。** 收听历史曾经是 `ROADMAP.md` §0 的 non-goal，
> 那时"`failed[]` 不是历史"很容易说。自 ROADMAP D14 起它成了一个**功能**，并且已经落地（§9.6）
> —— 于是这条规矩从"缺席"规矩变成了一条**分离**规矩，而且两边都是真实文件：历史是持久的、
> 用户级的、每一首都记，住在 `$UT_STATE_DIR`；`failed[]` 仍是易失的、有界的、只记失败，
> 住在 `$TMPDIR`。两者由同一个子进程在同一瞬间写下，不是重复。把这个数组长成历史功能，
> 等于把一份面向用户的记录放进一个重启即清的目录。

**`-d` 拒绝 `-f ascii|viz`。** 一个 detached 进程没有控制终端，所以终端渲染类的模式无处可画；
这道守卫如今在解析期就执行（`die`），而不是默默启动一个往自己日志里涂转义序列的播放器。
`audio` 是常态；`video`/`fast` 被接受，因为它们的 mpv 窗口是一个不需要这个终端的 GUI 面。
`uting` 用同一张清单校验 `-f`。

**`-d -j` 的信封带着 `sock` 与 `log`。** 它们本来就在状态文件里，而信封里没有它们时，客户端
只能从播放器**私有的**状态布局去**重建** socket 路径 —— `uting` 当年就是这么干的，在第二个脚本里
硬编码 `$TMPDIR/uting-$(id -u)/mpv-<id>.sock`，一旦播放器搬了状态目录就会静默失效（§9.3）。
（schema → AS-BUILT-contract.md §3。）

### 9.3 运行时 IPC 控制（`--set-volume`、`--pause`/`--resume`、`--seek`/`--seek-to`）

`--volume N` 只设 mpv 的*起始*音量；五个运行时动词改的是一个**正在跑**的 detached 播放器，
不需要 kill+重启。它们跨**多个并发**播放器工作，每个独立寻址，并共享同一套形状：解析目标
（或退 4）→ 经该播放器的 socket 发一条命令 → 再一次往返，**读回**信封要报的那个属性
（`ipc_command` → `do_set_volume` / `do_playback_verb`；信封在 AS-BUILT-contract.md §3，
那条曾经把四个播控动词挡在门外、如今已作废的判据在 ARCHITECTURE.md §26）。

**为什么并发的 detached 播放器是可能的（mpv 不构成障碍）。** mpv 默认非独占
（`--audio-exclusive=no`）；默认的 coreaudio / PulseAudio / PipeWire 输出是共享的，
由操作系统混音，而每个实例的 `volume` 是独立的**进程内软件音量**。关键在于 mpv 的 IPC 是
**每实例**的：`--input-ipc-server=<sock>` 是一个进程级 flag，所以让每个 mpv 指向自己的 socket
路径，就白得 N 条互相独立的控制通道。于是多播放器完全是 **yt 这一层**的事 —— mpv 不需要任何
特殊模式。（这也是为什么老的"第二个 `-d` 除非给 `--replace` 否则拒绝"的单槽守卫，
连同 `--replace` 一起被丢掉了：第二个 `-d` 就是再起一个播放器；`--stop --all` 让一切安静；
换一首是 `--stop --id X` 加一个新的 `-d`。）

**数据流（一次 `--set-volume` 往返）。**

```
   LLM 调用方                   ut-play                              mpv #<id>
      |-- --set-volume 70 --id <id> --->|                                    |
      |                                 |-- resolve_target <id>（顺手回收死的）|
      |                                 |-- sock = players/<id>.json.sock    |
      |                                 |-- [[ -S sock ]]（确认它真是 socket）|
      |                                 |-- {"command":["set_property","volume",70],"request_id":1}
      |                                 |     | nc -U -w1 sock ------------->|
      |                                 |<-- {"request_id":1,"error":"success"} ---|
      |                                 |-- 原子 temp+mv 把 .volume=70 补进去 |
      |<-- {"status":"ok","id":<id>,"volume":70}（退 0）---------------------|
         一个进程，不是两个：把门的包装层已经没有了（ARCHITECTURE.md §4）
```

**每播放器一个文件**（`players/<id>.json` 的一个目录）是刻意选的，而不是一个共享的大 JSON 数组：
写入按文件保持原子（temp 文件 + `mv` 的老套路），播放器**之间**没有读-改-写竞态，回收一个死掉的
播放器就是 `rm <id>.json`（外加它的 `.sock`/`.log`）。socket 与日志路径都由 id 推导，
所以没有别的地方需要存它们。在**单个**播放器的文件**内部**还剩一处 RMW 风险：子进程的元数据回填
（`patch_player_meta`）与一次 `--set-volume` 可能同时 temp+mv 补同一份 `<id>.json`，
后落地的那个 `mv` 会静默覆盖掉另一个的字段。一把按 id 的 `mkdir` 锁
（`lock_player_state`/`unlock_player_state`，作用在 `STATE_DIR/lock-<id>`；`mkdir` 在 POSIX 上
是原子的，而且不需要 `flock` 这个二进制 —— 原生 macOS 没有它）把这两个写者串起来。
它有界自旋约 5s 之后**不带锁**继续，所以一个崩掉的持锁者卡不死调用方 —— 与锁存在之前那些补丁
一直承担的是同一种尽力而为的风险。`patch_player_meta` **另外**还做 pid 守卫（只在文件的 `.pid`
仍等于自己的 pid 时才补），于是解析窗口内的一次 `--stop` 会赢，它的回收永远不会被一次迟到的
标题写入覆盖掉。

**IPC socket 是 `-d` 契约的一个公开部分（而且 `volume` 是活读的）。** `uting` 把每拍一次的
**读**（进度 + 暂停态）和按住不放的音量键直接走 socket，而不是每次按键 fork 一个动词：
它的 Now-Playing 视图每秒刷一次，否则每一拍都要付一条进程链。它的暂停与 seek 键**确实**搬去了
动词 —— 一次按键一次调用付得起，一拍一次付不起 —— 而 ARCHITECTURE.md §26 记着划出这条线的
那次实测。这是对 D8 的一次刻意例外，所以 socket 路径是在 `-d -j` 的信封里**交给客户端**的
（`sock`），而不是从状态目录布局里重建出来；并且是这份文档 —— 而不是某个实现细节 ——
批准了那条 JSON-RPC 通道。对 `--status` 的后果：状态文件里的 `volume` 只知道启动时的 `--volume`
与 `--set-volume`，所以一个经 socket 改音量的客户端会让它说谎。因此 `--status` 报的是**活的**
音量，取不到时才回退到记录值。它对 `nc` 是软门，从而保住 `--status` "只依赖 jq" 的性质
（AS-BUILT-contract.md §4）。已验证：在 `uting` 里按两下 `0`，把一个以 `--volume 0` 启动的播放器
推到 `10`，`--status` 报的就是 `10`（它从前会永远报 `0`）。

**四个属性，一次往返（`live_props` / `read_player_live`）。** 同样的论证覆盖 `pause`、
`time-pos` 与 `duration`，而且更糟：状态文件从来就没存过它们，所以 socket 是它们**唯一**存在的
地方，而当时只有 `uting` 在读。它们如今是播放器记录的一部分（AS-BUILT-contract.md §3），
由 `live_props(sock, prop…)` 读出 —— 它把整份属性清单顺着**一条**连接发下去，吐出
`<request_id><US><value>` 行 —— 再由 `read_player_live` 做关联，`--status` 的两种输出模式共用它，
于是归一化只存在一份。三条规矩是承重的：

- **按 `request_id` 关联，绝不按行序** —— mpv 会把异步事件插进每个客户端的流里
  （`do_set_volume` 遵守的是同一条）。
- **`head -n <count>` 才是关掉管道的那个东西**，*针对一个把连接一直挂着的对端*。mpv 对每条命令
  恰好答一次，而 `jq` 已经把没有 id 的事件丢掉了，所以最后一行预期输出就是 `head` 退出的地方 ——
  它 SIGPIPE 掉 `nc`，读就结束了。
  **更正（2026-08-24），记下来而不是悄悄删掉**：这一行长期挂着的 **1.11s → 0.03s**，
  是对着一个*脚本化的*对端量的，那个对端的空闲计时器把 `nc -w1` 的钟耗完了。那个替身随
  "不许有替身"的规矩一起被删了，而对着**真 mpv**，同一次读**用 `head` 或用光秃秃的 `cat` 都是
  0.04s**。所以这道守卫是对"会那样表现的对端"的防御，不是一次量出来的收益，
  `tests/playback.sh` 也**刻意不为它写检查** —— 没有一条能变红。**一次测量的耐久度，
  只等于它当初对着的那个东西的耐久度。** 调用方自己 break 掉读循环也**达不到**同样效果 ——
  没有人再写一次，就没人会注意到读者已经走了。
- **管道外面要有 `|| true`**，否则 `set -euo pipefail` 会把一次 `nc` 超时变成在赋值处中止。

`null` 与 `false` 全程分开：`paused:false` 意思是"在播"，`paused:null` 意思是"这个问题问不出去"
（没有 `nc`、socket 死了、没人答）。在那里报 `false` 就是一次**捏造的读数**，
而活读存在的意义正是终结这种失败模式。一个有用的副作用：`paused != null` 如今是一个刚 detach
的播放器诚实的就绪探测 —— 而 `volume` 在 mpv 还没开始监听时就能从状态文件里答出来。

**句柄是一个单调 token，不是 pid（D9）。** `new_player_id` 用
`basename "$(mktemp "$PLAYERS_DIR/XXXXXX")"` 铸出句柄 —— 原子且不撞。这一下解决两个问题：
(1) socket 必须在**启动时**就经 `YT_IPC_SOCK` 命名，但子进程的 pid 要到启动**之后**的 `$!`
才知道 —— token 打破了这个先有鸡还是先有蛋；(2) 它把 pid 复用从一个活生生的危险降级成一个
**很窄的残余风险**：存活检查针对的是 `<id>.json` 里存着的那个 pid，而记录在进程组消失的那一刻
就被回收，所以窗口只剩"一条已被回收、但尚未被扫到的记录，且它的 pid 已经被某个**进程组组长**
回收再用"。这不是完全免疫 —— `group_alive` 仍然是 `pgrep -g <存着的 pid>` —— 在那个窗口里一次
`--stop` 会给一个无关的组发信号。真正堵上它需要第二个不变量（进程启动时间，或者去探播放器
自己的 socket）；现状是**接受**，不是**解决**。`mktemp` 会留下一个**光秃秃的** `<id>` 文件来占住
这个 id；`<id>.json` 写完之后那个 token 被 `rm` 掉 —— 回收用的 `*.json` glob 永远不会碰它，
否则每次启动都要漏一个文件。

**`do_set_volume` 的机制。** 校验 `0-100`（与启动的 `--volume` 对称）→ `resolve_target` →
`[[ -S "$sock" ]]`（测的是"它是不是 socket"，而不只是"存不存在"，于是一个被 `SIGKILL` 的 mpv
留下的陈旧 socket 报 `ipc_failed` 而不是挂住）→ 一次性 `nc` → 检查 `.error=="success"` →
原子 `temp`+`mv` 把 `.volume` 补上（与 `patch_player_meta` 同一套 temp+mv 套路，
由按 id 的 `mkdir` 锁与它串行化）→ `{status:"ok",id,volume}`；任何一步没中 → 退 4。

**`request_id` 关联（为什么光靠 `head -1` 是错的）。** mpv 会把**异步事件**复用给每一个连着的
客户端，与命令回复交织在一起（见 mpv 的 `ipc.rst`），所以对 socket 输出光来一个 `head -1`
可能抓到的是一个事件而不是那条 ack。做法是给命令打上 `"request_id":1`，再用
`jq -c 'select(.request_id==1)' | head -1` 挑出回复。这条管道后面需要跟一个 `|| true`：
在 `set -euo pipefail` 下，一次 `nc` 超时 / `SIGPIPE` 会让管道非零，从而在**赋值处**中止脚本
（与探测/解析路径同一套守卫写法）。

**`resolve_target` 的返回值纪律。** 它是把"一次请求"映射到"一个播放器"的唯一地方
（`--set-volume` 与 `--stop` 共用）。它完全靠**出参全局量**沟通，自己一个字都不打印：
成功时设 `RESOLVED_ID` 并返回 0；失败时设 `RESOLVE_ERR`（`not_playing` | `ambiguous`）——
歧义时再加 `RESOLVE_PLAYERS_JSON`（候选清单）—— 并返回非零。调用方以
`if ! resolve_target "$id"; then …; fi` 的形式用它，再自己从那些全局量把错误渲染出来
（于是 `--stop` 可以把 `not_playing` 当作幂等成功，而 `--set-volume` 把它当作退 4 ——
同一个 fd1 不能被预先绑死成一种形状）。用设全局量而不是 echo，理由与 `reap_dead_players` 一样：
bash 3.2 的数组（`RESOLVE_PLAYERS_JSON` 的候选）过不了 `$(...)` 捕获这一关，
而调用方也不能把结果吞进一个子 shell 里。选择规则：给了 `--id` → 就那个播放器（若活着），
否则 `not_playing`；没给 `--id` 且恰好 1 个 → 就它（让常见情形零摩擦）；0 个 → `not_playing`；
2 个以上 → `ambiguous`。每次调用都先跑 `reap_dead_players`，于是进程组已经没了的播放器
在选择之前就被清掉。

**用 `nc` 而不是 `socat`（不加新依赖）。** 已有的 mpv 包装器多用
`socat - UNIX-CONNECT:$sock`（干净的 EOF，没有 `-w` 的延迟地板），但 macOS 上没有 socat。
我们留在原生 BSD 的 `nc -U -w1` 上，用 `request_id` 过滤买回健壮性 —— 比引入一个工具链其余部分
都不需要的依赖便宜。延迟是地板不是天花板（约 ≤1s/次）：mpv 把 socket 一直开着，所以回复之后
若没有后续事件，`nc` 可能一直坐到 `-w1` —— 对人驱动的调节没问题，对紧循环不行。
Linux 的 `nc -U` 行为不同，属于已接受的已知缺口（ARCHITECTURE.md §26）。`nc` 是在分派处
惰性把门的（`require_cmd nc`），绝不进全局 `require_deps`，于是一次光秃秃的搜索永远不必要求它
（AS-BUILT-contract.md §4）。

**参考（mpv IPC）。**

- mpv `DOCS/man/ipc.rst`（规范性）—— `request_id` 是被认可的回复关联机制；事件与回复交织
  （这就是为什么光靠 `head -1` 是错的）。
- mpv `DOCS/man/ao.rst` —— 默认输出是共享的（并发实例会混音）；`--audio-exclusive` 默认 `no`。
- purarue/mpv-sockets、wis/mpvSockets —— 最接近的前人工作：每实例一个 IPC socket
  （借用了每实例 socket 命名 + jq 抽取）。
- lwilletts/mpvc —— `set_volume` 命令形状的参考；它的回复解析（grep `"success"`、没有
  `request_id`）**刻意不抄**。

### 9.4 持久状态层（`ut-playlist`）—— 以及它与 `players/` 之间那条线

§9.1–§9.3 描述的是**本来就该死**的状态：一条播放器记录住在
`${TMPDIR:-/tmp}/uting-$(id -u)`，进程组一走它就被回收，整个目录重启即清。这对一个**正在跑的
进程**是正确的，对一份用户攒了半年的清单则是致命的。所以第一个收听功能（ROADMAP P4）
从第二个、独立的存储开始：

```
   $UT_STATE_DIR/                      默认 ${XDG_STATE_HOME:-~/.local/state}/uting
     playlists/<name>.json             一个播放列表一个文件，原子 temp+mv
     playlists/.lock-<name>/           mkdir 锁，与 lock_player_state 同一个原语
```

**一条记录是一次调用，不是一个引用。** 一个条目是 `{engine, id, url, title, duration,
added_at}` —— 搜索结果的一个子集，外加从信封里折进来的 `engine`，因为 `engine` + `url`
恰好就是 `ut-play --engine E -- URL` 的那两个参数。只存一个光秃秃的 URL 等于把路由这个事实
扔掉，逼后面某个面去猜它 —— 而自 ROADMAP D12 起，那是一个硬性的用法错误，
不再是从前那种静默的错标。`channel`、`view_count`、`live_status` 刻意不存：播放用不着它们，
而它们会过期成错误答案。schema → AS-BUILT-contract.md §3。

**为什么是第七个命令，而不是在已有东西上加个 flag。** 这个存储与播放器只共享锁这一个原语，
与引擎则毫无共享。放进 `ut-play` 会给播放器一份跨播放的状态、以及第二种要它拥有的文件；
放进 `uting` 则成了"由渲染器写的状态" —— 正确性往**上**加、加进 UI，于是两个面里只有一个继承它。
作为自己的动词，它对 agent 是一次调用，对 TUI 是同一次调用。

**与播放器那把锁的三处不同，全都由"持久"逼出来。** `lock_player_state` 超时后**不带锁**继续，
因为它写的是尽力而为的字段补丁。这一把：(a) 超时即**失败** —— 退 4、`locked` —— 因为这里一次
不带锁的写，可能把用户刚加进去的那首弄丢；(b) **抢**掉超过一分钟的锁，因为 EXIT trap 在每一种
正常死法（包括 `die`）里都会释放它，所以一个陈旧的锁目录意味着一次 SIGKILL，
而"一个再也写不进去的播放列表"比"一次没人见过的撕裂写"更糟；(c) 由一条**被看着变红过**的
检查来证明 —— 把锁掏空之后，八个并发 `--add` 只剩**一个**条目（实测），
这正是这套模式要挡住的读-改-写竞态。

**名字就是文件名。** 不做 slug：slug 会让"屏幕上的名字"与"磁盘上的名字"变成两个事实，
接着其中一个就是错的。代价是一个校验器（不许 `/`、不许控制字符、不许以 `.` 开头、≤64 字符）
和一条被接受的限制 —— 在大小写不敏感的文件系统上（macOS 的默认），`Rock` 与 `rock`
是同一个播放列表。这一条是**记下来**而不是归一化掉：bash 3.2 没有 `${var,,}`，而 `tr` 对
UTF-8 是错的，所以在这里写任何归一化，对最需要它的那些名字恰恰是撒谎。

**TUI 拿它做什么、不做什么。** `uting` 长出两个键 —— `a` 把焦点行加进去，`b` 把一个播放列表
当作行源打开 —— 且**自己什么也不存**：两者都带着 JSON 外壳调用 `ut-playlist`，
与 `play_selected` 外壳调用 `ut-play`是同一种方式。交给 `--add` 的条目是按 url 从**搜索信封**里
裁出来的，不是从行数组重建的：信封带着引擎标签和精确的字段拼写，于是 TUI 从头到尾不认识
条目记录 —— 而且行数组是过滤且重排过的，对它的下标并不是对 `.results` 的下标。

行记录长出了第七个字段 `engine`，而这正是一个混合播放列表能被播放的原因：
`play_selected` 传的是**那一行的**引擎，而会话级引擎会把一条 Bilibili URL 送去 `yt-resolve`。
因为播放列表信封产出的是与搜索**同样**的七字段行，列表视图、过滤与翻页一个字都不用改 ——
唯一需要认识这个新行源的，是三个会**重新取数**的键（`m`、`o`、`e`，而播放列表没有查询），
以及 `Esc`，它是从里面出来的路。

**而出来靠的就是 `Esc`。** 一个存储会**替换**屏幕上的行，所以没有返回键时，出口只剩 `n`
（重打一条查询）与 `q` —— 一扇单向门，`h` 打开的是同一扇（§9.6）。存储替换掉的一切都是本地状态
（信封、由它建出来的行、标签、光标位置），所以打开者把它们收起来、`Esc` 再还原：
不重新取数 —— 重新取数会花一次网络往返去重建手里本来就有的行，而且可能悄悄还给用户一组
**不同**的结果。这份暂存只在"行还是搜索的行"时才拿，所以 `h` 然后 `b` 然后 `Esc` 落回的是搜索
而不是历史；而这个键只在存储正显示在屏幕上时才出现在提示里 —— `e`、`a`/`b`、`h` 已经遵守的
是同一条规矩。

**这里没有的东西：队列。** 一条队列是"一个正在被消费的播放列表"，它归播放器，
住在播放器的运行时状态里。**一条活过重启的队列就是一个播放列表** —— 正是这条判断把两个存储
分开。它建在 §9.5。

### 9.5 队列 —— 一个正在被消费的播放列表（`--queue`、`--enqueue`、`--next`）

一个 detached 播放器播的是一条**队列**。单个句柄就是一条长度为一的队列，于是只有一条代码路径
而不是两条：每一次 `-d` 启动都在 fork 之前写下一份队列文件，正是这一点让 `--enqueue`、`--next`
与 `--status` 可以对**任何**播放器寻址，而不需要一个"这个有没有队列"的分支；也正是这一点让
`--status` 的 `queue` 键在一个活播放器上永不为 null。

```
   ${TMPDIR:-/tmp}/uting-$(id -u)/queue-<id>.json    {schema:1, pos, items:[{engine,url,…}]}
                                  lock-queue-<id>/   它自己的 mkdir 锁
```

**不放在 `players/` 下面，而这不是归档偏好。** `players/*.json` **就是**播放器记录的命名空间：
`reap_dead_players` 走的是那个 glob，一个停在那儿的 `<id>.queue.json` 会被当作一条 `.id` 为空的
记录读到 —— 然后被删掉。队列改为坐在 socket 与日志旁边，而 `rm_player_files` 在**一个**函数里
把这三样（外加两个锁目录）一起删掉，因为有三个调用点负责给一个播放器收尾 —— 回收器与两条
`--stop` 路径 —— 一个只加进其中两个的文件，在第三个那里就是泄漏。

**队列为什么归播放器，以及先被算过账的两个家。** 判据只有一句：
**一条活过重启的队列就是一个播放列表**（§9.4）。队列活不过，所以它按定义就是运行时状态，
住在 socket 与日志旁边而不是持久存储里。两条被否掉的模型记在这里，因为它们都合理到会被再次提出：

- **播放器去读一份外部队列文件。** 它让 `players/` 的单一所有者不变量（§9.2）纹丝不动，
  还白得 agent 面 —— 反正队列都会搭 `--status` 的信封出去。它栽在所有权上：播放器要在播到一半时
  去读一份**它不拥有**的文件，而"谁可以写、什么时候写"就变成一条这套套件必须先发明、
  然后还要一直守住的规矩。
- **第七个命令 `ut-queue`。** 它符合这套套件惯常的形状 —— 一个能力就是一个文件 ——
  而且播放器一行都不用改。它从另一侧栽在同一个不变量上：那样就有**两个**进程想驱动同一个播放器，
  而"`players/` 恰好一个所有者"在这里是硬的（§9.2）。那条路要先回答"谁回收、谁写状态文件"
  才能开工，而回答它就意味着把生命周期搬出播放器。

**两把锁，绝不嵌套。** 队列不共用 `lock_player_state`：记录与队列的更新频率差一个数量级
（每首一次标题回填，对每首一次推进**加**每一次 `--enqueue`），一把锁管两样会让各自等对方的钟。
硬规矩是**没有任何一条路径同时持有两把** —— 取一把、写、放掉，再取另一把。一把锁最多让你卡住；
两把锁能死锁，而在这种有界自旋下，症状甚至不是挂起，而是两次五秒停顿之后一次**静默的**
不带锁写入。

**JIT 解析，一次一首。** 一个流 URL 几小时就过期，所以一条预先全解析的队列播到一半就会 403；
每个条目都在轮到它时才解析。代价是两首之间的空档，而这笔账是有意付的。两个后果是契约性的
（AS-BUILT-contract.md §3）：一次解析失败**推进**队列而不是杀掉播放器 —— 否则上游一分钟不顺
就被焊死在播放器的寿命上 —— 而失败的那一首在 `failed[]` 里拿到自己的墓碑，键是 `<id>-q<pos>`。
**推进发生在墓碑写下之前**：当队列耗尽时，死的是**播放器**，那条记录归父进程、来自日志里的
墓志铭。反过来写的话，一次失败会被记两遍 —— 实测过，一个坏句柄同时留下 `<id>` 与 `<id>-q0`。

**记录跟着曲目走。** `patch_player_meta` 除了 `title` 与 `format` 之外也补 `url`，
所以十分钟后取的一次 `--status` 描述的是**正在播的**，而不是**当初启动的**。

**三条 bash 3.2 的事实塑造了子进程的循环，每一条都是量出来的，不是推出来的。**

1. **有前台子进程在跑时，trap 不会被派发。** 给一个 `sleep 5` 发 SIGUSR1，处理器五秒之后才跑，
   而且仍然返回 0；`cmd & wait "$!"` 则在一秒内进入处理器、`wait` 返回 158。所以子进程把 mpv
   放到**后台**再 `wait` —— 否则 `--next` 的意思就成了"等这首播完再跳过一首"，那不叫跳过。
2. **异步命令不能 trap SIGINT —— 只在没有作业控制时如此，而这个子进程不是那种情况。**
   通常那条规则的说法（bash 以 SIGINT 被设为 `SIG_IGN` 的方式启动异步命令，而一个进入时就被
   忽略的信号永远 trap 不到）是这份文档相信了两个版本的东西，它只对一半：bash 只在**作业控制
   关闭**时施加那个 `SIG_IGN`，而 `detach_play` 是在 `set -m` 下启动的。在 3.2.57 上实测，
   同一个子进程开与不开 monitor 模式：**开**的时候，`trap … INT` 会触发、`wait` 返回 130；
   **不开**的时候，一个发给进程组的 INT 根本到不了子进程。所以 detached 子进程的 INT 是一个
   普通的、可 trap 的信号 —— 而一个**没被 trap** 的它就是一次朴素的 kill。

   这个区别在子进程"临死前有话要说"之前是看不见的。一旦它要写一行收听记录（§9.6），
   它就以**数据丢失**的形式冒出来了：`--stop` 先给组长发 TERM、紧接着给整个组发 INT，
   而在 3.2 上第二个信号会**在两个处理器之间**把进程带走，第一个处理器一行都还没跑。
   可复现地实测到：两个播放器的一次 `--stop --all`，2 行里写成 0 行，
   而任一信号**单独**发时每次都到得了处理器。两处改动，且两处都是承重而非防御性的：
   子进程 trap `TERM INT`（同一个处理器，反正 `stopped` 是终态），并且 `stop_group` 的**第一拍
   只发 TERM** —— 到 INT 加入之前那 0.2s，就是子进程记录"发生了什么"的全部机会。
   mpv 不需要那一拍，因为子进程自己的处理器会杀掉它。

   升级过程仍然在每 0.2s 一拍上**重复两个信号**，因为这个组不是一个固定集合：两首之间的引擎调用
   会生出一个新的 yt-dlp、然后它的匿名重试、然后探测用的 curl，而在第一个信号之后一毫秒才起来的
   那个从没见过它。只要这种掉队者还在跑，子进程自己的 trap 也跑不了（又是事实 1），
   所以单单一个迟到的进程就足以让一次停止把整个升级过程等完。改后实测：三个播放器的
   `--stop --all` 用 956 ms —— 与之前同样是每播放器约 0.3s，而每一行都写下来了。
3. **两个信号可以同时挂起，而顺序不由我们挑。** 两首之间的引擎调用是一个前台命令，
   所以在它期间送达的 `--next` 要等，排在它后面到的 `--stop` 也要等；解析一返回，
   bash 就把两个处理器都跑了。一个被允许落在 `stopped` 之后的 `next`，会把一个已经被通知去死的
   播放器的循环重新启动 —— 停止耗时从 0.4s 变成 3.5s，3/3 复现。所以在 `child_signal` 里
   **`stopped` 是终态**：一旦置上，任何后来的信号都不许把它降级。

**一首曲目为什么结束，来自 `CHILD_REASON`，绝不来自 mpv 的退出码。** mpv 0.41 对"因信号退出"
一律答 4 —— 一个码同时覆盖"`--next` 杀的"、"`--stop` 杀的"和"用户杀的"。处理器在杀 mpv **之前**
就把 reason 设好，于是墓志铭描述的是发生过的事，而不是一次猜测。哨兵文件的方案考虑过并被否决：
那是又一把锁，而且会让死亡记录多出一种说谎的方式。

**两首之间的空档是一次 JIT 解析，而它是量出来的、不是拍出来的。** 中位 **4.3 s**、
p90 **5.7 s**、区间 3.2–5.8（n=12）—— 而写下来的预算是"大约 3 秒"，差了 1.4 倍，
这也正是为什么"一个没量过的大约 3 秒"就是下一次时序事故。这次测量定义在**耳朵**上而不是代码里：
从旧曲目报出的最后一个 `position`，到新曲目报出的第一个 `position`，读的是一个真播放器的
`--status`，队列是 yt 与 bili 交替的 5 项，三轮，每首都 seek 到 `duration-3` 让它自己结束
（`--next` 是另一条路径，不是这里量的东西）。**空档的 92% 是引擎往返**（解析中位 3.8 s），
所以唯一还能砍的地方是预取 —— 循环里没有别的东西大到值得管。方向上的不对称是真的，
这也是为什么混合队列才是唯一诚实的夹具：**→bili 3.4 s，→yt 5.3 s**，因为 `yt-resolve`
要读浏览器 cookie，还可能花掉一次 PO-token 探测与一次匿名重试，而 `bili-resolve` 只要一次
yt-dlp 调用。**因此预取不进 v1**，依据是那条在数字出现之前就写下、之后被遵守的触发条件：
只有当 p90 越过 **8 s** 时才付这笔账，因为在第 N 首期间解析第 N+1 首意味着第二个后台作业
加上一份会过期的缓存（流 URL 几小时就死）。这个数字挂在活站点上；上游一变就要重测，
而触发条件不动。

**N 次抽取，而不是一次。** JIT 解析把一次播放变成 N 次"yt-dlp 可能正好这一分钟不顺"的机会，
而反复抽取本身也可能招来限流。这就是把队列留在播放器里的真实代价，
它靠**在失败的曲目上推进**而不是重试来吸收 —— 一次重试就是上面那个空档，翻倍。

**`--next` 在父进程里移动位置，然后才发信号。** 于是信封报的是一条它**从盘上读到**的队列，
而不是一条它预测出来的 —— 与 `--seek` 对 `position` 已经遵守的是同一条规矩（§9.3）。
子进程自己的曲终推进是一次针对"它刚播完的那个位置"的 compare-and-swap，
所以如果一首恰好在 `--next` 落地的同一瞬间结束，谁先动谁赢、另一个成为 no-op：
永远不会跳掉两首。信号是发给子进程 **PID** 的 SIGUSR1，绝不发给整个组 ——
USR1 的默认处置是终止，所以一个全组的 USR1 会杀掉那个循环本该越过去的 mpv。

### 9.6 收听日志（`ut-history`）—— 持久存储的另一半

播放列表是人放进去的。日志是播放器写下的。它们共享状态根目录与条目记录，此外没有任何共享：

```
   $UT_STATE_DIR/history/<YYYY-MM>.jsonl      只追加，一次收听一行
```

**用 JSONL，而这是全套件唯一一处打破"一个实体一个文件"的地方。** 一次收听不是一个实体，
它是一个**事件**：一事件一文件到开春就是几千个 inode。三个后果随之而来，且三个都是承重的：

1. 追加不是读-改-写，所以这是**全套件唯一一处不上锁的写** —— `>>` 以 `O_APPEND` 打开，
   而一次小于 `PIPE_BUF` 的写会整条落地。盘上放一个 JSON 数组会让每一次写都成为竞态，
   而那正是 ROADMAP P4 早就排除掉的形状。
2. **因此每一行都必须小于 4096 字节。** 这不是风格规矩，这是第 1 条的**前提**。标题在 UTF-8
   边界上截到 200 字节（把 `utf8_complete` 对一次按键做的事，用 jq 再写一遍 —— 一次可能留下半个
   序列的截断，产出的是一行"不是 JSON 的东西"，而那恰恰是一份只追加的日志唯一无法恢复的事），
   然后**测量**成品行，按顺序丢掉自由文本字段直到装得下。一个只在典型输入上检查过的前提不算前提，
   所以 `tests/contract.sh` 会记录一个 8 KB 的标题，并对**盘上的字节数**做断言。
3. 按月分片让 `--clear --before` 基本上是一次 `rm`，而不是重写整份日志。

**记录点是"一首曲目结束了"，而不是"一个播放器死了" —— 而这就是整个设计。** `--stop` 会把整个
进程组带走，所以一行只在自然播完时才写的日志，记下的将只有"没人打断过的那些首"：
一份系统性偏斜的日志，而且比没有更误导人，因为"我听什么"会被读成"我从不跳过什么"。
于是那次调用坐在子进程循环里**每一次播放之后**、在离开循环的那个分支之前，
而 reason 来自 `CHILD_REASON` —— 绝不来自 mpv 的退出码，后者把"跳过"和"停止"拼成同一个字（§9.5）。
一次干净播完根本不带 reason；跳过与停止都是 `stopped_by_user`，
而把"0:05 的跳过"与"3:20 的停止"分开的是 `seconds`。为了让这句话在 `--stop` 下也成立付了什么，
见 §9.5 的事实 2。

**一首从没打开、也没失败过的曲目不是一次收听。** 落在两首之间那个空档（引擎往返）里的停止或跳过
什么也不写；而同一个空档以**失败**告终时**会**写一行，因为"我试着播它、它播不了"恰恰是历史存在的
意义，而且那是唯一一行"`seconds` 是 0 却说出了真话"的记录。

**播放器写，存储存。** `ut-play` **按名字**调 `ut-history`，与它调引擎是同一种方式，
而且对 JSONL 与按月分片一无所知；`ut-history` 则从不播放。它不在 PATH 上时，什么也不记、
什么也不说 —— **这套套件没有的能力，是靠"没有那个命令"来声明的**，
同一条规矩也让 `bili-resolve` 没有 `--transcript`。这次写发生在一个**先**忽略了 INT 与 TERM 的
子 shell 里，而 `SIG_IGN` 能活过 `exec`，所以一旦它被 fork 出来，哪怕产出它的子进程一毫秒后
就被杀，那一行照样落地。

**`UT_HISTORY=0` 关掉它，而默认是开的** —— 一份出厂即关的历史不是历史，
因为在这个功能产出过任何一行之前，没有人会去找那个开关。它买到的东西是有意有界的：
一个本地文件、在这台机器上、带一个属于它自己的 `--clear` 动词。重开条件是**共享账号**，
那时"这个登录名听过什么"就不再是一个人的记录了。

**体量，免得有人加一个没人需要的轮转。** 一行约 200 字节；一天 50 首，一年约 300 KB。
按月分片加 `--clear --before` 就是全部的体量故事 —— 没有轮转、没有压实、没有上限，
因为在那个速率下它们一个都不会触发。

**TUI 读它，且什么也不存**（`h` 键，见 `AS-BUILT-tui.md` §11）。日志的 `--ls` 信封与播放列表
`--show` 的 `.items` 是同一个形状，所以 `build_playlist_rows` 原样渲染它，
每一个在存储行上生效的键在这里都生效 —— 这也是为什么这个视图只花了一个加载器、
一个谓词（`stored_rows`），以及零个渲染器。
