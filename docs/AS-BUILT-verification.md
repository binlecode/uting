# AS-BUILT-verification —— 风险登记与验证矩阵

## 结构

这套套件**被什么证明**，以及**已知会在哪儿翻车**：设计层面的风险与它们的缓解
（「风险登记」），以及验证矩阵 —— 每一个面由哪条检查覆盖、哪些东西**刻意没有**被覆盖
（「验证矩阵」）。**测量都带日期，且按设计会过期**：一个没有日期的数字是一句
不能被反驳的断言。

## 模块

这里只放证据链、测量数字与风险 —— why/how 的叙事在 `ARCHITECTURE.md` 与各分册，
契约的 why 在 `AS-BUILT-contract.md`。它记录**现在**为真的东西：
一条已关闭的缺陷是 git 历史，不是本文的一节。

## 接口

检查的对象是真实命令面：两个套件（`tests/contract.sh`、`tests/playback.sh`）加 TUI
驱动器（`tests/drive.sh`），断言的是退出码与 stdout —— 功能检查，无 mock，无替身
（CLAUDE.md 的测试规矩）。

## 风险登记（设计层面的缓解）

| 风险 | 缓解 |
|---|---|
| 删掉 TUI 之后留下悬空引用 | 删任何符号之前先用 grep 把它闸住 |
| `resolve_nc_unix` 的 ncat 分支在 macOS 上跑不到（本机 `nc -h` 有 `-U`，探测永远选 nc） | **如实记为无覆盖**：给 ncat 分支造覆盖要么 shim PATH（是 mock，规则禁止）、要么真上一台 Linux —— 后者才是补法。两个套件在 macOS 上验的是 nc 分支 + 探测函数本身的语法与惰性门（`playback.sh` 的活 socket 读走的就是它） |
| 标题里带 tab/换行会撑破一行 | jq `@tsv` 转义；`load_rows` 里 `IFS=$'\t'` 切分（如今是 US，见 `AS-BUILT-tui.md`） |
| 从渲染好的行里错误地还原 URL | url 与显示分开放在平行数组里（按下标取） |
| 过滤过度匹配 / 注入一个 glob | 纯 bash：`nocasematch` + AND 词元 + 加引号的 `"$tok"` |
| 把 URL 当查询粘进去 | `<engine>-search` 拒绝 URL → 不会阻塞式误播（ARCHITECTURE.md「调用形状」） |
| `uting` 在没有 TTY 时被跑起来（agent/管道） | 要求 `-t 0 && -t 1`，否则 die（不挂起） |
| 一次改名破坏兄弟定位 | 每个脚本解析自己的符号链接链（ARCHITECTURE.md「命令拓扑」）；步骤 B 先重指，步骤 C 才删 |
| yt-dlp 的 `ytsearch<N>:` 前缀被覆盖 | 字面量只在 `yt-search` 里，从不被改写 |
| 一个引擎的 URL 被送去另一个的 resolver（引擎被静默错标） | 每引擎一份显式 host 白名单 → 退 1，绝不返回一条解好的流（`AS-BUILT-player.md`「解析」、ARCHITECTURE.md「站点知识的边界」） |
| 新增一个源需要改播放器或 TUI | 它不可能需要：播放器靠拼接引擎名找到 resolver（ARCHITECTURE.md「命令拓扑」），TUI 靠 glob 发现引擎对（`AS-BUILT-tui.md`） |
| 停止之后留下孤儿 mpv | 用进程组（pgid），不走 PID 树 |
| `set -u` 下的空数组展开（bash 3.2） | 用之前先守卫数组展开 |
| 有别的进程连上某个播放器的 IPC socket | `STATE_DIR/players` 0700；macOS 的 `$TMPDIR` 本就是每用户的（Linux 回退到 /tmp 时钉住权限） |
| pid 复用把一个死播放器误判为活的 | **收窄，未关闭**：句柄是单调 token、存活检查看 `<id>.json` 里存的 pid、记录在进程组消失时立即回收 —— 但 `group_alive` 仍是 `pgrep -g`，所以在那个窗口里一个被回收再用、且当上组长的 pid 会看起来是活的（`AS-BUILT-player.md`「运行时 IPC」） |
| 被捕获的 `-d` stdout 阻塞在一个后台作业上 | detach 路径上已经没有后台作业：子进程从解析信封回填自己的记录（AS-BUILT-player.md「进程组模型」）。任何**未来**写在可捕获动词里的 `… &` 都必须重定向自己的 fd —— 一次命令替换等的是管道的**每一个**写者，不只是我们 |
| detached 的 mpv 状态行把磁盘写满 | `YT_DETACHED` → 子进程里 `--no-term-osd-bar --msg-level=all=error`（AS-BUILT-player.md「进程组模型」） |
| 搜索失败没给 agent 任何形状 | 捕获 stderr → `classify_yt_dlp_error` / `classify_http_error` → `{status:"error",…,reason}` 信封，退 2+（AS-BUILT-engine.md「搜索子系统」） |
| 一次风控挑战被报成一次零结果的**成功**（HTTP 200 + `code:0` + `data.v_voucher`，Bilibili 的第三种说"不"的方式） | `fetch_page_once` 趁响应体还在手上判券：券**且**没有 `result` 数组 ⇒ `PAGE_RISK` ⇒ `classify_http_error` 判 `network`（可重试）⇒ 重试一次否则退 2。三层都查，只读前两层的版本会返回 `count:0` 的 ok 信封（AS-BUILT-engine.md「Bilibili 的传输」）。**这条覆盖不在套件里**：一张券没法按需产生，而唯一能产生它的东西是一个替身，那是这里不做的（「验证矩阵」） |
| 服务端的 `duration` 粗桶剪掉了 `-m/-M` 会留下的行（筛选改了**答案**而不只是**代价**） | 只在整个窗口落进一个桶时才下推 —— 要超集，绝不是更窄的切割 —— 而本地那对精确边界无论如何都照跑；`contract.sh` 用 `-M 600`（进桶）/`-M 601`（跨桶）这对判别性输入把两半一起钉住（AS-BUILT-engine.md「Bilibili 的传输」） |
| 一条长得像 flag 的查询变成一个动作 | `--` 在**每一个**动词里结束选项解析，且每个动词在它之后重新施加自己的位置参数检查（ARCHITECTURE.md「端到端控制流」、AS-BUILT-contract.md「门模型」） |
| 某个引擎发明一个新的 reason 值 | 那份枚举是 AS-BUILT-contract.md「数据契约」 的，且是封闭的；三个分类器实现它，谁都不许扩展 |
| 客户端在 `--status` 背后改了音量 | `--status` 从 socket 活读 volume，记录值只作兜底（`AS-BUILT-player.md`「运行时 IPC」） |
| 并发的元数据回填与 set-volume 互相覆盖同一份 `<id>.json` | 按 id 的 `mkdir` 锁（`lock_player_state`）把两次 temp+mv 串行化；回填另外还做 pid 守卫（AS-BUILT-player.md「运行时 IPC」） |
| 写回把用户手写的配置改坏（丢注释、错开中文注释列、写下一个自己读不回来的值） | 就地改写只动匹配行 `=` 右边的值：键的空白、值与 `#` 之间那段空白、以及注释本身逐字节搬过去，**注释列刻意不重排**（宽度层住在渲染路径里，按字节补齐会错开中文注释，而文件仍然合法、什么都不报）；写下去的值必须过 round-trip 闸（`#`、引号、换行、首尾空白、开头 `~/` 一律拒）；先写临时文件再 `mv -f`，`cp -p` 在前，所以一个 600 的文件回来还是 600；`mv` 的目标是**沿 symlink 链解析之后的真实路径**，所以一份从 dotfiles 仓库链过来的配置不会被换成普通文件、留下一个被架空的原件（`AS-BUILT-contract.md`「配置面」「写回」）。判别性输入在 `contract.sh` 的 TUI 段（「验证矩阵」） |
| 跑一次测试套件就改掉开发者自己的配置 | 三个调用点各自隔离（`contract.sh` 通篇一个空的临时文件、TUI pane 另有一个自己的、`drive.sh` 一份副本、`capture-pane` 一个自己的），**外加一条不靠任何人记得的守卫**：`contract.sh` 在两个出口各断言一次用户真实配置的 `cksum` 没变（「验证矩阵」） |
| 一个被环境变量压住的键被写进文件，然后每次启动被读到又扔掉 | 在读配置**之前**记下八个键里哪些已经在环境中；对这些键，写回变成 no-op 加一行提示（`AS-BUILT-contract.md`「配置面」、ARCHITECTURE.md「两个根数据文件」） |
| 一条链接里的起播偏移搭在 `url` 里被存进播放列表（一首收藏曲子从此每次从 10:01 开始） | `url` 与 `start_seconds` 各答一问，偏移只走后者。yt 那边是白拿的（`webpage_url` 本就不带 `t`），bili 那边**动手剥**，因为那个站的 `webpage_url` 必须保留 query（`?p=N` 在里面）—— 剥且只剥 `t=`（`AS-BUILT-engine.md`「起播偏移」）。yt 那半是一条**会漂移的前提**（外部依赖的输出形状），所以 `contract.sh` 有一条反向断言守着它，守的是这个键**存在的理由**而不是键本身（「验证矩阵」） |
| 一个凭据头到达 mpv 的 argv（在 `ps` 里可见） | 引擎不得把 `Cookie`/`Authorization` 放进 `http_headers`；写在 AS-BUILT-player.md「模式 → 格式 → mpv」与 AS-BUILT-contract.md「数据契约」 |
| mpv 被 SIGKILL 之后留下陈旧 socket | `[[ -S sock ]]` 测试 → `ipc_failed`，绝不挂起 |
| 对端不关连接时 `nc` 会等满 `-w1`（一个卡住的 mpv，不是健康的那种） | `request_id` 过滤 + `head -1`；一个**健康**的 mpv 在半关闭时就收，所以一次调用约 0.016s。`uting` 的重绘路径是一个紧循环，所以它根本**不等** `nc`：它从一个进程替换里读回复、读到最后一条就 break，这也把"卡住"那种情形也框住了 |

## 验证矩阵

**上一次运行 —— 这是一次测量，按当次运行填进来的，不是一个要维护同步的常数。** 每个套件都在
最后一行打印自己的计数，那是那个数字唯一的家；这里的条目记录的是某一次运行在某一天花了多少，
它**按设计会过期**，而不是靠漂移过期。*2026-08-31（提速与清理之后）*：
`contract.sh` **295 ok / 0 failed / ~49s**，其中 `--offline` 那一半 **199 ok / 17s**、
零网络调用。**同一天更早是 306 / ~135s** —— 少掉的 11 条与省下的 86 秒各有各的原因，
下面「一个套件为什么会变慢」一节逐条记着。TUI 段 21s、实网取数 14s、其余是本地进程开销。

**一个套件为什么会变慢，以及这一次把哪几件事拿掉了。** 一份跑两分多钟的回归套件，人就不会
在每次改动之后跑它 —— 而一条没人跑的检查等于不存在。这一轮按三条规矩过了一遍全文：

1. **一条检查存在的唯一理由，是它能找出 bug。** 拿掉的：三条断言**夹具自己**装好了的
   （日志/歌单种子、日志清空）、一条断言**这台机器**的 PATH 上没有 yt-dlp 的、一条断言
   **套件自己**把配置文件放回去了的、一条断言这个 checkout 有两个引擎对的 —— 六条全部
   改成**中止**：它们说的都是"这个文件自己出错了"，那不该混在产品的失败里报出来。
   还有两条：`bili --parts is one request` 是一个**秒表**（< 5s），它分不开"多了一次往返"
   和"今天网慢"，它产生的每一次红都会是网络的；`the offline fixture still fits` 找的是
   **夹具过期**，那也是这个文件自己的事。
2. **重复的调用就是重复的等待。** 同一个查询，一次运行里发了六次 `yt-search`；
   `周杰伦` 发了两次，两条主张都能从同一个信封上读出来。现在**每个引擎一次搜索**，
   全文共用。
3. **互不依赖的取数没有理由排队。** 二十来个实网调用彼此无关，串起来跑就是这个文件
   ~130s 里的 ~70s。它们现在**一次全部发出去**（`spawn`/`wait`），断言照旧从磁盘上读回来，
   顺序一个字没改。唯一留在第二波的是"输入来自上一波输出"的那四条（起播偏移那一段的
   句柄要从搜索结果里挑），而它只等**搜索那几个 PID**，不等整批。
   - **`spawn` 不把网络当成发现**：信封的 `reason` 是 `network` 时最多重试两次（实测
     bili 的 view 端点对连续调用三次里限流一次，同一个句柄下一次就 ok）。真的坏了的引擎
     答三次 `network`，照样报出来；**主语就是网络失败**的那几条走 `spawn_once`。
4. **TUI 段的等待改成看，不改成猜。** 二十五份一模一样的五行轮询循环收成一个
   `poll_until <秒> <谓词>`，粒度从 0.25s 降到 0.05s（一次重绘是 15–25ms —— 旧粒度**每次**
   都错过第一帧然后睡满四分之一秒），**预算一秒没变**。固定 `sleep` 全部消失：连按十次 `j`
   变成一次 `send-keys`，`Space Down i` 变成一次，"计数不许掉下 20"变成一个**反向轮询**
   （最多一秒，等它离开 20，期望是"没离开"）。`i` 那一趟从最多六行减到四行 —— 每一行
   都是一次真实的 `--info`。

`playback.sh` **49 ok / 0 failed / ~100s**，之后 `pgrep mpv` 为空。
**同一天更早的两次运行红了七条，那是一次抖动，定位过程记在下面的抖动登记册里。**
**那 68s 里没有一秒是猜的**：约 30s 是七次真实的引擎解析（`ut-play` 自己量到的换曲中位数 4.3s），
约 19s 是收听日志那一段把一首 19 秒的曲子**放到它自己的结尾**——这两半在"没有替身"这条规矩下
都不可压缩；余下的浮动是网络的，不是这个文件的。那几段等待是**有界轮询**而不是固定 `sleep`（见那个文件的门口）：
一个固定的猜测在机器只是慢的时候也会变红，而一次不是 bug 的红，仍然要有人去查一遍。*上一轮的数留在这里当网络方差的证据*：`contract.sh` 2026-08-25 当晚
五次运行落在 81–109s，同一个文件、同一批检查。

**这两个数字各自的成分**（计数本身在上面，只说一次）。`contract.sh` 如今**先跑离线那一半**，
而且能只跑那一半（`--offline`）：实网那一半约 77s（93 − 16，同一次运行相减），其中 tmux 那一段约 16s
——它从 4s 涨上来，涨的那 12s 是写回检查自己按下的两次重取（`→` 越过末页与 `o`）。
（那 16s 是同日、过滤那条检查落地**之前**量的；它一次数都不取，最多再花一秒。）
flag 门在 1s 变红、空闲生命周期 1s、死亡记录 2s。那 13 秒里有 5.5s 是播放列表存储对着一个
**活着的**持锁者刻意的自旋 —— 旁边那条陈旧锁检查只花 0.1s，因为陈旧判定挪到了自旋**之前**
（AS-BUILT-player.md「持久状态层」）。

这个顺序在文件里是作为**契约**陈述的，因为其中一部分是承重的
（离线在前；死亡记录夹具，然后 TUI 段放最后，因为 pane 里的 `uting` 会轮询 `--status`
而每一个生命周期动词都回收）。`tests/` 下**三个**入口点全都把 `TMPDIR` 指向自己的目录 ——
两个套件加 `drive.sh` 驱动器，后者是最后一个还在用用户目录的 —— 所以它们没有一个够得到
用户正在听的那个播放器的状态目录。两个套件也把 `UT_STATE_DIR` 指向自己的：
一个 detached 播放器每首曲目写一行收听记录（`AS-BUILT-player.md`「收听日志」），
没有它的话每次运行都会往用户真实的历史里追加一打没人听过的曲目，
而历史与播放器不同，不是 `--stop` 收得回来的东西。`drive.sh` 刻意**不**重定向 `UT_STATE_DIR`
—— 从它截下来的一帧应该显示一个人看得见的那个存储 —— 改为给 pane 喂 `UT_HISTORY=0`，
在不清空**读**的前提下压住**写**。

**配置文件是同一条规矩往外一层，而它是随写回一起才变得承重的。** `uting` 如今会把八个键
写回 `UT_CONFIG` 指的那个文件（`AS-BUILT-contract.md`「配置面」），于是"跑一次套件"从**读**开发者
自己的配置变成了**改**它。三个调用点各自隔离：`contract.sh` 通篇 export 一个空的临时文件、
TUI 段另给 pane 一个自己的、`drive.sh` 把用户那份**复制**进本次运行的临时目录
（读的一侧照旧是人看得见的那份，写的一侧落在副本上 —— 与 `UT_HISTORY=0` 同一笔交易），
`capture-pane` 那一处同样自带一个。**但三处各自记得 export 是靠不住的**，尤其是那个不走
`drive.sh`、自己起 TUI 的抓帧流程，所以真正的保险是一条守卫：`contract.sh` 在开头记下
用户真实配置的 `cksum`，在两个出口（`--offline` 与全跑）各断言一次它没变。
它抓的是**任何**漏网的调用方，包括这行字写下之后才加进来的那个；文件不存在时它报 skip，
不报绿 —— 一台没有配置可毁的机器，证明不了一台有配置的机器上的任何事。

**只做功能测试，且只有两个文件。** 渲染器 rig（`tui_pane.sh`）与它那个单元格网格证明器被移除了：
**版式是在一帧进入文档时被证明的**（`.claude/skills/capture-pane`，它仍带着 `assert_pane.py`），
而套件断言的是**存活** —— TUI 起来了、扛过两次 resize、按 `q` 以 0 离开。
唯一的例外是那次**往返**（`h` 打开日志、再按 `h` 回到搜索），它断言的不是画面而是**行源**：
表头上 `items=` 与 `results=` 的差别是一个状态，不是一幅版式。

**写回与两条边是同一条规矩下的新覆盖：断言的是文件的内容与表头上的一个数，不是画面。**
它们全挂在 TUI 段**已经起着的那一个** pane 上 —— 不多一次冷启动、不多一次冷搜索，
这正是 harden-before-you-extend 的样子。每一条各自带着它的判别性输入：

- `v` 之后，配置里那一行的**值**变了而行尾注释还在 —— 一个 `printf '%s=%s\n'` 的天真实现
  过得了值那一半，过不了注释那一半；
- 那个夹具**本身是一条 symlink**，指向另一个真实文件：`v` 之后它**仍然是** symlink，
  而变了的是链接指向的那份。这一条是零成本白捡的判别性 —— 一个 `mv -f` 到链接上的实现
  值那一半照样发绿（新的普通文件里就写着新值），只有 `-L` 这一问把两者分开；
- `f` 之后配置里**长出**了 `UT_PLAY_QUALITY=medium`，而夹具里原本没有这个键 ——

> 死亡记录夹具住在 `${TMPDIR}/uting-$(id -u)/players` 下，只以 uid 为键，
> 而**每一个生命周期动词都回收** —— 于是从任何地方来的一次 `ut-play --status`
> （包括一个 TUI 的存活轮询）都会在墓碑夹具被创建与被读之间把它删掉。
> 持久的修法是每次运行一个状态目录，如今 `tests/` 下每一个入口点都建它：各自 export 自己的
> `TMPDIR`，于是同一个 uid 上不会有第二个 uting 共享这个目录。留下来的是同一个机制在**单次运行
> 内部**仍然隐含的那条**顺序规矩** —— 死亡记录段必须排在 TUI 段之前，因为 pane 自己的
> `--status` 轮询会回收 —— 而它写在那一段自己身上，不是靠版面顺序碰巧成立。
>
> **第二条已经追平，且它是一条真实的种族条件而不是环境问题。**
>
> **第三条，观察到两次、且仍未定位 —— 记下来是因为一条没被记录的抖动，是一条第二次没人认得出的
> 抖动。** 2026-08-25，两次背靠背运行的第一次里，TUI 段最后两条检查一起红了 ——
> *"quits on q with 0"* 与 *"hands the tty back on exit"* —— 而第二次以 177/177 原样通过。
> **这一对一起失败正是那个信号**：第二条读的那行 FLAGS 是由打印 `RC=` 的同一条 pane 命令打出来的，
> 所以两者都没出现，意味着 `uting` 在轮询允许的 10 秒内没有离开。它不是"退出很慢"：
> 事后量过，七次运行（三次朴素、四次照着该段精确的 boot → 62x20 → 26x24 → `q` 序列驱动），
> **每一次退出都落在 186–250 ms**，也就是说预算是成本的五十倍。两个可能吞掉按键的应用内机制
> 找过并排除了：`$TMUX` 设置时会跳过 OSC 11 背景查询（AS-BUILT-tui.md），
> 所以读取器里不可能坐着一个终端回复；而 `q` 不是 UTF-8 首字节，所以 `utf8_complete` 吸收不了它。
> 剩下的是这台机器：那天下午这个 checkout 上还有第二个会话在工作、也跑过同一个套件，
> 而两者有没有重叠没有被记录下来。作为**未定位**归档，附带那次测量，而不是解释掉。
>
> **它在同一天傍晚又发生了 —— 同样那两条检查、同样是两次运行的第一次、第二次干净 ——
> 而这一次它留下了东西。** 那次运行之后七分钟，一个
> `ut-play --engine yt -f audio --` 加一条来自 pane 自己结果列表的 URL 仍在运行，
> 挂在 PID 1 下，它的 mpv 的 socket 在那次运行自己的 `uting-contract.*` 目录里。
> 那一段里没有任何东西会按 Enter，所以 **pane 收到了套件没有发出的输入**：原因仍未定位。
> 这次复现真正定下来的是：上面那个"机器上有第二个会话"的读法是较弱的那个，
> 因为那天傍晚一个也没有 —— 当天其余的工作在七小时之前就落地了。
>
> 那个播放器解释的是**后果**，而这一半如今已经修好。`uting` 在 `cleanup_on_exit`
> （EXIT INT TERM HUP）里停掉自己的播放，所以一个**离开了**的 TUI 会带走它的播放器，
> 而一个**没有**离开的 TUI 就是一个仍然攥着播放器的 TUI —— 那两条红与一个活着的播放器
> 是同一个事件，不是两个。这一半如今由三件事守着，每一件都由破坏它来证明过
> （一次按 Enter、然后永不按 `q` 的运行）：
>
> - cleanup **先回收再删除**，并报告一个**限定在本次运行自己 socket 目录**的孤儿 mpv ——
>   与 `playback.sh` 的 cleanup 同一个顺序。反过来先删，状态目录一没，播放器的**记录**也跟着没：
>   那个进程会活过 `--stop --all` 找得到它的能力，除了 `kill` 没有东西能让那段音频停下来 ——
>   而这会发生在一个自己 docstring 写着"不碰你的状态"的文件里；
> - 一条检查 *"the TUI left no player behind"*，于是泄漏是**可见的**而不只是无害的。
>   它只在这个精确情形下变红，而这正是它值一行的原因；
> - `q` 不生效时**转储** pane。那一帧是"哪个读取器吃掉了那个字节"唯一的证人，而它随 session 一起死；
>   在破坏性运行里那份转储的第三行带着 `▶ Playing:`。下一次发生时它会自己说出来。

**四件这个套件刻意没有的东西，记下来，好让每一件都是被有意拒绝的、而不是被反复重提。**
没有一件是缺口；每一件都是一个带理由的决定：

- **不加 `tests/lib.sh`。** 两个套件互相独立、各自能单独跑通是**设计**，不是意外，
  而 CLAUDE.md 的"no rig layer"直接管着这里。重复的是大约二十行 `report`/`ok`/`bad` 的账房代码，
  可以接受；而重复的**论证**不可以 —— 这正是 `TMPDIR` 那套理由**只说一次、被指两次**的原因。
- **不加 `tests/all.sh`。** 两条命令，而 CLAUDE.md 已经写明各自什么时候跑：
  `contract.sh --offline` 每次提交前、完整的 `contract.sh` 每次推送前，
  `playback.sh` 播放器改动时。
- **不加"跳过网络"的环境**变量**开关** —— 环境变量是给 set-once 调优用的，而"跑不跑网络"是
  一次**每次调用**的选择，那是 flag 的形状（CLAUDE.md 的分法）。而 flag 是有的
  （`tests/contract.sh --offline`），理由三条：(a) 离线/在线那条边界**本来就是承重的**
  （就写在这个文件的段序契约里），而一条谁也停不下来的边界，只有作者一个人用得上；
  (b) CLAUDE.md 要求**任何改动**都跑这个文件，包括一次注释修订，而一个没有 YouTube
  就跑不起来的门，是一道大家学会跳过的门；(c) "你拿到的是哪一种绿"是靠**输出**答掉的，
  不是靠不给这个选项 —— `--offline` 是同一次运行的**前缀**（同样的检查、同样的顺序，只是在
  第一次实网调用前停下），停下的地方**点名**了没跑的是什么，而且提交/推送两级写进了 CLAUDE.md。
  实测：全跑 ~100s / 278 条；`--offline` ~18s / 193 条、一个包都不发。
- **不加只为抬高计数的检查**，也不加任何时序或渲染画面断言。加固的默认动作是让**既有的**
  那条更强，而不是多一个文件（CLAUDE.md 的 harden-before-you-extend）。

**这里刻意不按路径点名任何*临时*检查。** 例外是三个挣到永久位置、提交在 `tests/` 下的文件 ——
两个套件 `contract.sh` 与 `playback.sh`，以及 TUI 驱动器 `drive.sh`
（它什么都不断言，存在的意义是回收 session 被杀之后留下的 detached 播放器）——
根 README 按名字描述它们，因为**没有指针指向的东西，贡献者跑不了**。
此外这个套件用来验证过的一切，
都是一个仓库不跟踪的 `tmp/` 下的一次性东西（`.gitignore`：`**/tmp/`），
所以按路径引用它们是一个 checkout 兑现不了的承诺 ——
它只在恰好一台机器上解析得开，直到那台机器的 scratch 目录被清掉为止。
**耐久的是每条检查的*形状***，而下面的条目记的就是这个：驱动了什么、怎么观察的、
以及活下来的断言数。一条检查从描述重建很便宜，而当它点名的那个文件已经不在时去信任它很贵。

**起播偏移是三层新覆盖（2026-08-30，随 `--start` / `start_seconds` 落地），三层各归各的套件。**
`contract.sh` 从 278 涨到 298，`playback.sh` 多两条：

- **门在离线半边**（七条）：`--start` 对负数、`hh:mm:ss`、小数、非数字、缺参一律退 1，
  且与生命周期动词并列时退 1。判别性在最后两条：拿来对照的两个动词在空闲时本来就答 4，
  这次调用也没有播放器，所以一个 **1** 只可能来自组合门 —— 这条检查没法在空闲路径上蒙混过关。
  `--start -60` 同时是旁边 `--seek -15` 那条的镜像：那里一个前导减号是**合法取值**，
  这里是一个被这个 flag 拒绝的合法取值，两者都要求解析器逐字取 `$2`。
- **信封在实网半边，且陈述为对每一个被发现的引擎的不变量**（每引擎四条）：偏移被读出来、
  它**不在** `url` 里、**只有**它被剥掉（两个引擎都把自己的 id 放在 url 里 —— yt 在 query、
  bili 在路径 —— 所以一个把整个 query 扔掉的实现在这里红）、以及 `?t=0` 答 `0` 而不是 `null`。
  最后一条是**判别性输入**：把"从头开始"和"没带偏移"折进同一个值的每一种写法
  （jq 的 `// null` 撞上假值 `0`、bash 的 `[[ -n ]]` 撞上空串）都在这里印错。
  B 站的 `?p=` 在剥完之后还在，这条挂在那个引擎旁边而不是循环里 —— 只有它有多 P。
- **句柄是从引擎自己的搜索里取的，这正是让它成为不变量而不是一张第三引擎不在其中的表的东西 ——
  但那一行是被过滤过的，而过滤本身就是这段不抖的全部原因。** `lofi` 返回的是电台：
  一个 24/7 直播（`is_live`，无时长）和它十二小时的回放（`was_live`，分片 manifest）。
  对任一种做定格式 resolve 要跑**几分钟**，这个文件在头一次撞上直播行时从不到两分钟涨到九分钟以上；
  第一版过滤只排掉 `is_live`，于是仍然挑中一条 `was_live` 的十二小时行，照样挂。
  最终形状：`live_status == null`（两种时态的广播都排掉）之后取 **duration 最短**的一条 ——
  不需要争一个阈值，且按构造就是整页里最便宜的句柄（实测 yt 4s、bili 3s）。
  句柄本身也被断言，所以哪天这个查询不再返回合适的行，红的是一条**有名字**的检查。
- **行为在 `playback.sh`**（两条）：`--start 600` 起播后从真 socket 读回 `time-pos`，
  判 `595 ≤ p ≤ 605`。**N 取 600 而不是 42，这是这条检查的全部设计**：一个把 `--start`
  丢掉的实现报的是个位数，与 600 差两个数量级，所以窗口可以给得宽松而永远不会在它要抓的
  那个失败上发绿。取 42 的话，诚实的窗口得有一两秒宽（冷启动、未预热的解码器报的第一个
  位置就落在那个范围里），而那个宽度**确实**能让"从零开始"在小 N 上蒙混过去 ——
  把容差放宽到检查能过，正是一条检查失去失败能力的方式；挪 N 才是让同一个容差不再要紧的方式。
  下界取 595 而不是 600，是因为 mpv 落在目标处或其之前的那个关键帧上（实测 599）；
  断言 600 就是在断言今天 `U1` 解析出来那条流的关键帧间隔。

> **第四条抖动 —— 2026-08-30，`playback.sh` 的七条一起红，定位到机制、没定位到触发。**
> 两次背靠背运行**一模一样**地 42 ok / 7 failed、346s 与 348s（同日第三次：49 ok / 0 / **79s**）。
> 七条是：player 1 的活读、bili 的 header 证明、`--quality` 的证明、队列推进，以及收听日志那三条。
> **它们的共同点是唯一的信号**：每一条都要求**一个播放头真的往前走**，而这次运行里
> **每一条只需要信封的检查都过了**。所以问题不在解析、不在 IPC、不在记录，就在"放不动"。
>
> **排掉的三个读法，各附证据。** ① **不是这次改动**：在它之前的那个提交上开一个 worktree
> 跑同一条路径，位置同样二十秒不动；而同一棵树现在 49/0 全绿 —— 两个方向都证了。
> ② **不是并发**：按套件的开头同时起两个播放器，两个都照常前进（`t=7s` 就都有位置了）。
> ③ **不是 `is_live`/`was_live` 夹具** —— 那是同一天在 `contract.sh` 里真的咬过一次的问题（「验证矩阵」 上文），
> 但这里三个夹具 `live_status` 全是 `not_live`。
>
> **机制**：`wait_live` 的预算是**固定的 40 秒**，而它等的那件事在健康状态下只要 4–8 秒 ——
> 三个夹具各跑两遍量到 `ttfp`（首个非零位置）分别是 7/8s、7/5s、4/5s，包括那条六小时的
> `n61ULEU7CO0`，**所以"U1 是条太长的夹具"这个顺手的解释是错的**，三者只差两三秒。
> 余量是 5–8 倍。而那次窗口里整个套件慢了 **4.4 倍**（346s vs 79s），
> 5 倍左右的普遍变慢就正好吃掉这个余量 —— 于是"要播放头"的全红、"只要信封"的全绿。
>
> **触发那次变慢的东西没有定位。** 与它最吻合的是上游在一次突发之后限流：那几分钟里跑过
> 几十次 resolve、三次完整的 `contract.sh`，还有一次对着直播 manifest 卡了五分钟的抽取。
> 但这不是证据 —— 窗口内对一个流 URL 做的一次 300KB range 请求回来是 206 / 0.08s / 约 3MB/s，
> 而那既不能证明也不能否定一个被限速的**持续**会话（googlevideo 仍会把第一块发得很快）。
> **按未定位归档，附上这些测量，而不是把它解释掉。**
>
> **它对设计说了什么，以及为什么不去调那个数。** 有界轮询取代固定 `sleep` 的理由（见本节开头）
> 是"一个固定的猜测在机器只是慢的时候也会变红"—— 而**那个界本身仍然是一个固定的猜测**，
> 只是大了一号。把 40 秒调大，买到的是这一类抖动更少，付出的是一次**真的挂住**要更久才报出来，
> 而后者才是这条检查存在的理由。**一次观察不足以做这笔交易**，所以这里只记录，不调参。
> 再次观察到时，该动的不是这个数字，而是让这几条等一个**事件**而不是等一段时间。
