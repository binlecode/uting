这套套件**被什么证明**，以及**已知会在哪儿翻车**：设计层面的风险与它们的缓解、
缺陷登记册（含它的历史），以及验证矩阵 —— 每一个面由哪条检查覆盖、哪些东西**刻意没有**被覆盖。

**这份文档与 `ARCHITECTURE.md` 的分工**：架构文档只留图、流程、伪码与决定；证据链、测量数字与
登记册在这里。节号沿用原有编号（**§25**、**§27**），所以既有的 `§25.1` 一类引用只需换文件名。
实现细节在 `AS-BUILT-player.md` 与 `AS-BUILT-tui.md`，契约在 `AS-BUILT-contract.md`。

**测量都带日期，且按设计会过期。** 一个没有日期的数字是一句不能被反驳的断言；
这份文档里的数字全都记着它是对着什么、在哪一天量的。

## 25. 风险登记（设计层面的缓解）

| 风险 | 缓解 |
|---|---|
| 删掉 TUI 之后留下悬空引用 | 删任何符号之前先用 grep 把它闸住 |
| 标题里带 tab/换行会撑破一行 | jq `@tsv` 转义；`load_rows` 里 `IFS=$'\t'` 切分（如今是 US，见 `AS-BUILT-tui.md` §11） |
| 从渲染好的行里错误地还原 URL | url 与显示分开放在平行数组里（按下标取） |
| 过滤过度匹配 / 注入一个 glob | 纯 bash：`nocasematch` + AND 词元 + 加引号的 `"$tok"` |
| 把 URL 当查询粘进去 | `<engine>-search` 拒绝 URL → 不会阻塞式误播（D8） |
| `uting` 在没有 TTY 时被跑起来（agent/管道） | 要求 `-t 0 && -t 1`，否则 die（不挂起） |
| 一次改名破坏兄弟定位 | 每个脚本解析自己的符号链接链（ARCHITECTURE.md §4）；步骤 B 先重指，步骤 C 才删 |
| yt-dlp 的 `ytsearch<N>:` 前缀被覆盖 | 字面量只在 `yt-search` 里，从不被改写 |
| 一个引擎的 URL 被送去另一个的 resolver（引擎被静默错标） | 每引擎一份显式 host 白名单 → 退 1，绝不返回一条解好的流（`AS-BUILT-player.md` §10、ROADMAP D12） |
| 新增一个源需要改播放器或 TUI | 它不可能需要：播放器靠拼接引擎名找到 resolver（ARCHITECTURE.md §4），TUI 靠 glob 发现引擎对（`AS-BUILT-tui.md` §11） |
| 停止之后留下孤儿 mpv | 用进程组（pgid），不走 PID 树 |
| `set -u` 下的空数组展开（bash 3.2） | 用之前先守卫数组展开 |
| 有别的进程连上某个播放器的 IPC socket | `STATE_DIR/players` 0700；macOS 的 `$TMPDIR` 本就是每用户的（Linux 回退到 /tmp 时钉住权限） |
| pid 复用把一个死播放器误判为活的 | **收窄，未关闭**：句柄是单调 token、存活检查看 `<id>.json` 里存的 pid、记录在进程组消失时立即回收 —— 但 `group_alive` 仍是 `pgrep -g`，所以在那个窗口里一个被回收再用、且当上组长的 pid 会看起来是活的（`AS-BUILT-player.md` §9.3） |
| 被捕获的 `-d` stdout 阻塞在一个后台作业上 | detach 路径上已经没有后台作业：子进程从解析信封回填自己的记录（§9.1）。任何**未来**写在可捕获动词里的 `… &` 都必须重定向自己的 fd —— 一次命令替换等的是管道的**每一个**写者，不只是我们 |
| detached 的 mpv 状态行把磁盘写满 | `YT_DETACHED` → 子进程里 `--no-term-osd-bar --msg-level=all=error`（§9.1） |
| 搜索失败没给 agent 任何形状 | 捕获 stderr → `classify_yt_dlp_error` / `classify_http_error` → `{status:"error",…,reason}` 信封，退 2+（AS-BUILT-engine.md §7） |
| 一条长得像 flag 的查询变成一个动作 | `--` 在**每一个**动词里结束选项解析，且每个动词在它之后重新施加自己的位置参数检查（ARCHITECTURE.md §6、AS-BUILT-contract.md §2） |
| 某个引擎发明一个新的 reason 值 | 那份枚举是 AS-BUILT-contract.md §3 的，且是封闭的；三个分类器实现它，谁都不许扩展 |
| 客户端在 `--status` 背后改了音量 | `--status` 从 socket 活读 volume，记录值只作兜底（`AS-BUILT-player.md` §9.3） |
| 并发的元数据回填与 set-volume 互相覆盖同一份 `<id>.json` | 按 id 的 `mkdir` 锁（`lock_player_state`）把两次 temp+mv 串行化；回填另外还做 pid 守卫（§9.3） |
| 一个凭据头到达 mpv 的 argv（在 `ps` 里可见） | 引擎不得把 `Cookie`/`Authorization` 放进 `http_headers`；写在 §8.1 与 AS-BUILT-contract.md §3 |
| mpv 被 SIGKILL 之后留下陈旧 socket | `[[ -S sock ]]` 测试 → `ipc_failed`，绝不挂起 |
| 对端不关连接时 `nc` 会等满 `-w1`（一个卡住的 mpv，不是健康的那种） | `request_id` 过滤 + `head -1`；一个**健康**的 mpv 在半关闭时就收，所以一次调用约 0.016s。`uting` 的重绘路径是一个紧循环，所以它根本**不等** `nc`：它从一个进程替换里读回复、读到最后一条就 break，这也把"卡住"那种情形也框住了（§25.1 F19） |

### 25.1 缺陷登记册 —— TUI 加固那一轮

对着 `shell/uting` 审计。**批次 1（一行改动）、批次 A（便宜的正确性/体验改动）、批次 B（IPC 层）、
批次 C（存活轮询）、批次 D（失败上报）、批次 E（输入层），以及视图清理与 i18n 那两轮，
全部已修 —— 登记册是空的** —— 这是一份**已知缺陷**的登记册，不是对代码的描述。
它留在这里而不是作为一个散落的 `PLAN-` 文件，是因为这些发现都是关于*这套*设计接缝的陈述，
而每一条只有挨着它所属的那一节才可行动。
下面这些行后来又对着代码重新审计过、并在本机自己的 bash 3.2.57 上重新测量过。
**其中七条断言了假的东西** —— F2 的 reason 来源、F5 的往返成本、F10 的字节序技巧
（而它的替代方案"对孤立字节做表成员判断"是**先量后写**，没有第二次凭想当然）、F11 的补白单位、
F13 的按位置读回复、F15 的全部，以及 F19 自己那个替换数字（它是对着一个探针量的，
而不是对着 mpv）—— 所以这些更正是**内联记下来**的，而不是被悄悄换掉：
它们每一个都曾是某个修复将要建立其上的前提。F19 那一轮最锋利：
一个错的数字靠重测被发现，被换成另一个来自"行为不像那个程序"的 rig 的错数字，
最后是真播放器才把它定下来。

**是复现出来的，不是推断出来的：**

- Space → 暂停 → 取消暂停会让脚本以状态 1 退出（`set -e` 在第二次切换时把它杀掉）。
- `play_selected` 从一个 case 分支返回 1 会让脚本以状态 1 退出 —— 没有输出，没有清理消息。
- bash 3.2 上 `read -rsn1` 交回一个**字节**：你 以 `e4 bd a0` 到达，是三个键。
- 在 UTF-8 locale 下，3.2 的 `${q%?}` 剥掉的是一整个**字符**（你好 → `e4 bd a0`），
  所以 F10 的退格不需要任何按字节修补的兜底。
- 一次 `nc -U -w1` 往返对着**真 mpv 花约 0.016 s** —— 这里曾经记着的"约 1.02 s"是对着一个
  从不关连接的探针量的，也就是一个**卡住的**播放器，不是一个健康的（F19；更正见本节末尾的已关闭清单）。
- `printf '%-8s'` 补到八个**字节**，不是八个字符（F11）。

**`set -e` 家族 —— 已修。** 三条都是同一个坑（ARCHITECTURE.md §28）：
一个非零状态从一个"读起来像表达式而不像命令"的地方到达 `set -e`。见本节末尾的已关闭清单。
F2 的**上报**那一半 —— 一次失败的 Enter 是一个可存活的 no-op 且不给任何消息 ——
在批次 D 发出，采用与 `n`/`m`/`o` 失败同一种"按任意键"的样式，这也是它与 F7 同批的原因。
**一处更正，记下来是因为一个修复差点就建在它上面：** 那个 reason **不能**来自信封的 `reason`。
AS-BUILT-contract.md §3 那份分类属于**阻塞式**播放路径；对一次同步的 `-d` 失败，
播放器是带着散文 `die` 在 **stderr** 上，stdout 上什么也不发。

`uting` 捕获那份 stderr，方式与 `fetch_json` 对搜索已经做的一样。

同一轮里审计通过的：其余每一个 case 分支函数在所有路径上都返回 0（`move_selection`、
`cycle_mode`、`cycle_sort`、`new_search`、`more_results`、`filter_live`、
`stop_current_playback`、`apply_filter`）；`mpv_get_prop` 以 `|| true` 结尾，
且只在命令替换里被用到。

**调用栈边界 —— `uting` 伸手越过一条它本就有的接缝。** 空：这一类已关闭。两名成员都发出了 ——
存活轮询（F3，批次 C）与输入层那些按字节切分的读取器（F10 + F9，批次 E）。

**形状 —— 重复与没写完的规矩。** 一条不剩；F11 是最后一行，随下面的 i18n 那一轮关闭。

**撤回 —— F15 不是缺陷。** 它把（后来被删掉的）mini player 的 `${#total_time}` 条宽计算读成了
一个 ambiguous 宽度 bug，理由是 `total_time` 可以是 `● LIVE`。它不可能：`fetch_play_times`
的直播分支带着 `PT_PCT=""` 提前返回，而那个视图的 `bar_total` 只在
`if [[ -n "$PT_PCT" ]]` 内部计算，那里前缀的每一部分都是 ASCII（`fmt_sec` / `SHORT_DUR`）。
如今那个变量与那个视图都不存在了 —— 卡片按 `cols` 定它的条宽，绝不按 `${#var}`。
那里错的只有注释：它陈述了结论（"前缀那些格全是 ASCII"）却没写出让它成立的那次提前返回；
如今它点名了那次提前返回。算术一个字都没改。

**接受，不是缺陷**（记下来免得被反复重议）：过滤模式吞掉 `q`/`s`/`9`/`0`/`l` 是**有意的模态**；
过滤模式下一次失败的播放会在"按任意键"上吃掉一次击键，这与 `n`/`m`/`o` 失败的行为一致。
pid 复用会让已发布的 `check_player_alive` 的 `kill -0` 误报，
与 §25 为播放器自己的 `group_alive` 记下的完全一样 —— 由单调 id **收窄**，未关闭，
而且不值得在客户端再上第二套机制。

**顺序 —— 按投入产出比，不按严重度。** 一条不剩。F11（那次纯装饰的 i18n）排在最后，
因为它是最大的一次编辑、也是唯一纯装饰的一次；轮到它时，视图清理那一轮已经把让它变大的
标签版式删掉了，于是它以"一次字符串替换 + 登记册从没列过的九个瞬时点"发出。

（有五个批次排在它前面并先发：便宜的正确性/体验改动 —— F18、F14、F16；IPC 层 ——
F19、F13、F5，重新审计把它从最后提到最前，因为一次往返被发现要花一秒而不是借来的约 10 ms；
存活轮询 F3；失败上报 F2b + F7；输入层 F10 + F8 + F9。见下面的已关闭清单。）

**批次 B 关闭 —— IPC 层**（`bash -n` 干净；`set -e` 复现分别对着一个活对端、一个陈旧 socket、
一个消失的 socket 与完全没有 socket 都绿；然后是一个真 tmux pane 驱动真后端 ——
yt-dlp 搜索、detached mpv）：

**先说更正，因为 F19 是基于一次假测量立案的。** 那个"每次往返约 1.02 s、每次卡片重绘约 3 s"
的数字来自一个**从不关连接**的手写 socket 对端。真 mpv 在客户端半关闭之后**会**关，
于是 `nc` 立刻返回，而**旧**代码的 `fetch_play_times` 花 **0.026 s**、单个属性花 **0.016 s**
—— 对着一个活的 mpv socket 量的，并在 tmux 里确认：修复前的构建在 6 个一秒采样里把卡片的时间读数
滴答了 6 次，与修好之后一模一样。第二个数字从来就不该记在一个健康播放器头上。
那个探针实际建模的是一个**卡住的**对端；那才是旧代码按次付 `-w1` 的那种情形。

所以 F19 作为一次真实但小得多的改动成立，而这一批真正的缺陷是 F5：

- **F19（连带 F13）** —— `fetch_play_times` 如今把它那三条 `get_property` 顺着**一条**连接发下去
  而不是三条，而每个读取器都从一个进程替换里取回复、读到它想要的最后一条就 break，
  于是一个不再关连接的对端对重绘的代价从"每次调用一个 `-w1`"变成零。对着真 mpv：
  `fetch_play_times` **0.026 s → 0.017 s**，`mpv_get_prop` 与 `send_mpv_ipc` 不变，约 0.016 s。
  对着那个从不关的探针（也就是卡住播放器那种情形）：**3.12 s → 0.07 s**，
  而卡片在 5 个一秒采样里重绘 5 次 —— 从前只做到 1 次。回复按 `request_id` 匹配，绝不按行序 ——
  mpv 会把异步事件复用进每个客户端的流里，而正是这一点让"批量发"成为安全的
  （F13 那个 `map(.data)[]` 的草稿会把一个事件坐到一个属性的位置上）。
  对着一个把三个请求**倒序**作答、且中间夹着事件的对端验证过；
  一个 `time-pos` 还是 null 的新播放器仍然渲染 `--:--`，不会把 duration 滑进 position 的位置。
  `send_mpv_ipc` 也拿到了它从来没有过的投递确认。
- **F5** —— `adjust_volume` 改成带 0–100 钳位的读-改-设，而不是 `add volume ±5`，
  于是 socket 这条路再也不能走过套件其余部分所说的那份契约（mpv 自己的上限是 130）。
  端到端对着真 mpv 验证过：一个以 `--volume 10` 启动的播放器，按二十下 `0` 之后，
  在 `ut-play --status` 里读出 **volume 100** —— 旧的 `add` 会把它留在 110。
  那次多出来的往返正是它与 F19 绑在一起的原因；在 0.016 s 上它怎么算都付得起，
  而这也是那次假测量唯一一处**改变了决定**而不只是改变了一句话的地方。

**批次 C 关闭 —— 存活轮询**（`bash -n` 干净，`shellcheck` 无新发现，三个 `set -e` 复现都绿，

- **F3** —— 一个死掉的播放器不再把它的 chrome 留在原地。`check_player_alive` 在主循环顶端

  并经新的 `clear_play_state` 清除；为什么包装进程 pid 才是该测的东西、
  以及为什么空 pid 意味着"未知，按活着算"，见 `AS-BUILT-tui.md` §11。
  在 tmux 里对着一个被它的进程组杀掉的播放器验证过：**卡片**在一个 1 秒滴答内清空、
  **完全不需要按键**；**列表**横幅撑到下一次按键（那次读是阻塞的 —— 接受，且如今是断言而不是假设）
  然后消失；而在 `/` 打开时，一次过滤击键会清掉横幅**且不离开过滤模式** ——
  这半件事是一个只改一处调用点的修复会漏掉的。一个活播放器、一个空 pid、一个没有 id 的状态
  都原样不动。那个单元测试**抽取真实的函数体**（用 `awk` 扫脚本，于是它不可能与一份副本漂移），
  并且还断言 `clear_play_state` 覆盖**每一个**声明过的 `CURRENT_PLAY_*` 全局量 ——
  它顺带发现的那个既有缺口正是这么找出来的：`stop_current_playback` 从来没清过轮询路径会清的
  某个字段，于是"清干净了"有两种定义，而其中一种是错的。

**批次 D 关闭 —— 失败上报**（`bash -n` 干净，无新 `shellcheck` 发现，`set -e` 复现与批次 C 的
测试仍然绿，以及一个带 23 条断言的夹具 tmux rig，为了抓抖动跑了三遍）：

- **F7** —— `report_fetch_failure rc [query]` 取代了 `new_search`、`more_results`、`cycle_sort`
  里三份"没有结果 / 那个错误 / 按任意键"的副本。那些副本那时已经漂移了 ——
  `m` 与 `o` 说 "no results"，而 `n` 说 `no results for "…"` —— 这是"一个块想变成一个函数"
  的常见信号。每个调用方仍然在上报**之前**恢复自己动过的全局量，
  所以查询是作为**参数**传进来的，而不是从 `QUERY_LABEL` 读的 —— 那时它已经变回仍然有效的那一个。
  按键逐个验证过：先是消息，然后是它背后完好的状态（label、`RESULT_N`、`SORT_FIELD`）。
- **F2b** —— 一次失败的 Enter 如今会说明原因。`play_selected` 像 `fetch_json` 保存搜索的
  stderr 那样，把播放器的 stderr 留在一个临时文件里，并上报它的**最后一行**、
  剥掉播放器自己的 `Error: ` 前缀（`die` 可能在原因上方打印上下文）。stderr 为空时降级为
  "playback failed"；`rc` 为 0 但信封里没有 id 或 sock 时报 "malformed launch envelope"，
  而不是把那次按键丢掉。两个调用点上的 `|| true` 保留 —— 那是 F2a 那道守卫，
  而这里只是给它一句话可说。
- 两者都以同一个 `press_any_key` 结束。那次暂停就是整套机制：一条打进滚动区的消息，
  恰好活到下一次重绘，而下一次重绘只有一次按键之遥。
- **不上色。** 计划里说给播放原因上 `C_YELLOW`；主题那一轮把那个变量退役了（它在每个主题里都是
  `''`），而它旁边那些 `n`/`m`/`o` 失败打印的是素色，所以读一个退役的全局量什么也买不到。
- **更正 —— 计划为 F2b 写的那个复现步骤本身已经不可达。** 它说要强制 `-f ascii` 走 detached 路径、
  看着播放器拒绝。而 F16（批次 A）在启动时就用 `MODE_CYCLE` 校验 `-f`，
  于是 `ascii` 如今死在参数解析里、根本到不了 `play_selected`：
  一个已发出的修复关上了下一个修复想要穿过去做测试的那扇门。

**批次 E 关闭 —— 输入层**（`bash -n` 干净，无新 `shellcheck` 发现，早先每个 rig 仍绿，
外加一个跑在真实函数体上的单元测试与两个新 tmux rig；**前提是在写下一行代码之前先量的**）：

- **F10** —— `utf8_complete` 从首字节把一个字符补完，两个读取器都经过它，
  于是在过滤或新搜索提示处键入的一个 CJK 字符是**一个**键，而不是两三个乱码键。
  首字节的那些类用 `cw_range ''` 一次性建好，并**按成员关系**测试，与 `char_w` 测它的格宽表同法。
  **计划里标为"未定"的那个前提成立了**：`cw_range` 用**空**前缀确实能在 3.2.57 上构造出孤立的
  0x80–0xFF 字节，而 `[[ "$CLASS" == *"$byte"* ]]` 比较的是字节 —— 哪怕干草堆本身是非法 UTF-8 ——
  每一个首字节 C2–F4 恰好落进一个类，而续字节、0xC1、0xF5–0xFF 与 ASCII 一个都不落。
  那个 `printf -v n "%d" "'$b"` 的兜底没用上。续字节的读带超时，
  于是一个撕裂的序列卡不死卡片 1 秒一拍；一个不完整的序列**穿过去**而不是被丢弃，
  因为丢弃会静默吃掉一次按键，而那些兜底分支本来就会忽略它们用不了的东西。
  退格的回显如今擦掉 `disp_w` 量出来的那么多格，而不是一格 —— 一个 CJK 字形是两格。
- **F8** —— `read_query_input` 返回 0/1。Esc 与 EOF 的区分（2 与 1）它唯一的调用方从来没读过。
- **F9** —— 过滤的兜底分支从 `?)` 放宽，后者匹配一个**字节**、因此永远匹配不到一个拼装好的字符。
  **与计划的偏离，以及理由：** 一个光秃秃的 `*)` 会把方向键分支没有认领的每一条转义序列
  都变成查询文本 —— PageUp 会打进 `[5~`，F1 打进 `OP`，一个带修饰的方向键打进 `[1;5A`。
  在它上面加一个 `"["?* | "O"?*)` 分支把那些丢掉；单独的引导符仍然穿下去并被追加，
  与从前完全一样，因为一条序列后面总还有东西。
- **测试时发现、就地修掉：终端驱动一直在我们头上回显。** `read -s` 只把驱动的回显关掉**一次读**
  的时长、之后就恢复，于是两次读之间，驱动会把仍在队列里的东西回显出来 ——
  而任何一次突发输入都会留下这种东西。用在新搜索提示处粘贴"咖啡"（六个字节）量出来：
  终端收到最后那个字符**两遍**，我们的加驱动的（`e5 92 96 e5 95 a1 e5 95 a1`，
  而查询在内部是正确的 `咖啡`）。这**不是新问题** —— 批次 E 之前那个逐字节读取器在同样的突发下
  会把 U+FFFD 洒满一行 —— 只是当每一个多字节键本来就是乱码时，它看不出来罢了。
  一个自己画输入的 UI 用不着驱动的回显，所以 `stty -echo` 如今覆盖整个会话，
  并经与光标同一个 trap 恢复（一个双路径 rig 断言 `q` 之后**以及**信号之后都恢复了，
  因为一个退出时没把 `echo` 放回去的 uting，会让用户在自己的 shell 里盲打）。
- **关掉回显只是一半，另一半读起来像一个密码提示。** 报告过来的说法是"spin 字形上有一个锁图标"
  —— 而那从来不是我们画的字形：那一帧的 tmux 截屏里只有 `▖`，别无他物。
  终端看不见应用，它只看得见 pty 的两个开关，而且它会去轮询：
  **回显关着而规范模式还开着**正是 `getpass()` 的样子，于是 Ghostty 按那条启发式
  （`macos-auto-secure-input`）打开了 macOS 的 Secure Input，iTerm2 在光标处画了一把锁。
  `bash` 的 `read -rsn1` 在它自己那次读的时长内清掉 ICANON、之后再放回去，
  所以 uting **不**像密码提示的时刻，恰恰只有"某个键正在被读"的那些瞬间：
  每一次击键之间的空隙都在广告一个密码提示，一整次取数的全程也是 —— 那里根本没有读在跑。
  锁之所以落在 spinner 上，是因为 spinner 把光标停在它自己的字形上（`printf '%s\b'`，
  于是每一帧原地覆盖），而指示器就画在光标处。**在 Ghostty 上这不只是外观问题** ——
  Secure Input 在每一次搜索的全程真的生效了，把键盘从这台机器上其他每一个应用手里拿走。
  代码如今怎么做，只在 `AS-BUILT-tui.md` §11 说一次；给在这里写终端代码的人的坑在
  ARCHITECTURE.md §28；把它钉住的检查在 §27。值得带走的教训是：
  **这个 UI 一直在推理它*画*了什么，而终端读的是它*设*了什么** ——
  一个拥有 tty 的 UI 拥有它上面的每一个标志位，不只是它本来想改的那一个。
- **一条 rig 的教训，记下来是因为它先产出了一次假失败。** 信号路径的测试报告说 tty 被留在了
  `-echo`，而其实什么也没错：那个 harness 阻塞在 `sleep` —— 一个**子进程** —— 而 bash
  会把 trap 推迟到当前命令结束。TUI 阻塞在 `read`，一个会被信号打断的 builtin，
  所以 harness 必须以同样的方式阻塞，才算在量同一件事。与批次 B 那个从不关连接的探针同科：
  **一个在某一个细节上与程序不同的 harness，量的就是那个细节。**
- 另一条 rig 教训：`wait_for "Navigation"` 不能证明过滤模式已经离开，
  因为过滤**期间**菜单也会被画 —— 而过早发出下一个键，会让 `read_nav_input` 的 ESC 续读
  把它当作序列的第二个字节吞掉。要等的是过滤自己那个提示消失。
  **那次吞键是应用里的一个缺陷，而它当时是作为 rig 的一条性质被写下来的** ——
  如今读取器会保留那个早到的字节（见下面的视图切换那一轮）；而那条等待仍然是正确的 rig 纪律，
  因为"一帧显示了什么"与"读取器已经消费了什么"是两个不同的钟。
- **第三条教训，很久之后才发现，也是三条里最糟的一条：回显 rig 一直因为错误的理由在通过，
  而且为此烧掉一个核。** 它的阻塞循环是
  `while true; do IFS= read -rsn1 _ || true; done`，本意是像 TUI 那样阻塞在 `read` 里
  （上面第一条教训）。它从不阻塞。调用方把它作为一个**非交互** shell 的后台作业启动，
  于是 bash 把它的 stdin 重定向自 `/dev/null`，每一次读都立刻返回 EOF；
  `|| true` 把这个吞掉了，于是"像程序那样阻塞"变成了一个占满一个核的紧自旋。更糟的是，
  这个自旋**活得比它的 pane 还久**：rig 装的是 TUI 自己那套 `trap … INT TERM HUP`，
  而一个 bash trap 处理器**返回到循环**而不是退出，于是 `SIGTERM` —— 正是这个测试发出的那个信号
  —— 恢复了 tty 然后继续自旋。每跑一次漏一个孤儿；发现时有七个还活着，
  最久的 1 小时 21 分，16 核上负载 8.5。而这个测试自己那一步 `kill -TERM` 之所以通过，
  **恰恰是因为**那次泄漏：它先用 `ps` 把 harness 找出来，而只有一个还在自旋的进程才找得到。
  由此得出三条规矩：当主张是"像 TUI 那样阻塞"时，读的是**终端**而不是 stdin；
  绝不对一个"失败才是有趣情形"的读加 `|| true`（一次失败的读意味着 tty 没了，那是**离开**的理由）；
  以及 harness 里的信号 trap 必须**重新抛出**（`trap - $sig; kill -s $sig $$`），
  好让调用方观察到一次真正的信号死亡而不是一个幸存者。而那个让人不舒服的推论是：
  **一条绿色断言并不能证明那个机制真的跑过。** 前两条教训讲的是 rig 量错了东西；
  这一条讲的是 rig **什么也没量却报告成功** —— 那是再怎么反复读断言也抓不到的，
  只有去看机器实际在干什么才行。
- **第四条，来自原地渲染那一轮：一个没有窗口尺寸的 PTY 会渲染出一个只有一行的列表，
  而在它上面做的每一条帧断言都一文不值。** 一个光秃秃的 `pty.fork()` 从 0x0 起步，
  而环境里的 `LINES`/`COLUMNS` 修不了它 —— `term_size` 是**刻意**经 `/dev/tty` 读 `stty size` 的，
  于是 reflow 没有行数可花、只画了一行。那些帧看起来足够像真的以至于会被信任：
  页眉、横幅、**一条**结果、页脚。rig 必须在第一次读之前 `ioctl(fd, TIOCSWINSZ, …)`；
  之后同样的驱动产出了完整的十行页，行差异才有了意义。与上面三条同科 ——
  harness 在一个细节上与真终端不同，而那个细节正是这次测试的全部主题。同一条教训的后半：
  **断言下在单元格网格上，不下在字节流上。** "暂停恰好改变了一行"是一条关于
  `\033[K` / `\033[J` / CHA 施加**之后**的单元格的主张 —— grep 发出的字节做不出这条主张，
  而一帧正确的原地渲染，它的字节流看起来与它产生的那个屏幕毫不相像。
  教会这一课的那个 rig 是一个架在手写 pty 上的 `pyte` 模型；它已经没了，而这就是原因。
  **用一个终端模拟器去测一个终端程序，留下的是一个可能恰好在被测细节上与真终端不同的 harness。**
  `tmux` 是一个真终端：`capture-pane` 给屏幕类主张提供网格，`pipe-pane` 给字节类主张提供流，
  中间没有模型。

**由 reflow 地板修复关闭 —— 那个"既有的" rig 失败**（`bash -n` 干净，`shellcheck` 无增量，
每个套件都绿，而列表 rig 终于是 22/22 而不是 21/1）：

- **缺陷本体。** `psize` 的地板 1 赢过了一个为 0 的行预算，于是帧高出一行，
  在 62×12 且 `/` 打开时（以及 46×14、40×14）把页眉顶出去。修法在 `AS-BUILT-tui.md` §11：
  页脚被拆成四个可分别丢弃的部分，在行付不起时按价值顺序把行数还回来。
- **方法论上的教训，而这才是昂贵的那部分。** 那次失败在整个加固轮期间一直在屏幕上。
  从批次 C 往后每一批都跑了列表 rig、看见 `21 passed, 1 failed`、确认这次失败在上一个提交上
  也复现、写下"既有问题，不是这一轮的"，然后走开 —— 五次。那些陈述每一条都是**真的**，
  而它们合在一起是一种**永远不去看**的方式。**"在 HEAD 上也复现"回答的是"是不是我弄坏的"，
  而那与"它是不是坏的"不是同一个问题。** 一个被允许停在一个失败上的套件，
  会教会读它的每一个人"一个失败就是基线"；**要守的数字是零，而守住它最便宜的时刻，
  是它第一次动的那一刻。**
- **输入层 rig 里有两条断言永远不可能失败，把它们剪掉是同一次清扫的一部分。**
  `no "ï¿½"`（"屏幕上没有替换字符"）找的是把 U+FFFD 的 UTF-8 字节按 Latin-1 读回来的样子 ——
  六个字节，而无论读取器把输入搅得多烂，它们都不可能出现在一个 UTF-8 的 pane 里。
  把针改成一个真正的 U+FFFD 也救不了它：列表视图什么也不回显，
  所以那个读取器真的会切碎字符的、F10 之前的构建，留下的 pane 也是干净的。
  搅碎只在一条**回显你所键入内容**的行上才看得见，这也是为什么"精确匹配提示行"那几条断言
  才是要紧的 —— 在 F10 之前的构建上量过，`n` 提示读作
  `❯ New search (Esc or empty to cancel): 咖啡??啡?啡啡???`。第二条被删的是一条坐在那条精确检查
  上面一行的 `want "New search"`：严格更弱、同一瞬间，而且它在坏掉的构建上也通过 ——
  因为那条被搅碎的行里也含有 "New search"。与下面回显 rig 那条教训同科 ——
  **一条绿色断言并不能证明那个机制真的跑过** —— 而更锋利的推论是：
  **一条弱断言挨着一条强断言并不是免费的**：当强的那条被改掉时，被相信的会是它。

**i18n 那一轮关闭 —— F11，以及登记册从没写下来的那四分之三**（`bash -n` 干净，
`shellcheck` 无新发现 —— 与 HEAD 同样是 15 条，逐条对应；早先每个套件仍绿；两个新 rig，14 + 19 条断言）：

- **F11 立案时**是 `Playing`/`Paused` 与 `NOW PLAYING FOCUS`：三个字符串
  `S_PLAYING` / `S_PAUSED` / `S_CARD_HEAD`，画在四个点上（状态同时出现在列表横幅与卡片里）。
  两个点本来就**测量**它们打印的东西 —— 横幅对着 `disp_w` 过的固定部分省略标题，
  卡片的元信息行对着量出来的 `tail_w` 丢字段 —— 所以一个被翻译的字符串会按版式设计的方式优雅退化，
  而且中文在这里其实**更窄**（播放中 = 6 格，`Playing` 是 7），只把卡片丢 mode 的阈值挪了一格。
  卡片页眉刻意复用够到它那个键位提示的措辞（`S_FOCUS`，"focus card" / "专注卡片"）：一个视图，一个名字。
- **登记册漏掉的：另外九个点，全是瞬时的。** 启动提示、`n` 提示、`searching…`、
  `m` 与 `o` 的动作回显、无匹配文案、过滤横幅、`Press any key…` 与 `Quitting…`（两个调用点）
  也都是英文字面量。它们活过了三次审计，因为它们打进**滚动区**、下一次重绘就抹掉 ——
  它们没有一个出现在一张截下来的帧里，所以早先那几轮跑的每一条帧比对检查对它们都是瞎的。
  **登记册对 F11 的判断没错；它是不完整，而不完整的那部分恰恰是没有任何 rig 看得见的那部分。**
  记下来是因为它可以推广：**一次只读"重绘画了什么"的审计，看不见被重绘摧毁的那些 chrome。**
- **rig 为了抓住它们不得不改变形状，而且改了两次。** 用 tmux 轮询 `m`/`o` 的回显会因为错误的理由
  通过 —— 更多 与 排序 也在导航提示行里，所以 grep 这个 pane 能找到那个词，
  而那句话可能根本没被画过。那些回显改为在**函数层面**断言：一个 rig 在 `fetch_json` 被打桩的情况下
  调用真正的 `more_results` / `cycle_sort` / `new_search` / `press_any_key`，两种语言各来一遍，
  并断言整行内容以及每一个英文字面量的**缺席**。pane rig 保留只有 pane 才能展示的东西：
  任何重绘之前的启动提示、会话中途的 `l` 翻转、强制失败的尾巴，
  以及 `YT_ASCII=1` + 中文 —— 那里无匹配文案必须带着 ASCII 破折号出来，
  这正是那句话是"两个表条目在打印处组合"而不是"一个把破折号焙进去的条目"的原因。
- 设计上的后果在 `AS-BUILT-tui.md` §11（穷尽表规矩、三条约束，以及唯一一次刻意的英文改动：
  `for 50 results` → `· 50 results`，好让一个 `printf` 格式服务两种语序）。

**视图清理那一轮关闭**（`bash -n` 干净，无新 `shellcheck` 发现，批次 C/D/E 的套件仍绿，
以及三个新 rig：25 条卡片断言、9 张列表截图、19 条端到端 tmux 断言 —— 见 §27）：

- **第三个视图被删掉**，**卡片的标签随它一起**；列表的序号变成一个定宽列。
  三者都是 `AS-BUILT-tui.md` §11 的决定，记在那里而不是这里，因为它们是**形状**而不是缺陷 ——
  但其中两个让开放发现缩了水。F11 不再是一个版式问题、变成两个字符串的替换
  （已经没有 `%-8s` 要按字节补白了），而 mini player 所体现的那处 F7 重复是**被删掉**而不是被记录。
- **又一条 harness 教训，同样来自一次假失败。** 把行的正则放宽到接受"标记出现在序号原来的位置"
  （`^ *(\d+\.|>) `）之后，四条过滤模式的断言失败了：过滤自己那条光标行是第 0 列的 `> <query>`，
  于是放松后的模式把它当成一条结果行匹配上了，然后报告说它没有时长轨。
  这条教训活得比教会它的那个形状更久 —— 标记回退把序号放回了每一行，
  于是那些 rig 如今匹配 `^(> |  ) *[0-9]+\. `，它排除光标行的理由更好：
  **一条结果行永远有序号，而光标行永远没有。** 无论如何，要点与批次 E 那两条教训一样：
  **断言必须点名它想说的那个东西，而不是那个东西碰巧包含的一个字符串。**

**列表视图的轨/details 那次工作关闭：** 最初那次审计还带着 F4 —— 播放元数据靠重新切分**显示串**
再推导出来，而它之所以能解析正确，只是因为 `clean` 折叠了空白，
并且它把自己解析出来的 `views` 字段扔掉了（证明那次切分从来就不是一份契约）。
`play_selected` 如今读那一行自己的字段（`AS-BUILT-tui.md` §11），
而那个修复必须绕开的 tab 折叠风险，正是记录分隔符是 US 而不是 tab 的原因。
同一次审计还指出这份文档 §11 的图把新搜索/更多结果写成了 `s`/`S` 而不是 `n`/`m`；也一并改正。

**输入延迟那一轮关闭 —— Enter 键被当成了一个 UTF-8 首字节：**

- **对 Enter 的一次单字节读，结果是空串。** `read` 会剥掉它的 `\n` 分隔符，
  而 ICRNL 在 `read -n1` 建立的非规范模式下也把 Return 变成 `\n` ——
  这正是为什么下游每一个 case 分支早就把 `""` 与 `$'\n'`、`$'\r'` 并排列着。
  而 `utf8_complete` 拿那个空串去对首字节表做测试，**而 `*""*` 匹配每一个模式**，
  于是 Enter 被分类成一个 2 字节首字节，坐在下面那个 `read -rsn1 -t 1` 里
  等一个不可能到来的续字节。代价：每次 Enter 之后整整一秒的死屏，
  外加只要用户在那一秒里按了什么就会被**吞掉**一次击键（它被追加进 `CHAR_IN`、被读成一个错键）。
  修法是对空串提前返回。
- **这个 bug 是被用户在不知情的情况下已经做过的一次 A/B 定位的。** 报告是
  "启动提示之后有一个很大的延迟，但查询写在 argv 上时没有" —— 两条路径完全共享 `fetch_json`，
  唯一的差别是 `read_query_input`。在一个 pty 上从 Enter 计时到 `searching` 那一行：
  **1038 ms 对 20 ms**，而修复把提示那条路径带到 32 ms。同样这一秒在每一次 `play_selected`
  之前也在付，因为 `read_nav_input` 让 Enter 走同一次调用 —— 在那里看不出来，
  因为一次播放本来就要好几秒，这也是为什么它被报成一个**提示**的 bug。
- 另外三处 `== *"$var"*` 的 glob（`char_w`、`cluster_back`）在同一轮里审计过，
  它们不可能收到空参数：它们收到的永远只是 `i < ${#s}` 时的 `${s:$i:1}`。

**detached 输入那一轮关闭 —— 播放器一直在吃 TUI 的键：**

- **缺陷在 §9.1 的启动处，而症状在 TUI 里。** `[` 与 `]` "什么也没做"。
  它们解码是对的（`0x5b`/`0x5d`，用一份加了埋点的副本验证过），IPC 也是通的
  （`[ [ ]` 三次的 `time-pos` 是 `30.47 → 20.47 → 10.45 → 20.43`），
  所以既不是键位的错、也不是线路的错：mpv 坐在调用方的 tty 上，赢了对那个字节的争夺。
  机制（`set -m` 压制了 bash 自动的 `/dev/null`）与 `lsof` 证据见 `AS-BUILT-player.md` §9.1。
  值得记下的是这些键**一直都在 AS-BUILT-contract.md §1.4 与 ARCHITECTURE.md §18 里** ——
  设计记录了三个 UI 从没告诉过任何人的键，而一旦它们被加进提示块，
  与 mpv 的碰撞面就显形了。
- **一处更正，记下来是因为差点有两个新缺陷立案在它上面。** 这一轮起初的结论是：
  mpv 占着 tty 也破坏了 bash 的 `read -t 1`、因而杀死了列表视图那个一秒时钟 ——
  证据是一个一直为空的 `PT_CUR`，以及阻塞了 12 秒与 41 秒的读。两半都是错的。
  一次"mpv 在 tty 上/不在 tty 上"的 A/B 显示两边都是 **4/4 超时正常**，
  而滴答链对着一个本地合成源跑 6/6；那些长读是 YouTube 把本次会话自己反复的搜索限流到
  57–90 秒，这让 harness 卡在 `play_selected` 的命令替换里、没留下任何一个空闲秒给滴答去触发。
  **一次穿过饱和网络做出的测量不是对这个程序的测量** ——
  与上面回显 rig、探针对 mpv 那两条教训同科，也是那个时钟最终改为对着
  `av://lavfi:sine` 而不是一个视频来验证的原因。

**视图切换那一轮关闭 —— 视图之间的每一条边都走了一遍，而不只是被报告的那一条**
（`bash -n` 干净，`contract.sh` 绿，每个修复都在 tmux 下驱动过）：

- **存储是一扇单向门。** `b` 与 `h` **替换**那些行，而没有任何键能把它们放回来：
  `m`/`o`/`e` 正确地拒绝（没有查询可重取），`Esc` 在列表里是一个**有文档记载的 no-op**，
  于是唯一的出口是 `n`（重打一条查询）与 `q`。修法在 `AS-BUILT-player.md` §9.4 ——
  打开者把它即将覆盖的东西收起来，回去的那个键再还原。**这是用户报告的，不是某条检查发现的**，
  而这才是发现之下的那个发现：既有的每一条 TUI 检查都是驱动一个键、再断言应用活了下来，
  而"活下来"恰恰正是一扇单向门会做的事。`contract.sh` 如今断言的是**往返**，两半都断言。
  **它先以 `Esc` 上线过，而那是错的，错在一个可测量的地方** —— 在 bash 3.2 的地板上，
  一个孤立的 Esc 要花整整一秒，于是"一个什么都不做的键"的修复变成了"一个感觉是坏的键"。
  改成 `h` / `b` 开关之后，一扇存储的门顺势变成了一条通则，现在写在 `AS-BUILT-tui.md` §11：
  **一个模式由进入它的那个键退出**。
  - **而 `b` 那扇门后面还有一次提问，那一次也是用户报告的**（2026-08-26）：`b` 打的是存储自己的
    `--ls` 散文，然后弹一个与搜索提示长得一样的 caret —— 报过来的说法是"它不给我看有哪些列表，
    只给一个没用的搜索框"。屏幕上那一行确实在，所以这不是一个渲染 bug，而是一个**提问的形状**
    不对：存储明明知道有哪些名字，却要用户凭记忆把名字打进来。修法在 `AS-BUILT-tui.md` §11
    （编号 + 量出来的名字列 + 序号在 TUI 里解析）。`contract.sh` 的 TUI 段现在把这条路
    整条走一遍 —— 列出来、按 `1` 打开**那一个**（表头点名，于是差一位是看得见的）、再按 `b` 出来
    —— 三条断言都在落地前被看着变红过（选单不打行、序号不解析，各一次）。
- **过滤循环只做了主循环每帧工作的一半。** `filter_live` 是同一个屏幕上的第二个键循环，
  它调了 `check_player_alive` 却没调 `player_check_ready`，
  于是在 `/` 打开的整段时间里，起始态的 spinner 既不前进也不收敛 ——
  按 Enter、再按 `/`，一个死住的 spinner 帧会一直坐在那儿，越过它自己那个 20 秒上限。
  **任何未来的每帧职责都必须同时加进两个循环，或者两个都不加；它们不是一个循环。**
- **`apply_filter` 从一条七字段的行里读了六个名字。** 记录在播放列表成为行源时长出了 `engine`
  （`AS-BUILT-player.md` §9.4），而这个读取器没有跟着加宽。`read` 把剩余部分全给最后一个名字，
  于是 `live` 到手时是 `is_live<US>yt`，那个 `is_live` 判断永远不可能为真，
  在过滤里敲 `live` 从此什么也匹配不到。它藏了这么久的原因值得记：
  那个循环会把它刚切开的字段**重新发出**，于是把那个带尾巴的变量贴回去产出的是一条
  **逐字节相同的行** —— 每一行都完好地活过过滤，错的只有那个合成出来的检索串，
  也就是**一次没有可见损坏的损坏**。
- **Esc 会吞掉在它之后键入的那个键**，在每一个视图里。一个孤立的 Esc 只有在它后面那个字节被读掉
  之后才知道它是孤立的，而读取器把那个字节丢了 —— 于是 Esc 那一秒窗口内的任何键都会消失
  （两个方向都量过：`Esc` 然后 `o`，`sort=relevance` 没变；`Esc` 然后右方向键，页码还在 1）。
  对于首字节又是一个 `\x1b` 的键更糟：引导符被吃掉，方向键的**其余部分**作为字面键到达，
  而 `[` 是 seek 键 —— 于是 `Esc` 然后一个方向键不只是丢了那个方向键，它还 seek 了一下。
  读取器如今把它读得太早的东西**留住**，按那个字节可能的两种形态：
  一个完整的键（`PENDING_KEY`，在暂存时就做 UTF-8 补全，因为续字节还在队列里），
  或者解析中的一个位置（`PENDING_ESC`）。它是在确认上面那个修复时发现的 ——
  Esc 在列表里一直是 no-op，直到它**短暂地**成为离开一个存储的路，所以在那里从来没有人按过
  这个键。那个绑定后来被开关取代了，而这个修复**留下**：它从来就不是 Esc 专属的 ——
  它丢的是**任何一个转义字节之后**的那个键，而 Esc 至今仍是卡片与过滤框的出口。
  一秒窗口是"ESC 既是一个键、又是每个方向键的引导符"的代价；被修掉的是**丢掉下一个键**，
  不是那个窗口。**它其实已经被写下来好几年了 —— 作为一条 rig 教训**
  （§27，"下一个键发得太早"）：harness 被教会绕着这个行为去等待，
  而不是把这个行为读成一个 bug —— 一个缺陷就是这样藏进一条写测试的惯例里的。

## 27. 验证矩阵

**上一次运行 —— 这是一次测量，按当次运行填进来的，不是一个要维护同步的常数。** 每个套件都在
最后一行打印自己的计数，那是那个数字唯一的家；这里的条目记录的是某一次运行在某一天花了多少，
它**按设计会过期**，而不是靠漂移过期。*2026-08-26，两个套件都绿*：
`contract.sh` **185 ok / 0 failed / 57s**，其中 `--offline` 那一半 **144 ok / 14s**、
零网络调用；`playback.sh` **42 ok / 0 failed / 62s**，之后 `pgrep mpv` 为空。
**62s 里没有一秒是猜的**：约 30s 是七次真实的引擎解析（`ut-play` 自己量到的换曲中位数 4.3s），
约 19s 是收听日志那一段把一首 19 秒的曲子**放到它自己的结尾**——这两半在"没有替身"这条规矩下
都不可压缩。从 68s 降到 62s 的那 6 秒，是三个 `sleep` 变成了有界轮询（见那个文件的门口），
而快只是次要收获：一个固定的猜测在机器只是慢的时候也会变红，而一次不是 bug 的红，
仍然要有人去查一遍。*上一轮的数留在这里当网络方差的证据*：`contract.sh` 2026-08-25 当晚
五次运行落在 81–109s，同一个文件、同一批检查。

**这两个数字各自的成分**（计数本身在上面，只说一次）。`contract.sh` 如今**先跑离线那一半**，
而且能只跑那一半（`--offline`）：实网那一半约 43s、tmux 约 4s。
flag 门在 1s 变红、空闲生命周期 1s、死亡记录 2s。那 14 秒里有 5.5s 是播放列表存储对着一个
**活着的**持锁者刻意的自旋 —— 旁边那条陈旧锁检查只花 0.1s，因为陈旧判定挪到了自旋**之前**
（AS-BUILT-player.md §9.4）。改掉的三个数：文件门口从前写 `~80s`（实为 57s）、
"一次 5s 锁自旋"（实为三次、17s，其中两次是同一个失败被问了两遍）、
"~25s 的 tmux"（实为 4s）。**一个成本注释也是一句主张**，而这个文件的规矩是主张要被执行、
不是被阅读 —— 这三个数没有任何一条检查在看着它们，于是它们静静地漂了。

这个顺序在文件里是作为**契约**陈述的，因为其中一部分是承重的
（离线在前；死亡记录夹具，然后 TUI 段放最后，因为 pane 里的 `uting` 会轮询 `--status`
而每一个生命周期动词都回收）。`tests/` 下**三个**入口点全都把 `TMPDIR` 指向自己的目录 ——
两个套件加 `drive.sh` 驱动器，后者是最后一个还在用用户目录的 —— 所以它们没有一个够得到
用户正在听的那个播放器的状态目录。两个套件也把 `UT_STATE_DIR` 指向自己的：
一个 detached 播放器每首曲目写一行收听记录（`AS-BUILT-player.md` §9.6），
没有它的话每次运行都会往用户真实的历史里追加一打没人听过的曲目，
而历史与播放器不同，不是 `--stop` 收得回来的东西。`drive.sh` 刻意**不**重定向 `UT_STATE_DIR`
—— 从它截下来的一帧应该显示一个人看得见的那个存储 —— 改为给 pane 喂 `UT_HISTORY=0`，
在不清空**读**的前提下压住**写**。

**只做功能测试，且只有两个文件。** 渲染器 rig（`tui_pane.sh`）与它那个单元格网格证明器被移除了：
**版式是在一帧进入文档时被证明的**（`.claude/skills/capture-pane`，它仍带着 `assert_pane.py`），
而套件断言的是**存活** —— TUI 起来了、扛过两次 resize、按 `q` 以 0 离开。
唯一的例外是那次**往返**（`h` 打开日志、再按 `h` 回到搜索），它断言的不是画面而是**行源**：
表头上 `items=` 与 `results=` 的差别是一个状态，不是一幅版式。
`playback.sh` 出于同样理由丢掉了它那个 banner-tick 用例，如今根本不需要 tmux。
这笔交易放弃了什么，明说出来：一个会折行的 CJK 标题、一条不再右贴的轨、
或者一次会清屏的重绘 —— 测试抓不到它们，只有下一次文档截帧才会。
**有一条时序主张随它们一起走了，而这里点名它是因为别的地方都没点名：**
一个 detached 播放器会靠 TUI 自己那 1 秒滴答把卡片从 *Starting* 翻到 *Playing*、不需要按键。
那需要一个 pty；`playback.sh` **刻意**没有终端，`contract.sh` 的 TUI 段**刻意**不起播放器，
而 `drive.sh -k Enter -w Playing` 只是等那条横幅出现、不对它断言。
所以它今天在任何地方都没有被证明，而诚实的条目就是这句话本身，
而不是某处一条半覆盖它的检查。

**有两条检查被写出来、被盯着看、然后被撤掉 —— 记在这里是因为登记册就是覆盖率决定该待的地方，
也因为一条撤掉却不留痕迹的检查会被重新加回来。** 两条都栽在同一场考试上：*它没法被弄红。*

- **`live_props` 里那个 `head -n <count>` 的管道关闭**（`AS-BUILT-player.md` §9.3）。
  对着真实对端它不可能失败。把 `head` 换成 `cat` 再跑，两边都量到 **0.04 s**，
  所以一条对它的时序断言无论代码怎样都会通过。那道守卫曾经看起来省下的 1.11 s，
  是一个*脚本化对端*的空闲计时器，而那个对端随着其他每一个替身一起没了。
  守卫作为防御留在播放器里，但不配一个假装套件证明过它的绿钩。
- **一条被停止的队列不立墓碑。** 把子进程那个 `stopped` 分支整个禁掉，`failed[]` **仍然**是空的，
  所以这条检查对着坏掉的代码也是绿的。这个主张改住在它能失败的地方：
  `contract.sh` 用夹具驱动墓碑的边界（一次正常播完不写、一份没有墓志铭的日志不写），
  而那才是"关于**回收器**记录什么"的规矩该待的地方。

`tests/playback.sh` 在那两个位置各带一行指针，于是下一个读者找得到理由，
而文件不必把它承载两遍。

> **观察到的抖动 —— 共享状态那一条已 CLOSED，这里是它的记录。** 2026-08-23，三次运行里的第一次
> 有十条检查失败，后两次以 78/78 原封不动通过；2026-08-24，同一簇在另一个窗口开着一个普通交互式
> `uting` 时红了两次，几分钟后什么都没改就 3/3 通过。机制比"两次运行重叠"更锋利：
> 死亡记录夹具住在 `${TMPDIR}/uting-$(id -u)/players` 下，只以 uid 为键，
> 而**每一个生命周期动词都回收** —— 于是从任何地方来的一次 `ut-play --status`
> （包括一个 TUI 的存活轮询）都会在墓碑夹具被创建与被读之间把它删掉。
> 持久的修法是每次运行一个状态目录，如今 `tests/` 下每一个入口点都建它：各自 export 自己的
> `TMPDIR`，于是同一个 uid 上不会有第二个 uting 共享这个目录。留下来的是同一个机制在**单次运行
> 内部**仍然隐含的那条**顺序规矩** —— 死亡记录段必须排在 TUI 段之前，因为 pane 自己的
> `--status` 轮询会回收 —— 而它写在那一段自己身上，不是靠版面顺序碰巧成立。
>
> **第二条已经追平，且它是一条真实的种族条件而不是环境问题。**（见 §25.1 的相应条目。）
>
> **第三条，观察到两次、且仍未定位 —— 记下来是因为一条没被记录的抖动，是一条第二次没人认得出的
> 抖动。** 2026-08-25，两次背靠背运行的第一次里，TUI 段最后两条检查一起红了 ——
> *"quits on q with 0"* 与 *"hands the tty back on exit"* —— 而第二次以 177/177 原样通过。
> **这一对一起失败正是那个信号**：第二条读的那行 FLAGS 是由打印 `RC=` 的同一条 pane 命令打出来的，
> 所以两者都没出现，意味着 `uting` 在轮询允许的 10 秒内没有离开。它不是"退出很慢"：
> 事后量过，七次运行（三次朴素、四次照着该段精确的 boot → 62x20 → 26x24 → `q` 序列驱动），
> **每一次退出都落在 186–250 ms**，也就是说预算是成本的五十倍。两个可能吞掉按键的应用内机制
> 找过并排除了：`$TMUX` 设置时会跳过 OSC 11 背景查询（AS-BUILT-tui.md §11），
> 所以读取器里不可能坐着一个终端回复；而 `q` 不是 UTF-8 首字节，所以 `utf8_complete` 吸收不了它。
> 剩下的是这台机器：那天下午这个 checkout 上还有第二个会话在工作、也跑过同一个套件，
> 而两者有没有重叠没有被记录下来。作为**未定位**归档，附带那次测量，而不是解释掉。
>
> **它在同一天傍晚又发生了 —— 同样那两条检查、同样是两次运行的第一次、第二次干净 ——
> 而这一次它留下了东西。** 那次运行之后七分钟，一个
> `ut-play --engine yt -f audio --` 加一条来自 pane 自己结果列表的 URL 仍在运行，
> 挂在 PID 1 下，它的 mpv 的 socket 在那次运行自己的 `uting-contract.*` 目录里。
> 那一段里没有任何东西会按 Enter，所以 **pane 收到了套件没有发出的输入**：原因仍未定位。
> 这次复现真正定下来的是：上面那个"机器上有第二个会话"的读法是较弱的那个，
> 因为那天傍晚一个也没有 —— 当天其余的工作在七小时之前就落地了。
>
> 那个播放器解释的是**后果**，而这一半如今已经修好。`uting` 在 `cleanup_on_exit`
> （EXIT INT TERM HUP）里停掉自己的播放，所以一个**离开了**的 TUI 会带走它的播放器，
> 而一个**没有**离开的 TUI 就是一个仍然攥着播放器的 TUI —— 那两条红与一个活着的播放器
> 是同一个事件，不是两个。`contract.sh` 的 cleanup 从前只有 `rm -rf`、别无他物，
> 于是状态目录没了、播放器的**记录**也跟着没了：那个进程活过了 `--stop --all` 找得到它的能力，
> 除了 `kill` 没有任何东西能让那段音频停下来 —— 而这发生在一个自己 docstring 写着
> "不碰你的状态"的文件里。三处改动，每一处都由破坏它来证明（一次按 Enter、然后永不按 `q` 的运行）：
>
> - cleanup **先回收再删除**，并报告一个**限定在本次运行自己 socket 目录**的孤儿 mpv ——
>   这是 `playback.sh` 的 cleanup 早就在用的顺序；
> - 一条检查 *"the TUI left no player behind"*，于是泄漏是**可见的**而不只是无害的。
>   它只在这个精确情形下变红，而这正是它值一行的原因；
> - `q` 不生效时**转储** pane。那一帧是"哪个读取器吃掉了那个字节"唯一的证人，而它随 session 一起死；
>   在破坏性运行里那份转储的第三行带着 `▶ Playing:`，
>   而这恰恰是第一次发生时无从记录的那个事实。下一次发生时它会自己说出来，
>   而这一次是靠重建才推出来的。

**四件这个套件刻意没有的东西，记下来，好让每一件都是被有意拒绝的、而不是被反复重提。**
没有一件是缺口；每一件都是一个带理由的决定：

- **不加 `tests/lib.sh`。** 两个套件互相独立、各自能单独跑通是**设计**，不是意外，
  而 CLAUDE.md 的"no rig layer"直接管着这里。重复的是大约二十行 `report`/`ok`/`bad` 的账房代码，
  可以接受；而重复的**论证**不可以 —— 这正是 `TMPDIR` 那套理由**只说一次、被指两次**的原因。
- **不加 `tests/all.sh`。** 两条命令，而 CLAUDE.md 已经写明各自什么时候跑：
  `contract.sh --offline` 每次提交前、完整的 `contract.sh` 每次推送前，
  `playback.sh` 播放器改动时。
- **不加"跳过网络"的环境**变量**开关** —— 环境变量是给 set-once 调优用的，而"跑不跑网络"是
  一次**每次调用**的选择，那是 flag 的形状（CLAUDE.md 的分法）。这一条从前是连 flag 一起拒的，
  理由是它会造出**第二种绿**的含义："你拿到的是哪一种绿？"**2026-08-26 反转成 flag**：
  `tests/contract.sh --offline`。反转它的论证有三条，前两条是这个文件自己欠的：
  (a) 离线/在线那条边界**本来就是承重的**（就写在这个文件的段序契约里），而一条谁也停不下来的
  边界，只有作者一个人用得上；(b) CLAUDE.md 要求**任何改动**都跑这个文件，包括一次注释修订，
  而一个没有 YouTube 就跑不起来的门，是一道大家学会跳过的门；(c) "第二种绿"是靠**输出**答掉的，
  不是靠不给这个选项 —— `--offline` 是同一次运行的**前缀**（同样的检查、同样的顺序，只是在
  第一次实网调用前停下），停下的地方**点名**了没跑的是什么，而且提交/推送两级写进了 CLAUDE.md。
  实测：全跑 ~57s / 185 条；`--offline` ~14s / 144 条、一个包都不发。
- **不加只为抬高计数的检查**，也不加任何时序或渲染画面断言。这份登记册描述的那轮加固给两个套件
  净增了**零**条检查：它让既有的诚实起来、删掉三处重复、修掉一个竞态。

**这里刻意不按路径点名任何*临时*检查。** 例外是三个挣到永久位置、提交在 `tests/` 下的文件 ——
两个套件 `contract.sh` 与 `playback.sh`，以及 TUI 驱动器 `drive.sh`
（它什么都不断言，存在的意义是回收 session 被杀之后留下的 detached 播放器）——
根 README 按名字描述它们，因为**没有指针指向的东西，贡献者跑不了**。
（今天这个形状之前有过两个基于 pty 的 rig，然后是一个 tmux 渲染器 rig：
一个从 0×0 起步的 pty 产出看似合理的一行帧 —— 一次错误的绿 —— tmux 修好了那个，
但"对画面本身做断言"这件事最终整个走掉了。）此外这个套件用来验证过的一切，
都是一个仓库不跟踪的 `tmp/` 下的一次性东西（`.gitignore`：`**/tmp/`），
所以按路径引用它们是一个 checkout 兑现不了的承诺 ——
它只在恰好一台机器上解析得开，直到那台机器的 scratch 目录被清掉为止。
**耐久的是每条检查的*形状***，而下面的条目记的就是这个：驱动了什么、怎么观察的、
以及活下来的断言数。一条检查从描述重建很便宜，而当它点名的那个文件已经不在时去信任它很贵；
§25.1 那些 harness 教训留在这里也是同一个理由 —— 它们是一个已被删掉的 harness 里值得留下的那部分。
